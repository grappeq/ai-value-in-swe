## Tier, era, independence

- **Tier: A (quasi-experimental, peer-reviewed, with an actual counterfactual design) — borderline with B; the specific caveat is recorded so the human can re-grade if they read the causal design differently.** The RQ3 churn analysis uses a Regression Discontinuity Design (RDD) with a per-repository, project-specific cutoff (first self-admitted GenAI mention), OLS pre/post trend fitting, and — importantly — three explicit robustness checks: (1) parallel RDD models re-run against two *global* cutoff dates (GitHub Copilot's June 2021 release, ChatGPT's November 2022 release) instead of each repo's own adoption date; (2) bandwidth sensitivity checks at ±90/±180/±360-day windows; (3) placebo tests shifting the cutoff date forward/backward in time. The authors report the RDD findings held stable across all three checks. This is a real counterfactual design (PROTOCOL §3's Tier A bar), not a bare before/after comparison — but note the counterfactual is a **within-repository extrapolated pre-trend**, not a cross-sectional control group of non-adopting repositories; there is no matched comparison group of repos that never adopted GenAI. On balance this sits above typical Tier B telemetry (no randomisation, no counterfactual) but short of an RCT or a design with an external control arm — **graded A with this caveat explicit, not silently.**
- **Era: E1/E2, NOT E3 — confirmed explicitly by the authors' own stated limitation, despite the paper's 2026 publication date.** This is the single most important scoping fact for using this source. The study's GenAI-adoption signal is restricted to explicit textual mentions of **ChatGPT and GitHub Copilot only** (regex-matched on `chat[ -_]?gpt` and `co[ -_]?pilot`); the authors state this directly as an External Validity threat: *"our focus on ChatGPT and GitHub Copilot might not capture the usage patterns of other GenAI tools that were released more recently, e.g., Claude Code."* Per PROTOCOL's era-assignment rule (tag by tool modality studied, not publication year), this makes the paper's adoption/churn analysis **E1/E2 (autocomplete + chat-assisted)**, even though the underlying repository timelines and the 2026 publication date could nominally overlap the agentic era. This paper cannot speak to agentic-tool (Claude Code, Cursor-agent, Devin-class) churn effects at all — a limitation it shares, in a mirror-image way, with GitClear's own era-aggregation problem (GitClear also cannot modality-segment its churn signal — see sources/gitclear-2025.md Appendix A6 note). **Both sides of this contradiction are pre-agentic or era-unsegmented; neither side settles the E3 question.**
- **Independence: high — no COI to flag.** All seven authors are academic-affiliated (Kyushu University, NAIST, University of Bari, Singapore Management University, University of Osaka, Shinshu University, Heidelberg University); acknowledgments cite EU public funding (for Calefato) — a public research grant, not vendor/corporate sponsorship. No tool vendor, consultancy, or commercial code-analytics company is an author, funder, or named data provider. This is a clean, independent-academic counterpoint to GitClear's dual-vendor-sponsored Tier B report — directly the kind of independent corroboration/refutation PROTOCOL's COI rule calls for.

## Method & population/dataset

- **Measurement basis: measured (telemetry)** throughout the churn analysis — server-side git history mining, not self-report. (The paper also runs a small, separate developer survey for RQ2 — governance/policy perceptions — but that is a distinct research question, not part of the churn measurement basis.)
- **Repository sampling, verified from the paper's own Figure 1 pipeline and Section 2.1 text (NB: an earlier, less careful extraction pass wrongly reported a "≥50 stars" criterion — this is NOT in the primary text and should be disregarded):**
  1. Initial pool: 207,062 GitHub repositories (via the GitHub search tooling of Dabic et al. 2021), restricted to the five most-used languages per the 2024 GitHub Octoverse report — Python (77,542), JavaScript (48,500), TypeScript (37,424), Java (25,160), C# (18,436).
  2. "Engineered software project" filtering (Munaiah et al. 2017 criteria, adapted): exclude repos with no or non-standard license; exclude repos with no GitHub release, fewer than 2 contributors, or archived status; exclude the bottom quartile (Q1) by #issues, #PRs, #contributors, and lines of code; exclude repos with a code-ratio (LoC / (LoC+comments)) outside the 97% confidence interval (removes near-zero-code and comment-only/near-code-free repos). Result: **14,785 repositories** (Java 5,060, C# 3,544, TypeScript 2,464, Python 1,875, JavaScript 1,842).
  3. RQ3-specific eligibility: repo created **before the ChatGPT launch date (30 November 2022)** and with **≥1 commit on or after that date**; forks excluded.
  4. Mention search: regex search for ChatGPT/Copilot mentions in source-code comments, documentation files, and commit messages (specific file-extension allowlist per language, to cut API-reference false positives) → 3,004 raw mentions → manual review (two independent coders, sample-size-calculated at 341 mentions for 95% CI / 5% margin, 4% disagreement rate, Fleiss' κ 95% CI (0.87, 0.95) "almost perfect") → **1,292 true-positive self-admitted GenAI usages across 156 repositories** (11 Python, 12 JavaScript, 37 TypeScript, 47 C#, 49 Java).
  5. Final churn sample: **151 of the 156 repositories**, excluding 5 that had explicit *prohibitive* GenAI policies (per the RQ2 policy analysis) — i.e., repos that banned GenAI use were dropped from the "did adoption change churn" analysis, which is methodologically correct (you cannot study post-adoption churn in a repo that never adopted). For the RDD specifically, a further 2 repositories were excluded for insufficient time-series data (minimum 5 weeks with ≥1 commit, ≥1 week either side of the cutoff), leaving **149 repositories** for the RDD analysis proper (Wilcoxon/Mann-Whitney results use the full 151).
  - All OSS, English-language-dominant (the paper notes this as an external-validity limitation), GitHub-only (no GitLab/Bitbucket). No explicit repo-size or star-count filter beyond the quartile-based engineering-project filter above.
- **Adoption-attribution method:** the **first self-admitted GenAI mention in a repository's commit history** is used as a proxy adoption date, `t_mention`. This is an explicit proxy, not a ground-truth adoption date — the authors flag this directly (Section 8.1/8.2): self-admission likely **understates true adoption** (developers who use GenAI without leaving a textual trace are invisible to the method, so churn effects from "silent" adopters are not captured at all) and the mention date may **lag** true first use by an unknown amount. Both biases plausibly push toward finding a smaller/null effect rather than manufacturing a spurious one — relevant for interpreting the null.
- **Churn definitions — deliberately matched to GitClear's own definition, plus one addition.** The paper explicitly states it uses *"the code churn, as defined in the GitClear report"* as its primary definition, then adds a second granularity:
  - **Line-based churn** `chL(c) = (#lines changed again within 14 days) / (total #lines changed by commit c)` — this is the direct analogue of GitClear's 2-week/14-day churn metric.
  - **File-based churn** `chF(c) = (#files changed again within 14 days) / (total #files changed by commit c)` — a new, coarser granularity the authors added "to gain a more comprehensive understanding."
  - **This closes off the "different churn definition" reconciliation candidate for the contradiction** (see Cross-ref below): the definitions are the same 14-day/2-week reversion-or-update window, not merely similar.
- **Identification design:** repository-level **before/after** comparison around each repo's own `t_mention`, using a **360-day pre-adoption window and 360-day post-adoption window**, analysed three ways:
  1. **Wilcoxon signed-rank test** (paired, within-repo, comparing each repo's average pre- vs. post-churn), effect size = Wilcoxon *r* (thresholds: negligible <0.1, small 0.1–0.3, medium 0.3–0.5, large ≥0.5).
  2. **Mann-Whitney U test** (independent samples, pooling all commits across all 151 repos, pre vs. post), effect size = Cliff's δ (thresholds: negligible <0.147, small 0.147–0.33, medium 0.33–0.474, large ≥0.474).
  3. **Regression Discontinuity Design (RDD)**, weekly-aggregated commit data, OLS with 4 parameters (intercept, time trend, treatment effect, interaction term), run per-repository on the 149 eligible repos, with the three robustness checks described in the Tier note above (global cutoffs, bandwidth variation, placebo tests).
  - **No cross-sectional control group** of non-adopting repositories is used anywhere in the design — the counterfactual is each repo's own extrapolated pre-adoption trend, not a comparison population. This is the design's main limitation relative to a true DiD-with-controls.

## Key findings — measured, all telemetry

**Primary finding (headline, directly contradicts the GitClear churn narrative):**
1. **Pooled average churn fell, not rose, after adoption**, across all 151 repositories' commits pooled (Mann-Whitney): **file-based churn 0.17 → 0.06** (p<0.05, Cliff's |δ|=0.42, medium effect); **line-based churn 0.68 → 0.50** (p<0.05, Cliff's |δ|=0.09, negligible effect). [T4/T5-adjacent quality-debt signal; measured; era E1/E2 per above]
2. **Per-repository (Wilcoxon), most repos showed *some* significant change, but the direction was predominantly downward:** of 151 repos, 119 had a significant file-based churn difference (30 increasing, **89 decreasing**); 120 had a significant line-based churn difference (33 increasing, **87 decreasing**). Restricting to medium-or-large effect sizes: 11 repos had an increasing file-based churn (vs. 49 decreasing); 15 repos had an increasing line-based churn (vs. 49 decreasing). [measured]
3. **RDD (the design with the strongest causal claim), 149 repos: only a minority showed *any* significant discontinuity at all** — 26/149 significant for file-based churn, 30/149 for line-based churn (i.e., the large majority, ~80%, showed no statistically significant discontinuity in either direction at the adoption cutoff). Among the significant file-based cases: 15 had an upward trend (12 of those with a *decelerating* / negative slope, only 3/26 = 11.5% showing a genuinely accelerating upward trend) and 11 had a downward trend. Line-based: 15 upward, 15 downward. **The authors' own conclusion: "We cannot conclude that there is a general trend toward increasing code churn."** [measured; this is the paper's central null result on the general-increase question]
4. **Heterogeneity by GenAI-assisted task type (RQ1 taxonomy applied to RQ3):** churn effects concentrate almost entirely in **generation tasks** (code, test data, test methods, regex, comments) — 10 of 16 significant file-based RDD discontinuities and 9 of 15 significant line-based discontinuities involved generation tasks, vs. essentially no consistent pattern for **optimization** (refactoring/code-improvement mentions: 1 significant case) or **maintenance** (comment/dependency/version-update revisions: 0–2 significant cases). **This is a genuine positive/non-null finding, recorded with equal diligence to the null overall result:** GenAI-*generation* usage specifically is more churn/rework-associated than other GenAI use, even though the aggregate/general effect is null-to-negative. [T5/T4; measured; the paper's authors frame this explicitly as evidence that "GenAI output has a provisional nature" for generation specifically]
5. **No direct comparison to a non-adopting control population; no defect-rate, PR-merge-time, or contributor-count metrics reported** — the RQ3 analysis is churn-only. (The paper's RQ1/RQ2 sections, not extracted in depth here as out of scope for this contradiction, cover the qualitative taxonomy of 32 tasks/10 content types/11 purposes and a 13-policy governance analysis — potentially relevant to RQ1/RQ3 of the wider research protocol, flagged in Follow-up leads.)

**Authors' own limitations (Section 8, quoted/paraphrased faithfully):**
- **Construct validity:** self-admission "represents a lower bound on actual GenAI adoption" (silent adopters invisible); mentions are ambiguous about scope (a "generated by ChatGPT" comment could mean a whole class or a single line); self-admission is itself a *behaviour* that may correlate with task type (developers more likely to admit GenAI use for "mundane" tasks like translation than for core business logic), which could bias which usages are even observable.
- **Internal validity:** heuristic mention-detection may produce false negatives for non-standard phrasing (mitigated by manual validation, described as high-precision/low-recall); low number of policy documents (13) and survey responses (8) for the RQ2 governance analysis (not the churn RQ).
- **External validity:** GitHub-only, five popular languages only, predominantly English-language artifacts; restricted to ChatGPT/Copilot mentions specifically — **explicitly excludes Claude Code and other more-recent agentic tools** (the authors' own words, quoted above) — this is the era-boundary limitation flagged in the Tier/era section.
- **On the adoption-date proxy specifically:** "we used the first explicit mention of GenAI tools as a proxy for adoption timing, which may not accurately reflect when projects actually began using GenAI. However, our generous analysis window of 360 days... and robustness checks (e.g., placebo tests) help accommodate potential discrepancies."

## What this can and cannot support

**Can support:** a peer-reviewed, quasi-experimental (RDD-based, with robustness/placebo checks), independent-academic rejection of the specific claim "GenAI adoption generally increases code churn" — at the level of 151 GitHub OSS repositories with *self-admitted* ChatGPT/Copilot usage, using GitClear's own churn definition. Can also support a genuine, non-null, task-differentiated finding: GenAI-*generation* tasks specifically show more churn/rework association than GenAI use for optimisation or maintenance tasks — a plausible, mechanistically sensible finding (freshly generated code needing correction) that should be read as a real positive result, not folded into the "null" headline.

**Cannot support:** any claim about agentic-tool (E3) churn effects — the study's adoption signal is restricted to ChatGPT/Copilot mentions and the authors say so explicitly; any claim about "silent" (non-self-admitting) GenAI adoption, which by construction is invisible to this method and could behave differently; generalisation beyond GitHub OSS repos with ≥2 contributors and an active release history (i.e., not GitClear's population of paying enterprise customers + megaprojects); a strict causal "GenAI adoption reduces churn" claim either — the pooled average decrease (finding 1) sits alongside a large share of repos (about 80% in the RDD) showing no significant discontinuity at all, so "mostly null with a real subgroup of decreases and a smaller subgroup of increases concentrated in generation tasks" is the accurate summary, not a clean "churn falls."

## Cross-reference: adjudicating the churn contradiction (report only — `synthesis/contradictions.md` NOT edited per instructions)

Recall Side A (gitclear-2025) was already weakened at the last verification pass: GitClear's 2026-edition churn rise (+15%, 16.1%→18.6%) is concentrated almost entirely in a single 2024→2025 step that coincides with an undisclosed ~3.3–3.8× jump in the underlying per-signal sample size — a live, unaddressed dataset-composition confound that the GitClear authors do not discuss.

Having now read Side B in full, here is the adjudication:

1. **Churn definition is not the source of disagreement.** This paper deliberately adopted GitClear's own 14-day/2-week line-based churn definition (and added a file-based variant on top). Both sides are measuring the same construct on the same time window. This closes off "different metric" as a reconciliation candidate.
2. **Population differs substantially, and in a way that plausibly matters.** GitClear's population is dominated by paying enterprise customers (opted into "Industry Stats") plus a handful of named megaprojects (Google, Microsoft, Apple-scale OSS) — repos large enough and commercially significant enough to buy code-analytics tooling. This paper's population is 151 general OSS GitHub repos meeting engineering-project and self-admitted-GenAI-mention criteria — smaller, more typical OSS projects, self-selected on *disclosing* GenAI use in text. These are genuinely different populations; neither generalises to the other by default.
3. **Identification/attribution method differs fundamentally, and this is the more decisive difference.** GitClear has **no per-repository adoption date at all** — it reports a population-level, calendar-year, cross-sectional trend across a customer base whose composition itself changes yearor-year (per the compositional-jump finding). This paper runs a **repository-level, self-adoption-dated, quasi-experimental before/after design** with an actual (if within-unit) counterfactual and three robustness checks. A repo-level design that asks "did *this* repo's churn change around *its own* GenAI-adoption moment" is a more direct test of the causal claim ("GenAI adoption causes churn to rise") than a population aggregate that cannot separate organic behavioural change from customer-base composition drift. On design quality alone, Side B's test is the stronger instrument for the specific causal claim both sides are nominally arguing about.
4. **Era: both sides are compromised in the same direction, which is itself informative.** Side A cannot modality-segment its signal at all (autocomplete/chat/agentic all pooled). Side B explicitly restricts its adoption signal to ChatGPT/Copilot mentions and explicitly disclaims coverage of agentic tools (Claude Code named directly). **Neither side has tested the agentic-era (E3) version of this claim.** This means the contradiction, as currently evidenced, is really a contradiction about the *pre-agentic* (E1/E2) churn question — the E3 version of "does agentic-tool adoption raise churn" remains genuinely untested by either side, and that gap should be reported as such, not implicitly closed by whichever side wins the pre-agentic argument.
5. **The self-admission proxy's known biases cut in a specific direction worth flagging:** understated adoption and lagged adoption-dating in Side B would, if anything, bias toward attenuating a true effect toward null (diluting the "post" window with pre-adoption behaviour, or missing silent adopters entirely) — this is a limitation on the strength of Side B's null, not a reason to prefer Side A.

**Verdict: contested, not resolved — but the weight of evidence now leans toward Side B (no general churn increase).** One-sentence justification: Side B directly re-implements GitClear's own churn definition inside a peer-reviewed, quasi-experimental repository-level design with robustness/placebo checks and finds no general increase (net decrease pooled, ~80% of repos showing no significant RDD discontinuity, and a real but task-specific increase confined to GenAI-generation usage) — a more direct causal test than Side A's population-level trend, which itself carries an unaddressed compositional confound — but neither side has evidenced the agentic-era (E3) version of the claim, non-overlapping populations remain unreconciled, and the self-admission proxy's understatement/lag bias means Side B's null should not be read as a settled "AI adoption reduces churn" either. Recommend the human record this as: contradiction persists at the "insufficient/contested" tier for E3 specifically, while the E1/E2 pre-agentic version of the claim now tilts toward "no general increase" on the stronger-design side.
