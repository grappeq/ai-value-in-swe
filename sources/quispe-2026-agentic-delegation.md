## Tier and era grading

- **Tier: B** (structured observational / large-scale telemetry without randomisation). This is not an RCT — adoption is voluntary/self-selected — but it is a large-N (5,346 developers, 3.15M commits, 57M files), doubly-robust staggered-adoption design with extensive counterfactual construction (not-yet-treated controls), placebo tests, and mechanical-exposure robustness checks. Sits at the rigorous end of Tier B; would not qualify as Tier A because the authors themselves explicitly disclaim a causal reading (see §10.7 below).
- **Era: E3 (agentic).** Treatment is defined by first Claude Code (agentic, mode-D per the paper's own taxonomy) co-authored commit; the paper explicitly contrasts this against Generation-1 conversational/autocomplete tools (ChatGPT, Copilot-classic), which were "universally available throughout the pre-period" and therefore do not confound the estimated contrast.
- **One-line can/cannot support verdict:** CAN support a medium-confidence, era-appropriate (E3) claim that agentic coding tools are associated with a sharp, robust expansion in the number/novelty of programming languages an individual developer touches, surviving several mechanical-exposure robustness checks — but CANNOT support a causal claim (the authors say so themselves), CANNOT support any claim about task-type productivity, code quality, review cost, or production-codebase velocity (out of scope for this paper — it does not measure those things at all), and CANNOT be treated as an independent source given the GitHub co-authorship/funding.

## Theoretical model (new in v2 framing; extends v1's Bayesian-learning framing)

Three production modes for a developer-language pair: **Solo (S)**, **Conversational/Generation-1 (C)**, **Delegation/Generation-2 agentic (D)**. CARA-utility certainty-equivalent surpluses for each mode (Eqs. 1–3); each mode has an activation threshold; Generation-1 assistance does not lower the entry threshold for an *unfamiliar* language (Assumption 1: "for unfamiliar languages with skill s̲, γs̲ − r_C ≤ 0" — conversational AI needs an existing skill foothold to add value), but Generation-2 delegation can, creating an **"activation band"** of opportunities — "too weak for solo or conversational production but strong enough once the agent can execute part of the task" — that becomes viable only via delegation. Proposition 1 (mechanical): Generation-2 menu weakly dominates, N²≥N¹. Proposition 2: the activation-band probability is F(T^S) − F(T^D). Proposition 3: distinguishes the **flow** of newly-used languages (which should spike then revert, since a language can be "new" only once) from the **stock** of cumulative languages ever used (which should keep rising) — "the stock-flow pattern the event studies test." Proposition 4: expected expansion into unfamiliar languages = U_i · p_i(a_i) — increasing in headroom (unfamiliar-language stock) and general ability — motivating the specialist-heterogeneity test (Section 9).

## Data and method

- **Treatment universe:** 7,786,771 Claude-co-authored commits (Jan 2025–Jan 2026 window of Claude Code availability), 185,517 distinct authors, detected via the machine-readable `Co-Authored-By: Claude` trailer.
- **Sample construction:** treated = 5,000 early adopters (first Claude commit Q2–Q3 2025, ≥5 Claude-coauthored commits, stratified by adoption month and 3 commit-intensity tiers); control = 5,000 not-yet-treated developers (adopt Q4 2025–Q1 2026, same filters). Screened for bot accounts (name-pattern + behavioural: >400 commits/month with >90% concentrated in one repo) and for detectable pre-adoption use of competing agentic tools (Copilot, Codex, Cursor, Aider, Devin, Gemini/Jules, OpenHands) — 214 developers excluded (110 treated, 104 control) on this basis. Competing-agent use is rare in this population: the seven rival tools combined co-author 0.8% of sample commits vs. 21.7% for Claude; Copilot is the most common competitor (8% of developers show any use).
- **Outcome construction (this is the key v1→v2 methodology change — see below):** commit-level language assignment via GitHub's Linguist rules applied to each of 57.2 million changed files across 3,151,536 non-merge commits (133,096 developer-repository pairs, discovered from three sources — GitHub's contribution API, the raw Claude-commit stream, and GH Archive PushEvents, the last of which adds 45% more repo pairs than the other two combined).
- **Estimator:** Callaway & Sant'Anna (2021) doubly-robust group-time ATT estimator, staggered adoption, not-yet-treated comparison group, one month of built-in anticipation (because the commit-trailer date is a "slightly late measure of true first use"), 1,000-iteration multiplier bootstrap clustered by developer, `csdid`/d2cml-ai v0.4.2 implementation.
- **Panel:** 28 months (Jan 2024–Apr 2026), 149,688 developer-month observations, final estimation N = 5,346 (2,813 treated / 2,533 control).

## What changed between v1 (May 2026) and v2 (July 2026), per the paper's own text

1. **Title changed** — v1: "Coding Beyond Your Training: Claude Code and the Technological Frontier of Software Developers" → v2: "Agentic Delegation and the Language Frontier of Software Developers: A Model and Evidence from Claude Code on GitHub." (Verbatim footnote: "An earlier version circulated as 'Coding Beyond Your Training...'")
2. **Author added** — v1 sole author Alexander Quispe; v2 adds Kevin Xu (GitHub-affiliated), with the Microsoft–GitHub COI disclosure appearing for the first time in v2's front matter (not present in the v1 abstract as fetched).
3. **Outcome-construction methodology overhauled** — v2 states explicitly (§5.3): "Prior drafts of this literature (**and an earlier version of this paper**) have relied on repository-level proxies — assigning every commit the primary language of its repository — which mismeasures multi-language work inside repositories and understates language breadth." v2 rebuilds outcomes at the **commit level** (57M files, Linguist classification) instead of the v1 repository-level proxy.
4. **Effect sizes changed substantially as a result.** v1 abstract (as independently fetched): "positive and significant effects on monthly commits (+41), repositories contributed to (+1.5), distinct programming languages used (**+0.83**)." v2 headline language-count effect is **+2.5** (three times larger) — consistent with the stated mechanism (repository-level proxies understate language breadth) but this means the two versions' headline numbers are not directly comparable, and the magnitude jump is large enough to warrant caution about further revision.
5. **Sample redefinition** — v1 followed "5,838 software developers"; v2's analysis sample is 5,346 (estimation) / 5,825 (full panel) under revised eligibility/screening rules (competing-agent screen, activity screen) not necessarily identical to v1's.
6. **New outcomes added** — v2 adds newly-used languages (the flow measure, "the direct counterpart of the activation band") and language entropy as primary/secondary outcomes; v1's abstract mentions only commits, repositories, and language count plus a "cumulative-languages effect grows with time" claim attributed to a Bayesian-learning model. v2 reframes the theory around the "activation band" / three-mode delegation model (Section 4) rather than v1's Bayesian-learning-only framing (the Bayesian-learning material survives in v2 only as a secondary "persistence" mechanism in Appendix A.7).
7. **New robustness suite** — the mechanical-exposure checks (excluding the first-Claude language; excluding all Claude-coauthored commits; per-commit rate decomposition; placebo adoption dates 12 months early) and the specialist/generalist heterogeneity test (Section 9) read as new or substantially expanded relative to v1's abstract, which only claims robustness "across multiple activity filters" without specifying these designs.
8. No explicit numbered changelog or "differences from v1" appendix exists in the paper; the above is reconstructed from the two footnote/section mentions of "an earlier version" plus an independent comparison against the v1 abstract.

## Findings (one record per finding)

### F1 — Headline: monthly distinct-language count expands sharply at adoption
Number of distinct programming languages a developer works in per month rises by **2.528 (SE 0.063)** at adoption month (t=0), against a pre-adoption treated mean of **0.90**. Remains significant at t=1 (**1.227, SE 0.064**) and t=2 (**0.693, SE 0.067**). Simple (pooled post-adoption) ATT = **1.178 (SE 0.052)**. Measured (commit-level telemetry), not self-reported. Table 2.

### F2 — Temporal dynamics / decay pattern: language count
Event-study coefficients (event-time = months since adoption): t=0: 2.528*, t=1: 1.227*, t=2: 0.693*, "decaying toward zero by the second half of the first post-adoption year"; "point estimates at horizons beyond e=4 remain positive but are imprecise, as fewer cohorts contribute" (thinning risk set — Table 9 shows only 149 developers contribute by e=5, 37 by e=7). Pre-period coefficients at e≤−2 are "tightly estimated zeros." **This is a spike-then-decay pattern**, consistent across the paper's four headline outcomes except the cumulative-stock measure (F5), which instead keeps rising.

### F3 — Headline: newly-used languages spike then revert (the activation-band measure)
Languages never before observed in the developer's history: **+1.193 (SE 0.051)** at t=0 ("nearly four times the pre-adoption monthly flow of 0.31"), falling to **+0.126 (SE 0.034)** at t=1, and **statistically indistinguishable from zero at t=2 (−0.018, SE 0.038, not significant)**. Simple ATT = 0.294 (SE 0.030). Authors: "Because ΔN^new is a flow — a given language can be 'new' only once — the profile necessarily reverts." This is a **null result recorded with equal diligence** per protocol rule 3 — the effect essentially disappears within two months.

### F4 — Headline: language entropy (Shannon) rises then decays
+0.382 (SE 0.009) at t=0 (pre-adoption mean 0.15), +0.189 (SE 0.011) at t=1, +0.102 (SE 0.012) at t=2. Simple ATT = 0.172 (SE 0.010). Same spike-decay shape as F1/F2.

### F5 — Cumulative-language stock keeps growing (does not decay) — but flagged non-clean by the authors
+1.604 (SE 0.054) at t=0, **rising** to +1.892 (SE 0.063) at t=1 and +2.072 (SE 0.086) at t=2 — the only outcome that grows rather than decays with event time. Simple ATT = 1.930 (SE 0.068). **Critical caveat, stated by the authors themselves:** "Four of the five pre-period coefficients for this outcome are statistically significant, indicating that treated developers were already accumulating languages somewhat faster than not-yet-treated developers before adoption... we present its profile as descriptive evidence on stock dynamics rather than as a headline estimate. The monthly language count and the newly-used-language flow — both with clean pre-periods — carry the identification weight." This is a self-flagged parallel-trends violation on their own preferred outcome — a rare and creditable act of self-correction, but it means the "growth continues after adoption" headline claim in the abstract rests on the one outcome the authors say is NOT cleanly identified.

### F6 — Diagnostics (not "frontier outcomes" per authors): repositories and commits
Repositories: +1.494 (SE 0.058) at t=0 (pre-adoption mean 0.94), simple ATT 0.742 (SE 0.057). Monthly commits: +35.080 (SE 2.085) at t=0 (pre-adoption mean 10.68), simple ATT 18.677 (SE 2.269). Authors explicitly caution these are "diagnostics of engagement, not... frontier outcomes" and use them to interpret the mechanical-exposure concern, not as headline value claims.

### F7 — Robustness 1: excluding the first-Claude-introduced language
77% of first Claude-co-authored commits touch ≥1 programming language (1.78 languages on average) — a real mechanical-contamination risk the authors quantify explicitly. After purging all activity (at every horizon, not just t=0) in the language(s) the developer's first Claude commit introduced (7,529 developer-language pairs removed): language count still +1.580* (SE 0.055) at t=0, +0.898* at t=1, +0.545* at t=2 (down from 2.528/1.227/0.693 but still significant at all horizons). Newly-used-language spike falls from 1.193 to 0.807 — i.e. roughly **one-third of the t=0 first-use spike is mechanically the treatment-defining language itself; two-thirds is expansion beyond it.**

### F8 — Robustness 2: excluding ALL Claude-co-authored commits (unassisted-only outcomes)
Rebuilding every outcome using only commits WITHOUT the Claude co-author trailer ("unassisted portfolio"): language count still +1.663* (SE 0.061) at t=0, +0.685* at t=1, +0.285* at t=2 — roughly **two-thirds of the full effect survives even when every piece of AI-assisted output is deleted from outcome construction.** Newly-used languages: +0.724* at t=0 but only +0.054 (n.s.) at t=1 and **significantly negative** −0.077* at t=2. Cumulative languages (unassisted): +1.130*/+1.331*/+1.434* at t=0/1/2 — still growing. Authors: "the decomposition rules out the sharpest deflationary reading: the portfolio expansion is not an artifact of counting machine output."

### F9 — Robustness 3: activity-volume controls and per-commit rates
Conditioning the DR estimator on log pre-adoption commits and repositories leaves the language-count ATT unchanged to the second decimal (2.530 vs. 2.528 at t=0; 1.228 vs 1.227 at t=1). Per-commit rate outcomes (outcome ÷ month's commit count): languages-per-commit rises +0.0546* (SE 0.013) at t=0 only, then **+0.0045 (n.s.) at t=1 and −0.0092 (n.s.) at t=2**; new-languages-per-commit is +0.0482* at t=0 but turns **significantly negative** at t=1 (−0.0257*) and t=2 (−0.0240*). Authors' interpretation: the adoption-month spike includes genuine per-commit diversification, but "the persistent component of the expansion operates through the expanded volume of work spanning more languages... not through each commit individually becoming more polyglot."

### F10 — Robustness 4: stricter pre-period activity filters
Restricting to developers active in ≥50% of pre-treatment months (n=1,425) or ≥6 pre-treatment months (n=2,393): language-count ATT at t=0 attenuates modestly to 2.087* and 2.183* respectively (vs. 2.528* full sample) — still significant. Newly-used-language flow attenuates more (0.675*/0.757* vs 1.193*), which the authors attribute to denser observed histories leaving fewer languages that can register as "new" (a measurement mechanism, not a validity concern, in their reading).

### F11 — Robustness 5: timing-assumption sensitivity
Widening the anticipation window to 2 months: t=0 ATT 2.62 vs. 2.53 baseline (flat pre-period). Re-dating adoption to the earliest recoverable Claude commit in the full commit history (shifts 154 developers to earlier dates): t=0 ATT 2.77. Both close to baseline. Re-including the 214 developers excluded by the competing-agent screen: t=0 ATT 2.46 (SE 0.06) — "the screen sharpens the estimand but does not drive the estimates."

### F12 — Placebo test: fake adoption date 12 months early
Assigning every developer a fake adoption date 12 months before the real one and restricting to pre-real-adoption months only: effect at the fake adoption month = **0.003 (language count), −0.019 (newly-used languages), 0.005 (entropy)** — "not a single post-placebo coefficient is statistically significant for any of the three outcomes (zero of seven event times each)." This is a clean, well-executed placebo and among the stronger pieces of evidence in the paper.

### F13 — Heterogeneity: specialist/generalist headroom effect (mechanism test)
Double-sorting developers by pre-adoption ability (commit volume, median split) then breadth (language count, median split within ability half) into 4 cells (1,174–1,494 developers each). On newly-used languages at t=0: high-ability specialists **0.981*** vs. high-ability generalists **0.301*** (≈3x gap); low-ability specialists **2.388*** vs. low-ability generalists **1.015*** (≈2.4x gap) — specialists (narrow pre-adoption portfolios) expand into new languages 2–3x more than generalists at the *same* ability level, within-ability so not an artifact of activity volume. On the ability margin itself: the pattern runs opposite to the model's prediction (low-ability developers show larger effects than high-ability) — the authors read this as their ability proxy (raw commit volume) being confounded with "observed engagement" rather than as evidence against the model, and flag better ability proxies as a priority for future work. This is an honest **negative/null result on one of two model predictions**, recorded with the same diligence as the positive specialist result.

### F14 — Authors' own causal-vs-associational framing (verbatim)
Abstract: "Because adoption is voluntary and may coincide with project shocks, the estimates are event-time associations rather than definitive causal effects." Section 10.7 ("Honest framing"): "In the absence of an exogenous shock, the most defensible interpretation of the results is associational rather than causal... we interpret the estimates as event-time associations around first detectable Claude Code use — sharp, robust, and quantitatively consistent with the agentic-delegation mechanism — rather than as settled causal effects." The authors identify the specific confound explicitly: "a developer who decides to ship a Rust application may install Claude *because* the language is unfamiliar, making her first Claude commit mechanically contemporaneous with her first Rust commit" — and state plainly that "no outcome-side check resolves project-driven selection into adoption timing." They also note a **"reversed Ashenfelter dip"**: activity (commits, languages, repos) ramps up in the single pre-period month e=−1, which they read as consistent with the endogenous-timing/new-project story, not merely detection lag — though they also show this is largely absorbed by the anticipation window and doesn't reflect a broader pre-trend.

### F15 — Scope/task-type mapping (methodological note, not a numeric finding)
The paper's outcome (programming-language portfolio breadth of individual open-source contributors) does not map cleanly onto the PROTOCOL §2 task-type taxonomy (T1–T11) or onto RQ1's metrics (speed, throughput, quality, satisfaction). It measures a different construct — *which* languages/technologies a developer can produce in, not how fast/well a given task type is completed. It also explicitly excludes measuring code quality, defect rates, review cost, or production-system stability entirely. Relevance to RQ5 (translation question) is indirect at best: this is individual/open-source-level capability expansion, not enterprise brownfield production-codebase velocity, and the population is public GitHub contributors (unknown mix of hobbyist/professional), not an enterprise workforce.
