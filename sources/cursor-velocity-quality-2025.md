## Author/dataset overlap verdict — READ THIS BEFORE USING FOR TRIANGULATION

**This is the SAME Carnegie Mellon research group as both sibling papers already in this evidence base, not an independent third source.**

- **Hao He, Shyam Agarwal, Bogdan Vasilescu** are co-authors of all three papers: this one, `he-2026-2x-mandate` (He, Agarwal, Denisov-Blanch, Azaletskiy, Koyejo, Vasilescu — the enterprise "2× mandate" DiD study), and `agents-vs-ides-2026` (Agarwal, He, Vasilescu — the AIDev-based agent-vs-IDE study). Courtney Miller and Christian Kästner are new to this paper only.
- `he-2026-2x-mandate`'s own reference list cites this paper directly (ref [16]) as a companion/consistent result from the same author group — the authors themselves are aware of and rely on the overlap, they do not present it as an independent check.
- **Consequence for this evidence base:** convergence between this paper, `he-2026-2x-mandate`, and `agents-vs-ides-2026` on "velocity gains fade/reverse while quality debt persists" is **within-group consistency across three datasets and designs by the same lab, not cross-group triangulation.** Per PROTOCOL §3, this trio together does *not* satisfy "three independent sources" for any triangulated claim; treat all three as **one evidentiary voice** when assessing how many independent lines of evidence support the quality-debt/transient-velocity pattern. Independent corroboration for that pattern in this evidence base currently rests on GitClear (commercial, independent) and, more weakly, on METR's qualitative note about AI-generated code needing cleanup — both genuinely independent of the CMU group.
- **Dataset independence, however, is real and worth crediting separately from author independence:** this paper is an **entirely separate primary data collection** (own GitHub Code Search API discovery of `.cursorrules` files, own GHArchive pull, own local SonarQube run) — it does **not** use the AIDev dataset (Zhang et al., arXiv:2602.09185) that `agents-vs-ides-2026` is built on. So while the *authors* are not independent across the three papers, the *data* underlying this paper and `agents-vs-ides-2026` are genuinely different (own-collected Cursor-config-file sample vs. third-party AIDev PR-attribution sample), and different again from `he-2026-2x-mandate`'s single-enterprise internal telemetry. This is a meaningfully stronger evidentiary position than three papers all reanalysing the same shared dataset would be — record it as "same lab, three different datasets and designs, convergent finding" rather than either "fully independent" or "just a reanalysis."

## Tier, era, independence

- **Tier: A**, on the same PROTOCOL §3 basis as the two sibling CMU papers ("large-N telemetry with counterfactuals"): a staggered-adoption difference-in-differences using the Borusyak et al. (2024) imputation estimator, propensity-score-matched controls (AUC 0.83–0.91), placebo/pre-trend tests, and multiple robustness subsamples (high-adopter, config-refinement, activity-level, AI-tool-contamination). **Quasi-experimental, not randomised** — adoption is a self-selected decision by each repo's maintainers/committers, not researcher-assigned. Read as "strong Tier A observational," one notch below RCT-grade, consistent with how the other two CMU papers in this evidence base are graded.
- **Era: E3, with the standard boundary caveat.** The paper explicitly frames its object of study as "modern Cursor with agentic capabilities" and uses the first commit of a `.cursorrules` configuration file as the adoption-date proxy. **However**, `.cursorrules` files pre-date Cursor's agent mode — they were originally a context/prompt-customisation mechanism for Cursor's autocomplete and chat features going back to 2023, and the paper's detection method cannot distinguish "repo adopted `.cursorrules` for chat/autocomplete context" from "repo adopted `.cursorrules` specifically to configure agentic runs." This is the same E2/E3-boundary ambiguity already flagged for Cursor in `agents-vs-ides-2026`'s "AI-IDE" cohort and in `metr-2025-rct`'s Cursor entry — record this paper's Cursor treatment as **"predominantly E3 by the authors' framing and by the Jan 2024–Mar 2025 adoption window (post-agent-mode-launch), but with an unquantified E2-contamination risk inherent to the config-file detection method,"** not as a clean, verified E3 signal. The paper's own "Alternative AI Tool Contamination" robustness check (below) partially but not fully addresses this — it tests for *other* tools' presence, not for *which Cursor mode* was in use.
- **Independence:** Academic, CMU-only authorship (He, Miller, Agarwal, Kästner, Vasilescu) — no vendor affiliation identified, no Tier D flag. See the overlap verdict above for the critical caveat: not independent *of* the other two CMU papers in this evidence base, though the underlying dataset is independently collected (own GitHub/GHArchive/SonarQube pipeline, not AIDev). No funding/COI statement located in the fetched text.

## Method & population

- **Treatment signal — how Cursor adoption is detected per repo:** presence of a committed `.cursorrules` configuration file; **the date of the first commit touching this file is the adoption-date proxy.** Discovery used GitHub's code search API with an adaptive-partitioning algorithm, surfacing 23,308 candidate files across 3,306 repositories, filtered down to the final analysis sample.
- **Inclusion filters:** non-fork repositories; ≥10 GitHub stars (the authors cite ≈97% precision for this threshold as an "engineered project" filter per prior methodology); toy/educational/spam repos removed. Final treated sample: **806 repositories**, adopting `.cursorrules` between **January 2024 and March 2025**.
- **Control group:** **1,380 never-adopter repositories** — propensity-score matched **1:3** (three controls per treated unit), same-language restriction. Propensity model: logistic regression on repo age plus six months of dynamic pre-treatment history (active users, stars, forks, releases, PRs, issues, comments) plus cumulative baselines beyond month 6; reported **AUC 0.83–0.91** across adoption-month cohorts.
- **Identification strategy:** staggered-adoption difference-in-differences using the **Borusyak et al. (2024) imputation estimator** — counterfactual `Ŷ_it(0)` built from untreated observations only, with repo fixed effects, month fixed effects, and time-varying covariates. Pre-trend/placebo tests at horizons h = −6 to −2 months pre-adoption; the paper reports these pass heteroscedasticity- and cluster-robust Wald tests at p<0.05, supporting (not proving) the parallel-trends assumption.
- **Observation window:** January 2024 – August 2025 overall; every treated unit required to have **≥6 months of pre- and post-adoption observation**.
- **Sample composition (treated group, at baseline):** mean repo age 1,002.3 days (range 283–6,208); mean stars 1,475.3 (median 51.0 — a long right tail); mean contributors 19.2 (median 3.0); mean commits 1,816.6 (median 209.0). Primary languages: TypeScript 366, Python 118, JavaScript 60, Go 36, Rust 24 — i.e. overwhelmingly JS/TS/Python web- and tooling-style OSS projects.
- **Quality instrumentation:** the authors ran their **own local SonarQube Community Server v9.9.1** against each repo-month, extracting static-analysis warnings (reliability + maintainability + security issues, combined into one count), cognitive complexity, and duplicate-line density (language-specific thresholds: ≥10 consecutive statements or 100 duplicate tokens).
- **Dataset provenance (explicitly checked per the task brief):** **this is the authors' own primary data collection — GitHub Code Search API, GHArchive, and a self-run SonarQube pipeline.** It does **not** use the AIDev dataset (Zhang et al., arXiv:2602.09185) that `agents-vs-ides-2026` draws on. No shared-dataset dependency with that sibling paper; see the overlap section above for what this does and doesn't buy in terms of independence.

## Key findings (all measured/telemetry-based; no self-report data in this paper)

**1. Velocity — large, front-loaded, and transient; not a durable gain.**
- Overall (pooled) average treatment effect on the treated (ATT), log scale back-transformed to %:
  - Commits: **+2.63%** (SE ±4.40%; 95% CI [−6.1%, +11.2%]) — **not significant**.
  - Lines added: **+28.58%** (SE ±13.7%; 95% CI [+1.7%, +58.2%]; p<0.001).
- Month-by-month dynamic trajectory (ATT_h, h = months since adoption):
  - Placebo window (h = −6 to −2): not significant (supports parallel trends).
  - **Month +1: commits +55.4%, lines added +281.3%** — the peak.
  - **Month +2: commits +14.5%, lines added +48.4%** — sharp decay already under way.
  - **Months +3 to +6: effects return to approximately zero** on both metrics.
- The authors' own summary: **"the only significant development velocity gain is in the first two months post-Cursor-adoption."** This is a **decay to null**, not a reversal to negative — an important distinction from the IDE-First cohort in `agents-vs-ides-2026` (see cross-ref below), which decays *through* zero into significantly negative territory by month 6.

**2. Quality degradation — persistent, not transient, and does not track the velocity decay.**
- Static analysis warnings, overall ATT: **+30.26%** (SE ±6.66%; 95% CI [+17.3%, +44.4%]; p<0.001). Persists across months +1 to +6 **without significant attenuation** — i.e. does not fade as the velocity gain fades.
- Code (cognitive) complexity, overall ATT: **+41.64%** (SE ±7.62%; 95% CI [+26.9%, +58.6%]; p<0.001). Same persistence pattern.
- Duplicate line density, overall ATT: **+7.03%** (SE ±4.79%; 95% CI [−2.4%, +16.9%]) — **not significant; a genuine null result**, recorded here with the same diligence as the positive findings per CLAUDE.md rule 3.

**3. Dynamic panel GMM — a lead-lag mechanism claim, asymmetric in direction.**
The authors additionally fit an Arellano–Bond dynamic panel GMM to test lead-lag relationships between quality and velocity (contemporaneous variables instrumented with lags 2–3; Sargan and AR(2) tests both reported passing at p>0.05):
  - **Code complexity(t) → Lines added(t+1): −0.718*** (SE 0.098).**
  - **Static analysis warnings(t) → Lines added(t+1): −0.588*** (SE 0.092).**
  - Authors' own interpretation: "a 100% increase in code complexity and static analysis warnings causes a 64.5% and 50.3% decrease in development velocity" respectively — framed as **"accumulated technical debt subsequently reduces future velocity, creating a self-reinforcing cycle."**
  - **Reverse direction tested and found null:** "increases in development velocity do not produce a significant effect on static analysis warnings and code complexity" once other temporal dynamics are held constant in the GMM specification. This is a genuine negative result worth flagging precisely because it complicates a naive reading of the headline ATTs: the pooled/dynamic DiD estimates show velocity and quality-debt metrics *rising together* in the same post-adoption window, but the GMM's decomposition finds the causal arrow (in its specification) running from quality debt to *future* velocity, not from velocity to future quality debt. The paper does not fully reconcile this asymmetry with the simpler co-movement story in the headline ATT results — worth treating the GMM causal-language ("causes") with some caution, since it rests on instrument-validity assumptions (lags 2–3) that are asserted via passing Sargan/AR(2) tests rather than independently argued.

**4. Heterogeneity — robustness subsamples, but NOT the repo-age/size cut the triage note hoped for.**
- **High-contributor-adoption subset** (≥80% of commits from `.cursorrules`-touching contributors): quality-degradation effects (warnings, complexity) are **amplified**, not attenuated, relative to the full sample. Authors' reading: "accumulation of static analysis warnings and code complexity is stronger — not weaker — among repositories with continued configuration refinement."
- **Configuration-refinement subset** (≥1 post-adoption edit to `.cursorrules`): results robust and strengthened; authors read this as evidence the main ITT estimates likely *understate* the true per-use effect (consistent with the ITT-vs-TOT distinction discussed in Limitations).
- **Activity-level subsets** (≥1 commit/month or ≥10 commits/month): main findings persist among very active repos but are numerically weaker than the full-sample ITT (expected, given higher activity baselines).
- **AI-tool-contamination subset** (382 treatment repos also showing `.vscode` or other AI-tool indicators): "Cursor and Other" split shows attenuated-but-still-significant effects; "Only Cursor" split shows amplified effects; authors conclude "all of our main findings are persistent through all three settings."
- **No explicit repository-age or repository-size heterogeneity breakdown is reported anywhere in the fetched text.** Repo age is used only as a *matching covariate* in the propensity-score model, not as a moderator in a reported subgroup analysis. **This is a real gap relative to what the triage note expected this paper to speak to for §5 tension 2 (greenfield/brownfield) — record it as absent, not as a weak or null finding, since it was never actually estimated and reported.** This paper is weaker on tension 2 than `he-2026-2x-mandate`'s explicit pre-2022-vs-post-2022 repo cohort cut, which does report exactly this kind of moderator analysis.

**5. Nulls/negatives, collected in one place per CLAUDE.md rule 3:**
- Commits: overall ATT not significant.
- Duplicate line density: not significant, in both the pooled ATT and (implicitly) the monthly trajectory.
- GMM reverse-direction test (velocity → future warnings/complexity): not significant, holding other dynamics constant.
- Pre-trend/placebo tests: not significant deviations from zero in the −6 to −2 month window — this is a *supportive* null (backs the identification strategy), distinct in kind from the substantive nulls above.

## Limitations (authors' own, near-verbatim from the fetched text)

- **Observable-adoption selection bias:** "Developers can use Cursor without committing such files. Thus, our sample represents repositories with observable Cursor adoption rather than all possible Cursor-adopting repositories... To the extent committed adopters use Cursor more systematically, our estimates may represent an upper bound on average effects across all users."
- **ITT, not TOT, and usage intensity unknown:** "we do not know how intensively or persistently Cursor was used in each repository... our main estimates represent intent-to-treat (ITT) effects."
- **Model/version heterogeneity unmeasured:** "Our dataset lacks information on which Cursor version or LLM backend each repository used... across all model diversity" — i.e. no way to attribute effects to a specific Cursor release or underlying frontier model.
- **Imperfect matching / unobserved confounders:** despite AUC 0.83–0.91, "factors like developer expertise, team practices, project complexity, or organizational culture may affect both Cursor adoption and the post-adoption outcomes."
- **Cross-contamination of treatment and control:** "Repositories in both the treatment and control groups may be using alternative AI tools before and throughout the observation period, with or without visible traces... our estimates should be interpreted as the impact of systematic Cursor adoption compared to the current state-of-the-practice" — i.e. the control group is not an "AI-free" baseline, only a "no observable Cursor" baseline.
- **External validity:** "may not generalize to other LLM agent assistants, proprietary software projects, and programming languages beyond the three dominant ones in our dataset (JavaScript, TypeScript, Python)... Results observed may not persist as LLM agent assistants mature and developer workflows adapt."

## What this can and cannot support

**Can support (Tier A, E3-with-boundary-caveat, OSS-bounded):** that Cursor adoption in observable, engineered OSS repositories produces a large, front-loaded velocity spike (commits/LOC) concentrated in the first two months, which decays to statistically indistinguishable-from-zero by month 3 and stays there through month 6 — i.e. **the velocity gain measured this way is not durable at the repo level.** Can support that static-analysis-warning and complexity increases are large, persistent, and do **not** decay alongside the velocity effect — i.e. quality debt outlives the productivity bump that (arguably) produced it. Can support, at the more cautious "associational, GMM-derived" confidence level the paper itself signals, a lead-lag mechanism in which rising complexity/warnings *predict* reduced future velocity — a substantive contribution to §5 tension 4 with an explicit proposed causal direction, not just a correlation. Can support that these effects are robust to several contamination and intensity robustness checks. Duplicate-density shows no effect — a genuine null, useful as a boundary on how far "quality debt" claims should be pushed (churn/complexity/warnings rise; duplication specifically does not, in this sample).

**Cannot support:** any claim about individual developer productivity or task-level outcomes (unit of analysis is repo-month, not developer or task); any claim disaggregated by repository age or size (matched on, but not reported as a moderator — a real gap, not a null); any attribution to a specific Cursor version, model backend, or "agentic vs autocomplete" sub-mode (unmeasured, and the `.cursorrules`-based detection method cannot in principle distinguish these); any claim about proprietary/closed-source codebases, non-OSS teams, or languages outside JS/TS/Python/Go/Rust; any claim that this is independent triangulation of `he-2026-2x-mandate` or `agents-vs-ides-2026` — it is the same author group's third data point, not a fourth independent voice (see overlap verdict above); and, despite the GMM's causal framing, no fully clean causal identification of the quality→velocity feedback direction (instrument validity rests on the authors' own Sargan/AR(2) diagnostics, not on an independently argued exclusion restriction).

## Cross-reference assessment (for orchestrator — not written to contradictions.md)

**(a) vs. `agents-vs-ides-2026`'s IDE-First (IF) cohort reversal — same phenomenon, but not the same data, and not quite the same finding.**
Both papers find that AI-tool-adoption velocity gains in OSS repos are front-loaded and fade within roughly 6 months, while quality-debt metrics (complexity, static-analysis warnings) rise and persist regardless of what velocity does. But three things differ and should not be blurred together:
1. **Magnitude/direction of the fade.** This paper's overall Cursor effect decays to **null** (~0%) by month 3–6. `agents-vs-ides-2026`'s IF cohort decays through zero into **significantly negative** territory (−35% commits, −61% lines added) by month 6. "Decays to null" and "reverses to negative" are different findings, even though both support the same broad "gains are not durable" conclusion — the IF-cohort finding is the stronger, more alarming version.
2. **Treatment definition.** This paper's treatment is "adopted Cursor" (any adopter, vs never-adopters) detected via config file; `agents-vs-ides-2026`'s IF/AF split is about *prior AI-IDE exposure before agent adoption* — a moderator of a different treatment (multi-agent adoption: Claude Code, Copilot-agent, Cursor-agent, Devin, etc., detected via PR attribution), not "Cursor adoption" itself. The IF cohort's fading effect is specifically about repos that already had AI-IDE habits before adding an agent; this paper's decay is about first-time Cursor adopters generally, with no such prior-exposure conditioning.
3. **Data source.** Own-collected `.cursorrules`/GHArchive/SonarQube data here vs. the third-party AIDev dataset there — genuinely different pipelines, which is worth crediting (see overlap section) even though the authors overlap.
Net: **directionally convergent, mechanistically related, but not a replication of the same measurement** — read as two related-but-distinct findings from the same lab, both consistent with "AI-tool velocity gains in OSS repos are short-lived," rather than one finding confirmed twice.

**(b) vs. GitClear quality-debt tension (§5 tension 4) — this is the strongest genuinely independent triangulation point for this paper.**
GitClear is a fully independent commercial source (not CMU-affiliated, not sharing data or authors with this paper). GitClear's multi-year descriptive analyses report rising churn and duplication and declining refactoring in the AI era; this paper adds a **quasi-causal, matched-DiD, large-N academic estimate** of rising static-analysis warnings (+30%) and complexity (+42%) specifically attributable to Cursor adoption, plus a GMM mechanism claim that the debt suppresses future velocity. Recommend treating **GitClear + this paper** as a legitimate two-source (commercial + academic, independent) convergence on tension 4, distinct from the same-lab convergence in (a) above. This paper's duplicate-density null is a useful nuance GitClear's own duplication finding should be checked against — worth flagging in synthesis as a partial disagreement on which specific quality dimension rises (complexity and warnings, robustly; duplication, not in this sample) rather than a blanket "everything gets worse."

**(c) vs. the Stanford cleanliness-moderator finding (Denisov-Blanch quadrant, §5 tension 2) — this paper does not actually speak to it, despite superficial fit.**
The triage note flagged this paper as bearing on tension 2 via repo-age/size heterogeneity, but as noted in Key finding 4 above, **no such moderator analysis is reported** — repo age is a matching covariate only. This paper cannot be used to corroborate or contest the Stanford greenfield/brownfield-by-complexity-quadrant finding; that role is better filled by `he-2026-2x-mandate`'s explicit pre-/post-2022 repo cohort split (+44% newer vs +12% n.s. legacy), which is a genuine, reported heterogeneity cut. Recommend the synthesis memo not cite this paper for tension 2 at all, or cite it only to note the absence.

**(d) Internal tension worth flagging for synthesis, not contradictions.md (same-source, not cross-source):** the paper's own headline ATT results show velocity and quality-debt metrics rising *together* in the same post-adoption window (both peak/persist starting month 1), which reads naturally as simple co-movement or a shared common cause (adoption shock). The GMM analysis instead asserts a specific lagged causal direction (debt → future velocity, not velocity → future debt) and finds the reverse direction null. These two results are not strictly contradictory (the GMM is testing a finer-grained lagged relationship the ATT can't distinguish), but the paper does not fully walk through why "quality debt causes velocity's *own* prior rise to fade" is compatible with "velocity's rise does not cause quality debt to rise" — if velocity didn't cause the debt, what did? (The paper's implicit answer is presumably "Cursor's code-generation style itself," independent of volume, but this is not stated outright in the material fetched.) Flag as an interpretive gap in the source, worth a footnote in any RQ3/RQ5 synthesis memo that leans on the GMM mechanism claim.
