## Tier & era & independence

- **Tier: D (COI-flagged), not C.** Uplevel is an engineering-intelligence analytics vendor (the same product category as LinearB/Swarmia/DX Core 4) publishing an analysis of its own customer base as a marketing report. PROTOCOL §6 explicitly instructs grading this category **D, not C, when vendor-published** — this is exactly that case, so it is graded D even though it presents real (if thin) telemetry-style numbers, on the same logic as DX/LinearB/Swarmia in the protocol's own example list.
- **Era: E1 — confirmed.** The post-period is January–April 2024, describing plain GitHub Copilot "access" (inline-suggestion/autocomplete-era tooling); no agentic or multi-file tooling is in scope. Matches the seed tag exactly.
- **Independence flags:** Vendor-published, COI is direct and two-layered: (1) standard vendor-marketing incentive to publish an attention-getting contrarian finding ("41% more bugs" drove substantial press pickup for Uplevel); (2) a sharper, product-specific COI — the report's own recommendation ("monitor engineering effectiveness metrics… through A/B testing," "dig deeper to find the PRs with bugs") is a direct pitch for the kind of engineering-intelligence instrumentation Uplevel sells. Population is Uplevel's own customer base (self-selected enterprises already buying engineering-analytics tooling), not a random or representative sample — the same selection-bias pattern flagged for GitClear. No randomisation: this is an observational access-based split, not an RCT — despite some press coverage loosely calling it a "test and control group," there is no evidence of random assignment to Copilot access; access was presumably whatever each customer org had already rolled out.

## Method & population/dataset

- **Measurement basis: measured (telemetry)** for cycle time, PR throughput, and "Sustained Always On" (overtime/burnout proxy) — these are pulled from Uplevel's own engineering-analytics instrumentation of customer git/PR data, not survey self-report. Bug rate is also presented as measured telemetry, but **the operational definition of "bug" is never stated in any version of the report or any secondary coverage found** — no source specifies whether this means PRs carrying a "bug" label, linked bug-tracker issues, post-merge reverts, hotfix commits, or something else. This absence of an operational definition is itself the single biggest methodological gap identified.
- **Population:** "nearly 800 developers" across Uplevel's enterprise customer base. Secondary coverage (consistent across multiple independent aggregations, not independently confirmed from Uplevel's own text) reports a split of 351 developers with Copilot access vs 434 without.
- **Design: access-based pre/post + between-group comparison, not a randomised or matched-cohort design.** Two windows are compared: pre-Copilot (9 Jan–9 Apr 2023) and post-Copilot (8 Jan–7 Apr 2024) — per secondary coverage, not confirmed from the primary blog post, which does not state exact dates. The primary post states only that the "test group" (Copilot access) is compared against a "control group" (no access) with "similar roles, working days, and coding volume" — no detail on how similarity was established (matching method, covariates, statistical adjustment).
- **Central and most damaging methodological limitation (identified by jasonstcyr.com, corroborated by the CIO.com-style coverage): the study measured Copilot *access*, not Copilot *usage*.** Developers in the "test group" may have used Copilot rarely or not at all; there is no telemetry on actual invocation/acceptance rate distinguishing the groups. This confound alone is sufficient to undermine causal attribution of the bug-rate delta to Copilot itself.
- Uplevel's own product manager (Matt Hoffman, quoted in DevOps.com) offered a mechanistic explanation for the bug-rate finding — Copilot "trained using code of varying quality that OpenAI collected from across the Web" — which is speculation, not something the study measured.
- No control for confounders (concurrent project mix, team composition changes, code review process changes, layoffs) between the two one-year-apart three-month windows was described anywhere in the primary text or secondary coverage found.

## Key findings

All labelled **measured (telemetry)** per Uplevel's own framing; no self-reported/perceived companion metric was published alongside these (unlike METR-style perception-reality-gap studies), so there is no measured-vs-self-reported delta to record for this source specifically.

1. **Null result on velocity.** "No significant change in efficiency metrics" — Copilot access group showed a **1.7-minute decrease in PR cycle time** (secondary coverage; described elsewhere by Uplevel as "statistically significant" but "inconsequential in terms of actual engineering outcomes") and **no meaningful change in PR throughput** (number of PRs merged). [T4/T9-adjacent, general dev throughput; measured; era E1]
2. **Contested +41% bug-rate claim.** Developers with Copilot access saw a **41% increase in bugs within pull requests**, with issue throughput held roughly flat — framed by Uplevel as "Copilot may negatively impact code quality." No confidence interval, significance test, or bug definition is published. [T4 generic feature work / T8-adjacent (defect incidence); measured, but with the access-not-usage confound noted above; era E1]
3. **Burnout/overtime: Copilot group did worse, not better.** "Sustained Always On" (extended/out-of-hours working) fell **28% for the control (no-Copilot) group** vs only **17% for the Copilot-access group** — i.e., both groups improved on this burnout proxy over the year, but the non-Copilot group improved substantially more, so Copilot access is associated with a *smaller* reduction in burnout risk, not a bigger one. [cross-cutting; measured]
4. **Overall code volume increased** among Copilot-access developers (noted by DevOps.com coverage) — reported without further quantification and not connected by Uplevel to any quality-adjusted output measure.
5. **2026 retrospective add-on (not independent data):** the April 2026 follow-up post restates the above and layers on a seniority claim ("Copilot significantly raises task completion for more recent hires and junior positions but not for tenured/senior developers") sourced to outside literature (Cui et al.-style, not Uplevel's own telemetry) and an anecdote that ANZ Bank's internal testing reached a different seniority conclusion than GitHub's own published research — illustrative of context-dependence, not a new finding from Uplevel's dataset.

## What this can and cannot support

**Can support:** (a) a worked example of the access-vs-usage measurement confound for RQ2/RQ6 (a live illustration of why "rollout" ≠ "adoption" ≠ "impact"); (b) one contested E1-era datapoint for PROTOCOL §5 tension 4 (quality-debt signals) that can be cited *as contested* alongside GitClear, always with its methodological caveats attached; (c) a case study in vendor-report incentive structure (COI mechanism where the "finding" doubles as a pitch for the vendor's own instrumentation). **Cannot support:** any load-bearing effect-size claim in the exec brief — the "bug" construct is undefined, the design is observational access-based (not randomised, not usage-based, not matched), no confidence interval or significance reporting exists in any version read, and it is a single Tier D source with a direct product-relevant COI. Cannot be used as era-transferable evidence (E1, autocomplete-only) per the PROTOCOL §2 era-transfer rule — inadmissible for any E3 claim without an explicit "pre-agentic" label.

## Corrections vs the seed description (PROTOCOL §6)

- Seed: "Uplevel (2024) — null velocity + bug-rate claim [E1; methodology-critique value]." **Confirmed accurate in substance** — both the null-velocity and +41%-bug-rate claims are real and correctly summarised by the seed, and E1 tagging is correct.
- **Correction 1 — form of the primary artefact.** The seed implies a "report"; what actually exists and remains accessible is a marketing blog post (uplevelteam.com/blog/genai-developers) plus a lead-gen landing page gating a fuller PDF behind an email form. There is no evidence a rigorously documented, freely accessible methods paper ever existed. This matters for the tier decision: it reinforces D over C.
- **Correction 2 — tier.** The seed list does not itself assign a tier in §6 (tiers are assigned during extraction), but the natural instinct to grade this as Tier C ("practitioner signal, real numbers") would be wrong per the explicit §6 rule that vendor-published customer analytics reports (DX/LinearB/Swarmia/Faros-class) grade **D**. Recorded here as D.
- **Correction 3 — the access/usage confound is not mentioned in the seed** and is arguably the single most important methodological fact about this source; it should travel with the claim wherever cited.
- **Correction 4 — no operational "bug" definition exists in any source found,** primary or secondary. This is a gap worth flagging explicitly rather than silently assuming a reasonable definition.
- No 2025/2026 Uplevel re-run or expanded dataset was found; the 2026 blog post is a retrospective opinion piece re-citing the same 2024 numbers, not a successor study.
