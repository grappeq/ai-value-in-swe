## What this document is

An economics-style working paper using a regression discontinuity design on GitHub's free-Copilot programme for top open-source maintainers. It asks how access to an AI code-completion tool changes the allocation of a developer's activity on GitHub, not how fast or how well they work. The outcomes are event-count shares (coding versus project management), collaboration breadth, and exploration breadth.

## Full notes

**Tool modality (decisive for era).** Copilot based on GPT-3-series Codex, inline code completion. The authors state explicitly that Copilot "is not an AI chat tool like ChatGPT" and that later chat features were not available in the main study period (Copilot Chat was introduced after about one year). Study window July 2022 to July 2023 (table notes). Era E1 by modality.

**Design.**
- Running variable: the minimum (best) normalised rank of any repository on which the developer is a collaborator, taken from GitHub's undisclosed internal ranking of OSS repositories; cumulative minimum over time. Threshold normalised to zero; rank below zero means eligibility for complimentary Copilot for one year, renewed if the repository stays below the threshold. Ranking composition and cut-off are undisclosed, which the authors argue makes manipulation implausible; eligibility is not communicated to developers, who must check on the Copilot site (hence weak take-up).
- Population: active maintainers ("collaborators") of ranked repos; 50,032 top developers (2,422,916 developer-weeks) after excluding anyone with Copilot experience from the technical preview. Intro describes a wider panel of 187,489 developers. Main bandwidth +/-100 normalised rank units: 5,521 developers, 215,169 developer-weeks (Table A3); cross-section N=4,268 developers in Table 1. Mean normalised rank in the sample about -364 (right-skewed).
- Specification: linear in rank on each side with an eligibility dummy and interaction (Equations 1 and 2); robust standard errors (clustering by developer not stated). Controls added in the second column of each table: account age, achievements, followers, centrality.
- Treatment: ITT (eligibility). Observed use: 16% of the 50,032 ever used Copilot; mean 8.1 days; 3% weekly exposure. Copilot use measured from Copilot API transactions in the IDE plugin.
- Validity checks reported: McCrary-style density test (Table C1: coefficient 477.6, SE 417.2, no significant bunching); covariate smoothness (Figure C1); first stage robust to quadratic. Not found: placebo-threshold (fake cut-off) tests. The task brief asked for placebos; the paper offers a placebo-style check on residual activity (Table C5, comments/reactions/starring) whose values I did not extract, and covariate-smoothness checks.
- Robustness: bandwidth and polynomial sweeps (Figures C3, C4), kernels (C2), Calonico-Cattaneo-Farrell optimal bandwidth (C3), absolute measures (C4), winsorisation (C6), propensity-score matching (C7), differences-in-discontinuities and a student-access DiD (C8).

**Outcome operationalisation.** "Coding" = create repository, fork, pull request, push events. "Project management" = project-board creation, issue assigned/closed/labelled/merged/reopened/subscribed, issue-comment deletion, review-requested, reviewed pull request (Table A1). Both are cumulative shares of the developer's total platform activity; the residual (comments, stars etc.) is in the denominator only. Baseline shares: coding about 0.44, project management about 0.37-0.44 depending on sample.

**Main effect (Table 2, ITT, +/-100).** Coding share +0.054 (SE 0.002; +12.4% on baseline 0.434; N=269,546); with controls +0.041 (SE 0.002; +9.0%; N=248,032). Project-management share -0.100 (SE 0.002; -24.9% on baseline 0.402); with controls -0.089 (SE 0.002; -20.1%). Minus signs were lost in PDF extraction; directions follow the authors' text. Note that N here (269,546) differs from the 215,169 stated for the same bandwidth in Tables 1, A3 and C2; unexplained.

**Sensitivity of magnitude.** Kernels barely matter (coding +0.052 to +0.054; PM -0.100 to -0.110). Optimal-bandwidth estimates are smaller: MSE-optimal coding +0.043 (+9.4%), PM -0.100 (-28.2%); coverage-error-optimal (bandwidth about +/-35-38) coding +0.023 (+5.2%), PM -0.051 (-15.0%). Differences-in-discontinuities coding about +0.03, PM about -0.033 to -0.036. Direction is robust; the headline magnitude is not.

**Dynamics (Figure 4, text only).** Effects weaker in quarter 1, peak in quarter 3 (up to about 10% coding, 27% PM per the text), attenuating from quarter 4 to about 2.5% (coding) and 8% (PM). Authors link attenuation to eligibility re-evaluation after year one.

**Autonomy versus collaboration (Hypothesis 2).** Maximum distinct collaborators across activity types: -17.251 (SE 0.346; baseline 21.759; -79.3%; N=161,155); with controls -14.697 (SE 0.351; baseline 29.947; -49.1%). Event decomposition (graphical): pushes and repository creation up; forks and PR creation slightly down; issue closing and merging up; review requests, issue assignment, PR reviews and issue subscriptions down. The authors read this as substituting Copilot for human help. Mechanism is inferred, not observed.

**Exploration versus exploitation (Hypothesis 3, Table 3).** New repositories +0.484 log points (SE 0.010; +62.3%), with controls +0.367 (+44.3%); previously-touched repositories about -9.1% / -12.0% (SE 0.011). Language exposure +1.753 on baseline 9.245 (+19.0%; SE 0.075) and +1.152 on 5.127 (+22.5%) while the text quotes +21.8%. Salary-weighted language exposure +1.4% (about USD 1,683 on USD 119,371). The authors' extrapolation to about 300,000 eligible maintainers (about USD 468 million per year net of a USD 120 licence) is explicitly back-of-envelope.

**Ability heterogeneity (Hypotheses 4a/4b, Table 4, Figure 6).** Median splits on four proxies: centrality (maximum share of a repo's commits), GitHub achievement badges, followers, account tenure. The rank itself is explicitly excluded as an ability measure. Coding effect low versus high ability: centrality +0.061 vs +0.021 (+14.2% vs +4.7%); achievements +0.082 vs +0.046 (+19.2% vs +10.6%); followers +0.098 vs +0.043 (+23.3% vs +9.8%); tenure +0.112 vs +0.025 (+26.6% vs +5.7%). PM: centrality -0.142 vs -0.054; achievements -0.149 vs -0.084; followers -0.154 vs -0.061; tenure -0.160 vs -0.067 (relative -33% to -37% vs -15% to -23%). SEs 0.002-0.003. No test of the low-high difference is reported in the text read. The "ability" proxies measure platform prominence and tenure, which is closer to experience/visibility than to skill.

**Firm affiliation (Table A6).** Effects similar for firm-affiliated (company email) and other developers: coding +0.068 vs +0.059; PM -0.095 vs -0.118. Authors cite this for external validity; the firm-affiliated subsample is only 28,721 of about 269,000 developer-weeks and remains public OSS activity.

**Output and quality.** The paper does not measure productivity, speed, throughput or code quality of the developers' work. Table A7 (added in the April 2025 version) reports ITT effects on proxies: PR acceptance rate +0.036 (SE 0.002; +4.7%), +0.014 with controls (+1.9%); repository-level critical CVEs -1.060 (SE 0.305; -13.6%) and -1.405 with controls (SE 0.363; text: 33.9% lower); continuous integration adoption +10.5% / +5.4%; dependency scanning +5.0% / +1.0%. Authors' reading: "no evidence that Copilot had a negative impact on developer efficacy or project cybersecurity". These are proxies and should not be read as AI-code quality.

**Authors' stated limitations.** (a) Exact code and the way Copilot was used are not observed. (b) Only public repositories are observed; 45.5% of Copilot usage occurs in weeks with no public activity, so private-repo behaviour is unseen; they suggest estimates may be understated by up to a factor of two if private behaviour responds similarly (an untested assumption). (c) Take-up is low because eligibility is not announced. Not acknowledged by the authors: the ITT first stage is small (about 6 percentage points more ever-users; about 1.8 points of exposure share) relative to the 5.4 point coding-share shift, so either the effect per user is very large or something else changes at the threshold (see red flags).

## Tier & era grading

- **Tier:** A-candidate (quasi-experimental regression discontinuity with density and covariate checks, N in the thousands of developers and hundreds of thousands of developer-weeks), downgraded in practice by: working-paper status, vendor-affiliated authors and proprietary data (Tier D COI flag applies), no placebo-threshold test located, and outcomes that are event-count proxies. Graded "A with COI flag, claims limited to task allocation".
- **Era:** E1 (autocomplete). Pre-agentic label required on any claim derived from this source. By modality (GPT-3-era inline completion, no chat, no agent), irrespective of the 2024/2025 publication dates.
- **Independence:** low. GitHub co-author, GitHub data and funding.

## Measured vs self-reported

All outcomes are measured platform telemetry. No self-reported measures, so no perceived-versus-measured delta. The treatment (Copilot use) is measured from API transactions; the construct "work allocation" is a proxy built from event types, not time spent.

## Can / cannot support - verdicts

- **Can support (E1, pre-agentic label):** the claim that free access to autocomplete shifted OSS maintainers' public activity towards pushes and away from issue and review handling; a methodology exemplar for threshold-based natural experiments using vendor eligibility rules; an era-independent hypothesis that AI substitutes for asking colleagues (bottleneck displacement from collaboration to solo work); mild directional support for larger relative shifts among less prominent or newer developers (seniority asymmetry, with proxy caveats).
- **Cannot support:** any productivity, speed or output claim; any claim about code quality of AI-generated code; anything about chat or agentic tools; generalisation from top OSS maintainers on public repos to enterprise teams on private mature codebases; the "flattened hierarchies" claim (authors say they "have not shown it directly"); causal interpretation of the mechanism rows as established (inferred from event types).
- **Task-taxonomy note:** "project management" (issue triage, assignment, review requests, boards) does not fit T1-T11 cleanly (partly T7 for PR review). Propose for the orchestrator: no taxonomy change on one source, but track "coordination / maintainer overhead" as a candidate cross-cutting tag.

## Red flags / things the orchestrator should know

1. **E1 despite recency.** Published late 2024, revised April 2025, but the tool is 2022-23 inline completion. Label pre-agentic; do not let it carry exec-brief effect sizes.
2. **Magnitude plausibility.** First-stage ITT is small (ever-use +6.1 points on 10.0%; exposure share +1.8 points) yet the coding share moves +5.4 points and project-management share -10 points. Scaled to compliers this implies very large per-user effects. Possible bundling or exclusion-restriction issues (other benefits or visibility for top-ranked repos at the threshold) cannot be ruled out from the paper; no placebo-threshold test located. This is my inference, not an author statement.
3. **Magnitude is specification-dependent.** The coverage-error-optimal bandwidth roughly halves both headline effects (coding +0.023, PM -0.051), and differences-in-discontinuities also gives about +0.03/-0.035. Cite direction with confidence, size with a range.
4. **Internal inconsistencies:** abstract and text say a two-year period, but every table note says July 2022 to July 2023; Table 2 N (269,546) differs from 215,169 in other tables for the same bandwidth; language-exposure effect quoted as 21.8% in text versus 19.0%/22.5% in Table 3; the text also says "15 additional new repositories" while the table reports a log-scale effect.
5. **Outcome is composition, not output.** Shares of event counts; a rise in pushes is not a rise in delivered value. Quality "proxies" (PR acceptance, CVE counts, CI adoption) are weak and some shrink to near zero with controls.
6. **Ability = prominence/tenure proxies, no significance test of difference.** Low-prominence developers also have a higher baseline project-management share, so relative effects are partly arithmetic.
7. **COI and data access.** Microsoft and GitHub co-authors, GitHub data and funding; findings are favourable to Copilot (positive security proxies, "net potential" valuation). Treat as Tier D-adjacent for exec-brief purposes.
8. **Population.** The most popular OSS projects' maintainers, mostly volunteers, public repositories only: far from our setting.
9. **PDF extraction caveat.** Minus signs were dropped from tables in the text layer; signs here follow the authors' text. Significance stars were not recoverable (SEs are tiny relative to coefficients in the main tables).
10. **Escalation check:** no Tier A/B paywall block (full text obtained via an HBS-derived copy); no source-level contradiction identified within this document. Cross-referencing against other rows is the orchestrator's job (blind extraction).
