## What this document is
A mining study plus a controlled longitudinal benchmark. RQ0 mines five open-source agent harnesses (Codex, Gemini CLI, OpenCode, OpenHands CLI, Qwen Code) against VS Code and GitHub CLI baselines (Mar 2025-Feb 2026). RQ1-RQ3 evaluate 35 sequential Qwen Code CLI releases (v0.0.10-v0.10.3; v0.0.11 excluded for a tool-availability bug) with the model held constant (self-hosted Qwen3-Next-80B-A3B-Instruct on vLLM 0.18.0, default CLI sampling), 50 stratified SWE-bench Verified tasks (20 easy, 25 medium, 5 hard), 2 runs per task, 600 s timeout, 3,500 executions. RQ2/RQ3 correlate 22 release-level factors and 10 architectural components with quality shifts.

## Full notes
**RQ0 ecosystem (measured, GitHub mining).**
- Releases per week / total / median interval: OpenCode 18.0 / 716 / 0.12 d; Codex 12.4 / 518 / 0.19 d; Gemini CLI 10.3 / 330 / 0.20 d; Qwen Code 10.0 / 288 / 0.59 d; OpenHands CLI 1.5 / 19 / 5.06 d. Baselines: VS Code 0.8/wk (40 releases), GitHub CLI 0.6/wk (33). Patch-to-minor ratio: OpenCode 39.1, Qwen Code 17.0, Gemini 4.9, OpenHands 1.3.
- Arithmetic check: "more than two releases per day" (abstract) holds on mean only for OpenCode (about 2.6/day); Codex about 1.8, Gemini about 1.5, Qwen about 1.4, OpenHands about 0.2. "13-28x" compares the fastest harnesses with baselines.
- Activity: 13.0-34.2 commits/day (four mature harnesses; OpenHands 2.8), 7.4-14.3 commits per release (VS Code 421.4), median PR review under 4 hours (0.13-0.17 d; Qwen 0.77 d).
- Issues: Gemini 9,951 (44.4/day, closed 81.8%); OpenCode 8,621 (31.0/day, 54.0%, 3,965 open; 3,103 opened in Jan 2026); Codex 5,574 (19.0/day, 77.8%); Qwen Code 1,029 (56.9%); OpenHands 200 (69.0%). VS Code 40,074 (109.8/day, 89.3%); GitHub CLI 1,118 (82.1%). Bug-fix commits are about 30% of effort.
- Attribution to the model: not measured. The claim that users blame the model rests on six anecdotal links (Cursor forum, Claude Code, Gemini CLI, Codex, Qwen Code issues). No issue categorisation by "model vs harness" is reported.

**RQ1 quality across 35 releases (measured, fixed model).**
- Run-to-run: Wilcoxon p=0.478 (resolve), 0.432 (tokens), 0.466 (tool calls); 87.7% of task executions agree across both runs.
- Resolve rate: mean 30.5%; range 23.0%-39.0% (peak v0.0.14); Spearman with release order rho=0.208, p=0.231. Early volatility up to about v0.3.0, narrower plateau after; "isolated regressions" around v0.5.0. Patch produced in 52-94% of tasks but only 23-39% resolved.
- Release-to-release swings reported in text: v0.4.1 to v0.5.0 39.4% to 32.5% (-6.9pp, "lowest since v0.3.0"); v0.5.0 to v0.5.1 27% to 34% (+7pp, "largest single-release improvement"); v0.2.3 to v0.3.0 26.0% to 33.0%. Maximum drop, maximum gain and the count of regressed releases are not tabulated; tiers (Good/Neutral/Bad at z=+/-0.75 sigma) appear only in Figure 10.
- Efficiency: tokens rho=0.743 (p<0.0001), first nine releases about 391K per task vs latest about 668K (+70%); trough 217K at v0.1.4; task-normalised range -24.2% to +19.6%; tool calls 6.9-14.3; turns +18%; step-1 prompt payload +8%; tokens vs turns rho=0.941. Resolved tasks 7.2 tool calls / 258.7K tokens; unresolved 12.95 / 697.7K.
- Case studies: v0.1.4 to v0.1.5 tokens 216.6K to 329.9K (+52%), tool calls 7.28 to 10.59, resolve rate flat at 26.0%, driven by PR #969 (search tool rewrite, +834/-776) and PR #981 (tool output formatting, +795/-607). v0.2.3 to v0.3.0 tokens 259K to 599.6K (+131%), resolve 26% to 33%, PRs #926 (+14,550 lines), #1058 (i18n, +4,740), #1076 (-671). Section 8.2 instead quotes +139% (v0.1.5) and +182% (v0.3.0): unreconciled.

**RQ2 development patterns (correlational, BH-corrected, n=35; delta n=34).**
- Resolve rate: bug_to_feature_ratio rho=0.546 (p=0.0006), bug_count 0.463, feat_churn_ratio 0.438 (p=0.0075), feat_pr_ratio 0.351, feature_count 0.331; refactor_churn_ratio -0.372 (p=0.025).
- Feature-heavy releases also cost more (tokens rho=0.401, Cliff d=-0.573; tool calls rho=0.360, d=-0.900). total_commits and unique_authors: large effects on token cost (d=-0.601, -0.482).
- Delta: larger mean PR size lowers tokens (rho=-0.441) and tool calls (-0.484); more deletions lower tokens (rho=-0.351; v0.4.1 to v0.5.0 removed 817 lines, tokens 517K to 450K); higher fix_churn_ratio raises tokens (rho=0.339, d=-0.833, "largest delta effect"). Counter-example: v0.1.1 to v0.1.2 compression fix cut tokens 26% (231K to 170K). Release cadence and PR size show no absolute association.

**RQ3 architectural components (correlational).**
- Absolute: LLM Provider additions vs token efficiency rho=+0.490; Extensibility +0.375; Context Management expansion -0.346 (partial -0.392); UI additive changes raise tokens (+0.369).
- Delta: large LLM Provider changes vs effectiveness rho=-0.336 (partial -0.221); Security fixes improve token efficiency (+0.346) and tool calls (+0.341); Persistence additive +0.353. Provider-layer example: PR #1235 (OpenAI converter, +346/-8) and PR #1245 coincide with 39.4% to 32.5% resolve rate; "invisible to tool-level integration tests". Causal attribution is inference, not ablation.

**Detectability (RQ-specific).** Authors inspected public CI and tests (more than 300 unit/integration/e2e tests): none evaluates resolve rate or enforces token or tool-call budgets; every documented regression passed all checks. They do not claim this is the sole cause, and attribute the gap to the cost of agentic evals at commit cadence. They did not test whether an eval gate would have caught the regressions.

**Authors' recommendations.** Treat harnesses as quality-critical software; add non-functional agentic regression testing (resolve rate, tokens, tool calls across versions); stage changes to Provider and Context layers incrementally; consolidate changes into coherent PRs and remove dead code; researchers should report and control harness version alongside model and report efficiency metrics.

**Limitations (authors').** One harness in depth; one open-weight model (may interact differently with prompt bloat); 50-task subset; binary resolve metric; n=35 limits power; manual component mapping; GitHub mining misses private work. Not stated by authors but evident: lab benchmark only, no production or user outcomes, no human baseline, no per-release confidence intervals (one task is 1pp per run, so a 7pp swing is about 3-4 tasks).

## Measured vs self-reported
Everything is measured (repository mining, benchmark runs, logs). The only self-reported element is practitioner complaints, cited as six anecdotal links and not analysed. Causal explanations ("plausible explanation") are author inference layered on correlations.

## Can / cannot support — verdicts
- CAN support: mechanism evidence that agent quality (resolve rate and cost) can shift between harness releases with the model unchanged (benchmark swings of up to about 7pp per step, range 23-39%; cost +52% and +131% in single steps), and that functional CI did not flag these in the one project inspected. Supports the argument that production "model drift" complaints may be harness changes, and that internal measurement should log the tool version.
- CANNOT support: the frequency or size of quality drift in production use, effects on developer productivity or code quality, effects for other harnesses or frontier models, any user-facing outcome, or a claim that users usually misattribute to the model (not measured). Tool-modality E3 only; no seniority or codebase-maturity evidence.
- Confidence for the mechanism claim: medium (clean control of the model, but one harness, one open model, 50 tasks, no per-release uncertainty).

## Red flags / things the orchestrator should know
1. Abstract's ">2 releases per day" applies to OpenCode only on mean rates.
2. Internal numeric inconsistencies: +52% vs +139% (v0.1.5) and +131% vs +182% (v0.3.0); peak resolve rate 39.0% (v0.0.14) vs 39.4% before v0.5.0; v0.5.0 given as 32.5% in RQ3 but implied 27% in RQ2 (27% to 34% at v0.5.1). Log as an unresolved internal conflict; the figures were not inspected.
3. Headline claim "practitioners blame the model" is anecdotal; no attribution rate. Do not cite a number for it.
4. Resolve-rate swings are on 50 tasks with no per-release intervals; treat single-release regressions as indicative. The non-significant trend (rho=0.208) is not evidence of "no improvement" with certainty at n=35.
5. Replication package not yet public; v1 not compared with v2.
6. Detectability finding rests on inspection of public CI only.
7. Qwen3-Next-80B-A3B is a small open model on a harness tuned for the Qwen family; results may not transfer to frontier models (possible tension with RQ-level claims about frontier agentic tools).
