## Tier, era, independence

- **Tier: B.** Large-N telemetry (tens of thousands of engineers; specific N not stated as a single headline figure in the passages read, described only as "tens of thousands") with no randomisation. The authors use two complementary quasi-experimental designs — a synthetic-control (CausalImpact) comparison against non-adopters with a genuine placebo-date test, and a within-person two-way-fixed-effects Poisson model — but adoption itself is observational/self-selected throughout, which is exactly the PROTOCOL §3 Tier B description ("large-scale telemetry without randomisation"), not the Tier A bar (no comparison-group-with-parallel-trends-style causal design of the kind he-2026-2x-mandate or heilman-2026-microsoft use; no counterfactual-with-fixed-effects-plus-independent-placebo-battery of that depth is evidenced in the passages read, though the single placebo-date test on the synthetic control is a genuine, if thinner, robustness check).
- **Era: E3, confirmed.** Tools studied are explicitly **command-line agentic tools** — Claude Code and GitHub Copilot CLI — with no autocomplete/IDE-inline-suggestion telemetry involved. This is a clean E3 case, in sharp contrast to heilman-2026-microsoft (same organisation, same broad research programme, but that paper's telemetry is IDE "suggestions/prompts/accepts" and explicitly excludes CLI tools). This paper is the CLI-agent complement Heilman et al. lacked.

## Method & population

- **Setting:** Microsoft software engineers, tens of thousands, across Microsoft's early-2026 CLI-agent rollout.
- **Windows:** pre-rollout baseline 1 October 2025 – 4 January 2026 (used to build predictors and a pre-period PR-count filter); post-rollout observation 5 January – 29 April 2026 (16 weeks).
- **Population filters:** engineers with ≥2 merged PRs in a four-week pre-rollout baseline ("active engineers"); pre-period PR counts trimmed at P5–P95.
- **Adoption-study sample isolation:** to isolate Copilot CLI adoption specifically, the adoption analysis (RQ1) excludes engineers with prior Claude Code access, so the adoption population faces a uniform choice at rollout.
- **Outcome metric throughout: merged pull requests, completed within a 28-day window of creation** — a single output proxy. The authors explicitly flag this as a narrow construct (see Limitations and the "what this can/cannot support" section).
- **Four research questions, four designs:**
  1. **RQ1 — who tries it (adoption):** logistic-style model of first-use as a function of peer exposure (reviewer peers' usage share, skip-level peers' usage share, direct manager's usage), prior IDE Copilot exposure (day-count buckets), baseline PR activity, career stage (IC2–IC6, M4–M6, reference IC4), and tenure (five bands, reference 5–15 years).
  2. **RQ2 — who sticks with it (retention):** retention defined as ≥5 of the first 14 days post-first-use showing tool use; modelled against the same predictor set.
  3. **RQ3/outcome — impact on output:** two designs run in parallel —
     - **Synthetic control / CausalImpact:** adopters vs. a synthetic counterfactual built from ten daily-mean regressors pooled from non-adopting PR creators; validated with a **placebo intervention date (2025-10-06, pre-rollout)** returning a null effect (−1.1%, 95% CI [−10.6%, +8.6%]) — a genuine falsification check, structurally similar in spirit to heilman-2026-microsoft's and he-2026-2x-mandate's placebo tests, though a single placebo rather than a battery.
     - **Within-person two-way fixed-effects Poisson regression:** `ln E[PRs_{i,w}] = α_i + τ_w + Σ_k β_k · 1[dose_{i,w}=k] `, engineer FE (α_i) and week FE (τ_w), standard errors clustered on engineer; also run with division-level fixed effects to absorb division-wide adoption momentum. This is the workhorse for the dose-response and the RQ5 heterogeneity analysis.
  4. **RQ4 — tool comparison:** single-tool-only adopters, Claude Code vs. Copilot CLI, compared on the same within-person design.
  5. **RQ5 — heterogeneity:** the same within-person dose-response model re-estimated within career-stage and tenure subgroups, each subgroup's lift measured relative to that subgroup's own zero-tool-use weeks, at a stated dose of three tool-use days per week. Benjamini–Hochberg false-discovery-rate correction applied within each moderator family (career, tenure) at α=0.05 on the interaction p-values.
- **Identification-strategy candour:** the paper does not claim exact causal point-identification; it stacks two complementary quasi-experimental designs (between-person synthetic-control-with-placebo, and within-person fixed-effects-with-dose-response) and treats their broad agreement as the strength of the causal claim, similarly to how heilman-2026-microsoft and he-2026-2x-mandate stack falsification tests rather than relying on a single design.

## Key findings (all measured, telemetry-based; the one survey mentioned is explicitly qualitative colour, not a quantitative claim)

1. **Headline output effect (synthetic control, abstract + Part 1 results): adopters merged ~24.0% more pull requests than the synthetic counterfactual [95% CI +14.5%, +33.7%], p<0.001.** Persistence checked by sub-period: February +29.4% [95% CI +17.7%, +44.4%]; March–April +20.0% [95% CI +7.4%, +35.9%] — overlapping intervals, read by the authors as a sustained (non-fading) effect across the four-month window.
   - **Placebo validity check:** a retrospective fabricated intervention date (6 October 2025, pre-rollout, no real tool launch) returned −1.1% [−10.6%, +8.6%] — a genuine null, supporting the synthetic-control design's validity.
2. **Dose-response (within-person FE model), by tool-use days/week, relative to zero-day weeks:** 1 day/week +15.0%; interpolated ~2 days/week ≈+28%; 3 days/week +39%; 4 days/week +44%; 5+ days/week +50.1%. Monotonic, well-separated across levels — the same "more use, more output, diminishing but still-rising returns" shape as heilman-2026-microsoft's dose-response (which tops out around +40.5%) and he-2026-2x-mandate's accumulated-use slope, though the three studies use different dose units and populations and should not be read as a single number.
3. **Tool comparison (RQ4, single-tool adopters only): Copilot CLI +24.9% PRs/week [95% CI +23.0%, +26.8%] vs. Claude Code +11.4% [95% CI +9.4%, +13.6%] — Copilot CLI's effect is roughly 2.2× Claude Code's, p<0.0001.** Authors offer two candidate (untested) explanations: differing task mixes between tool users, or better organisational/workflow alignment of Copilot CLI given Microsoft owns GitHub. **This is a head-to-head tool-comparison finding worth flagging for RQ1's value map** — it is the only source in this project's ledger so far with a direct within-company Claude-Code-vs-Copilot-CLI throughput comparison, and it favours the vendor's own tool inside the vendor's own telemetry, which is exactly the shape of result the COI flag exists to caveat.
4. **Adoption predictors (RQ1) — social exposure is the dominant signal, not seniority or tenure:**
   - Skip-level peers' usage (≥25% using): **+216% odds of trying** — the single strongest predictor found.
   - Direct manager's own use: **+82% odds**.
   - Reviewer peers' usage (≥25% using): **+54% odds**.
   - Prior IDE Copilot exposure: 1–14 pre-period days +49% odds; 60+ days +83% odds (openness to AI tooling generalises to trying the CLI agent).
   - Baseline PR activity: ≤1 PR/week +19% odds; 2+ PRs/week +34% odds.
   - **Career stage (reference IC4): IC2 −13% odds, IC3 −14% odds — both stated as significant in the text; IC5 "about +22%" higher odds. Managers (M4–M6): no significant difference from the IC4 reference stated in the text.** **IC6 is not given its own stated percentage in the running text** — the sentence structure ("IC5 and IC6 engineers had higher odds... about +22% for IC5") leaves it ambiguous in the prose whether +22% is IC5-only or a pooled IC5/IC6 figure; **recorded here as an open ambiguity in the source's own text, not resolved by estimation.** This +22%/−13%/−14% triplet is an **adoption-odds finding (who tries the tool), not an output-impact finding** — a distinction this extraction flags explicitly because the task brief's framing ("IC5/IC6 +22% vs IC2/IC3 −13/−14%") could otherwise be read as an impact-heterogeneity result; it is not.
   - Tenure (reference 5–15 years): <1 year +11% odds (weak signal); other bands near-zero/non-significant. Tenure "barely matters" for who tries the tool, in the authors' own framing.
5. **Retention predictors (RQ2) — behavioural, not demographic:** prior heavy IDE-Copilot use predicts **lower** retention (−12% to −15% odds, stated significant) — read by the authors as heavy IDE users having more fallback options and weaker CLI-specific commitment. Baseline activity (2+ PRs/week) predicts **higher** retention (+31% odds). **Career stage and tenure are weak-to-null predictors of retention** in the text — the authors' own framing is that "what an engineer does" (activity level, prior tool habits) predicts retention far more than "who they are" organisationally (level, tenure, and — by omission — no demographic breakdown by gender/location/etc. is reported as a predictor at all in the passages read).
6. **Heterogeneity in the OUTPUT effect by career stage and tenure (RQ5) — the paper's own seniority/tenure split on measured impact, and the primary target of this extraction:**
   - **Reference-group numbers (the only fully-quantified figures in this analysis):** IC4 (reference) lift at 3 tool-use days/week = **+21.3% [95% CI +19.6%, +23.0%]**; tenure 5–15-years (reference) lift at the same dose = **+21.5% [95% CI +19.9%, +23.1%]**.
   - **Qualitative pattern, stated directly in text: "more junior ICs and more senior managers experience a larger PR lift"** than the IC4 reference — i.e., a lift that is elevated at both the junior-IC end and the senior-manager end, relative to a dip around the IC4 mid-level.
   - **Tenure: explicitly named "C" shape, quoted verbatim: "we observe a 'C' shape, where low- and high-tenure engineers experienced larger lifts than mid-tenure engineers."**
   - **What is NOT available from the text: exact per-subgroup point estimates and CIs for IC2, IC3, IC5, IC6, M4, M5, M6 individually, or for the non-reference tenure bands, and no explicit statement of which specific subgroup contrasts survived the Benjamini–Hochberg FDR correction.** These exist only as marker positions on Figures 9 and 10 in the rendered paper. Three separate targeted extraction passes confirmed this is not an artefact of the fetch method — the authors present this analysis primarily graphically. **This is a material gap between what this paper is being cited for (a "powered seniority/tenure split with exact numbers") and what it actually reports in prose: the reference-group estimates are precise and CI-bounded; the shape of the rest of the curve is qualitatively described (junior-IC lift, senior-manager lift, C-shaped tenure) but not numerically quotable beyond those two reference points from the text alone.**
7. **Survey colour (RQ-adjacent, explicitly qualitative, self-report):** an internal post-hoc developer survey (609 responses, after an "Agentic Engineering Day") reported thematically coded responses: tools enabling broader team contribution (docs/tooling/prototypes by non-specialists), time savings reallocated to parallel work, **seniors describing an ability to decompose tasks/vet outputs/juggle parallel streams**, and **juniors expressing concern about not developing "code sense" if over-reliant on agents.** This is self-report theme-coding, not measured output, and is recorded here as directional colour consistent with (but not proof of) the practitioner "seniors extract more leverage, juniors risk skill loss" narrative already flagged in tension-5-seniority.md via prageng-2026-survey.
8. **Cost data (RQ4/RQ6):** no organisation-level cost figure of its own; the paper instead cites a **Fortune-reported anecdote** (one Meta employee averaging 281 billion tokens in 30 days; at Claude Opus 4.6's $5/million-token rate this implies ~$1.4M/month for that single user) to motivate why organisations need output evidence to justify CLI-agent token spend. **This is a third-party anecdote used for framing, not a measured cost figure from this study's own telemetry — do not cite as this paper's own cost data.**
9. **Quality/defect data:** none. The outcome throughout is merged-PR count; no revert, defect, incident, or code-quality measure is reported anywhere in the passages read.

## Authors' stated limitations (own framing, as extracted)

1. **Construct validity:** the 5-of-14-days retention threshold and 28-day merge window are acknowledged as somewhat arbitrary; the authors re-ran with 3-of-14 and 7-of-14 day thresholds and report stable results.
2. **Internal validity, adoption study:** cannot separate peer influence from homophily (engineers who resemble their heavy-adopting peers in other ways); cross-sectional design cannot rule out time-varying confounds (personal projects, vacations, etc.).
3. **Outcomes study:** merged-PR count "rewards small, frequent PRs" and misses quality/value costs — the authors explicitly state in their own abstract that "a merged PR is not the same as the value it delivers." Adopters self-select; the synthetic counterfactual may be biased (partially mitigated by the placebo-date test). Heavier-use weeks may carry a lighter task mix, so the dose-response should be read as association, not a fully causal claim. The single-tool-only restriction (RQ4) excludes multi-tool users from that specific comparison.
4. **External validity:** single company, single early-2026 window; generalises only to the extent other organisations resemble Microsoft's context. Azure DevOps telemetry only — undercounts activity in other ecosystems the same engineers might use. The 16-week window is stated as insufficient to detect long-horizon decline in the effect.
5. **Researcher positionality — explicit self-disclosure:** the authors state plainly that they are Microsoft employees, that Microsoft sells these tools (Copilot CLI directly, and profits from Claude Code indirectly via Azure/GitHub infrastructure), and that this "may have shaped design and interpretation despite no explicit pressure" — a direct, unprompted COI acknowledgement, in the same candid register as heilman-2026-microsoft and he-2026-2x-mandate.

## What this can and cannot support

**Can support (Tier B, E3 confirmed, strong self-disclosed COI, not independent of heilman-2026-microsoft):** that within Microsoft's early-2026 rollout, adoption of CLI-based coding agents (Claude Code, Copilot CLI) is associated with an approximately 24% increase in merged-PR throughput relative to a synthetic non-adopter counterfactual, sustained across a four-month window and corroborated by an independent within-person dose-response design showing a monotonic, diminishing-but-still-rising relationship between weekly tool-use days and PR output; that adoption spreads predominantly through visible social/peer exposure (skip-level and reviewer-peer usage far outweighing career-stage or tenure in predicting who tries the tool); that retention is driven by behavioural/activity factors rather than demographic or organisational-level factors; and that Copilot CLI showed roughly double the within-person throughput lift of Claude Code in this population (with two untested candidate explanations offered by the authors, one being Microsoft's own platform-alignment advantage — a result that should be read through the vendor-on-vendor COI lens).

**Can support at a lower, qualitative confidence level:** a "C-shaped" pattern in the OUTPUT-impact heterogeneity by tenure (low- and high-tenure engineers gaining more than mid-tenure) and an analogous statement that "more junior ICs and more senior managers" gain more than an IC4 reference — but only as directional, verbally-stated patterns. The paper does not provide exact, source-quotable point estimates or CIs for any non-reference career-stage or tenure subgroup in its prose, and does not state in text which specific subgroup contrasts survived its own Benjamini–Hochberg correction.

**Cannot support:** any claim that the frequently-cited "IC5/IC6 +22% vs IC2/IC3 −13%/−14%" triplet describes the OUTPUT-impact heterogeneity — those specific numbers are the ADOPTION-odds (who tries the tool) findings from RQ1, not the RQ5 output-impact split, and conflating the two would misstate this source; any exact numeric claim about IC2, IC3, IC5, IC6, M4, M5, or M6-specific output lift, or about any individual non-reference tenure band's lift, beyond the qualitative "C-shape"/"junior and senior managers gain more" description quoted above; any claim about code quality, defects, incidents, or technical debt (none measured); any claim about cost or ROI from this study's own telemetry (the only cost figure is a third-party press anecdote used for framing, not measured data); and no claim independent of the Microsoft-on-Microsoft COI or independent of heilman-2026-microsoft (shared author Murphy-Hill — this is the same research programme's second Microsoft-internal telemetry paper, not a cross-organisation replication).

## Cross-ref guidance (for orchestrator — not written to contradictions.md)

**(a) vs. heilman-2026-microsoft:** Same organisation (Microsoft), overlapping research programme, **shared author (Murphy-Hill)** — not independent. Complementary rather than contradictory in scope: Heilman et al. studies IDE Copilot "suggestions/prompts/accepts" telemetry (E1/E2, explicitly excludes CLI tools) with no seniority breakdown at all (IC-only population, no heterogeneity tested); this paper studies CLI agents specifically (E3, confirmed) and is the first paper in this project's ledger to test seniority/tenure heterogeneity on a *measured output* effect at Microsoft. The two papers' headline magnitudes are in a broadly similar range (Heilman's +40.5% at max IDE-usage tercile vs. this paper's +24.0% synthetic-control estimate or +50.1% at 5+ CLI-days/week) but different tools, different eras, different designs — treat as broadly consistent in shape (monotonic dose-response, diminishing returns), not a strict comparison.

**(b) vs. he-2026-2x-mandate (the tension-5 comparison this task exists to make):** This is a genuine second E3-era measured-output seniority/tenure split, but it **does not converge with He et al.'s flat-IC-to-Principal gradient.** He et al. found IC, Senior, Staff, and Principal statistically indistinguishable (a flat line across the IC-track ladder) with Management as a single outlier (+86%, "re-entry effect"). This Microsoft paper instead finds a **C-shaped** pattern *within* the IC track itself (junior ICs elevated, mid-level IC4 as a local minimum, senior managers also elevated) — a materially different shape, not simply a different magnitude. Neither paper is independent of a single self-selected/single-firm context (He et al.: one unnamed favourable-site firm; this paper: Microsoft, studied by Microsoft employees with an explicit, self-disclosed COI). The two papers also use different subgroup taxonomies (He et al.: IC/Senior/Staff/Principal/Management ladder at one firm; this paper: IC2–IC6/M4–M6 Microsoft-specific leveling) that are not a clean like-for-like mapping, which limits how precisely "C-shaped vs flat" can be compared. **Recommend treating this as: two single-firm E3 datapoints now exist, and they disagree on the shape of the seniority effect, not just its magnitude** — this is a materially different situation from "one datapoint, thin evidence" and should be reflected in the verdict wording (see recommendation below).

**(c) vs. prageng-2026-survey (the practitioner "seniors extract more leverage" self-report signal already in tension-5-seniority.md):** This paper's qualitative survey colour (seniors describing task-decomposition/output-vetting leverage; juniors worrying about code-sense atrophy) is directionally consistent with prageng-2026-survey's adoption/sentiment pattern, but — like prageng — is self-report/thematic, not the paper's own measured-output finding. The paper's *measured* output finding (the C-shape) is a more complicated story than a simple "seniors gain most" narrative: it shows junior ICs gaining too, with the dip concentrated at *mid*-career, which the pure "seniors extract more leverage" story does not predict on its own.

## Recommended revision to tension 5's verdict wording (reported to orchestrator; tension-verdicts file NOT edited per task instructions)

This source does not resolve tension 5 to "confirmed" or "resolved" — if anything it complicates it further, which itself is worth stating explicitly rather than treated as a strengthening of either existing camp. Concretely:

1. There are now **two** E3-era sources with a measured-output seniority/tenure split, not one, but **both are single-firm, both carry unresolved COI (He et al.'s self-selected favourable site; this paper's Microsoft-on-Microsoft COI, undisclosed-turned-disclosed), and neither is independent of other sources already in this evidence base** (he-2026-2x-mandate shares an author with the Stanford quadrant; this paper shares an author with heilman-2026-microsoft).
2. Critically, **the two E3 datapoints disagree with each other on the *shape* of the effect**, not just magnitude: He et al.'s IC-to-Principal ladder is flat (no significant heterogeneity among ICs, one manager-driven "re-entry" outlier); this Microsoft paper finds a C-shaped pattern with heterogeneity *within* the IC track itself (junior-IC lift, IC4 dip, senior-manager lift). This is direct, if imperfect (different job-ladder taxonomies, different firms), evidence *against* treating either single-firm result as a reliable read of the agentic-era seniority gradient.
3. The specific numbers most likely to circulate informally from this paper (the "+22% IC5/IC6 vs −13%/−14% IC2/IC3" figures) are **adoption-odds findings (who tries the tool), not output-impact findings**, and should never be cited as evidence about whether AI lifts the floor or the ceiling on output — only about who is more likely to try a CLI agent in the first place. This distinction is worth stating explicitly in the verdict text if this source is cited at all, to pre-empt exactly the conflation the task brief's own framing risked.
4. The paper's own output-impact heterogeneity claim (the C-shape) is verbally stated and appears to be a real analytical result, but is not quotable as an exact effect-size table from the text — this project's evidence rule against stating an effect size without a source-traceable number means the C-shape can be cited as a **directional finding** ("Microsoft's CLI-agent rollout shows larger measured PR-output gains at both the junior-IC and senior-manager ends than at the IC4 mid-level, and a similar low-and-high-tenure C-shape") but not with fabricated per-subgroup percentages.

**Suggested wording addition to the verdict (§3/§6 of tension-5-seniority.md, for the human to adopt or decline):** after the existing He et al. paragraph, add that a second, non-independent single-firm E3 source (Microsoft's own CLI-agent rollout study, microsoft-cli-agents-2026) reports a measured-output C-shaped pattern by career stage and tenure — junior ICs and senior managers gaining more than an IC4/mid-tenure reference — which is neither He et al.'s flat gradient nor the practitioner "seniors gain most" story, and that the verdict should read as: two single-firm, COI-flagged E3 datapoints now exist and they disagree with each other in shape, which if anything *strengthens* rather than resolves the "insufficient evidence" verdict — the disagreement is itself evidence that no single-firm study should be generalised, and the confidence level on "any claim about the agentic era specifically, in either direction" should remain low, now for a sharper, statable reason (active disagreement in shape between the only two measured-output E3 datapoints) rather than mere scarcity of datapoints.
