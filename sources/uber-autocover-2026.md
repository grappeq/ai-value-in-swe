## What this document is

(A) A peer-reviewed industry-track (SEIP) systems paper describing the design, rollout and evaluation of AutoCover, Uber's LLM-based multi-agent unit-test generator, with a benchmark against general coding agents, a 29-person survey, and production telemetry for August-September 2025.

(B) A practitioner-journalism summary of an Uber conference talk on its internal AI stack (MCP gateway, Agent Builder, AIFX CLI, Minion background agents, Code Inbox, uReview, AutoCover, Shepherd), with adoption and cost figures presented by Uber speakers.

## Full notes

### A. AutoCover (ICSE-SEIP 2026)

**Architecture.** Five specialised agents orchestrated in a LangGraph pipeline (sub-graphs for preparation, generation, execution, validation/repair), ReAct-style: Preparer (scenario discovery, initial coverage baseline, test-suite scaffolding), Generator (per-function generators fanned out in parallel, existing-test extender, full-file generator, already-tried deduplication), Executor (build-safe parallel execution in isolated Bazel sandboxes, per-test-case target cloning, AST-aware splicing, coverage attribution), Validator (conventions registry, mutation testing with bounded mutant count and type, linting, persistent stability cache), Fixer (targeted reversible repairs, "do no harm" rollback, frozen chronic non-improvers). Loop is Preparer -> Generator -> Executor -> Validator -> Fixer. Models named in Table 2: OpenAI GPT-5 Thinking (Preparer), GPT-4.1 (Validator), Claude 4 Sonnet (Generator, Fixer). Fallback routing across providers via Uber's internal LLM gateway.

**Viability definition.** A test is "viable" only if it executes successfully and raises code coverage or scenario coverage. Validator rejects change-detector tests and enforces stable oracles, isolation, table-driven structure.

**Modes.** CLI (on demand, edits local state), Headless (autonomous across monorepo shards, raises merge requests routed to owning teams), IDE (VS Code and forks incl. Cursor; background precompute with a 5-minute debounced invocation after file save; actions: insert, insert and ensure passes, dismiss).

**Languages.** Go, Java, TypeScript, Python (Kotlin support mentioned in the rollout timeline).

**Rollout.** Prototype/dogfooding Jun-Jul 2024; CLI and headless pilots Aug-Nov 2024; Validator-first Sep-Dec 2024; full parallel pipeline Jan-Mar 2025; IDE integration Apr-Aug 2025; available to all engineers by August 2025. Motivation: summer 2024 trials of Copilot (could not invoke build steps or obtain coverage/mock artefacts) and Cursor (poor persistence on multi-step generation, diverged from mocking conventions, long latency on large files).

**Evaluation design (three parts).**
1. *Benchmark (intrinsic):* 9 Go subjects sampled from Uber's codebase (3 basic end-to-end, 3 infrastructure, 3 product), 60-minute timeout, baselines run autonomously with the same rules and tool descriptions. Pre-deployment baseline Cursor 0.46.8; post-deployment Cursor 1.7.54, Cursor 2.3 and Claude Code 2.0.75 added. No human-written-test baseline. The "non-agentic baseline" is not a non-agentic tool: all baselines are general agentic assistants.
2. *Expert review:* two PhD-level reviewers (not authors, knowledgeable of Uber's codebase) rated final tests for AutoCover vs Cursor 0.46.8 only, on a six-point rubric (very good ... broken). Distributions bimodal; AutoCover produced no broken tests; percentages shown in the figure (33/67/44/56 etc.) are not individually attributable in the extracted text. Reviewer 1 stricter bimodal, Reviewer 2 more moderate.
3. *Production telemetry and survey:* August-September 2025 deployment data; 29 survey responses (23 active, 6 inactive).

**Benchmark results (Table 1, median across 9 subjects).** Median coverage by time budget (5/10/15/30/45/60 min): AutoCover 40.0/93.2/98.5/99.4/100/100%; Cursor 0.46.8 0/0/0/40.8/40.8/40.8%; Cursor 1.7.54 0/0/97.0/98.7/98.7/98.7%; Cursor 2.3 0/0/0/96.7/96.7/96.7%; Claude Code 2.0.75 0/0/90.4/90.4/98.1/100%. Median minutes to reach 40/80/90/95/99/100% coverage: AutoCover 4.7/7.2/8.3/10.8/19.5/41.6; Claude Code 12.8/13.8/13.8/41.4/48.9/48.9; Cursor 1.7.54 11.6 (to 95%), not reached at 99/100%; Cursor 2.3 17.0 (to 95%), not reached at 99/100%; Cursor 0.46.8 30.0 to 40% then not reached. Cursor 0.46.8 failed to produce runnable tests for three subjects. Newer baselines close most of the gap by 60 minutes. Authors state AutoCover "outperforms ... without additional tuning" for baselines.

**Production results (Aug-Sep 2025).** Per month: IDE hundreds of thousands of tests, Headless tens of thousands, CLI thousands. Viable-test success rate about 20% Java, 40% Go, 80% Python. About 44% of viable IDE tests explicitly accepted by users. Validator auto-fixes "tens of thousands" of developer-written tests; the number of fixed tests is "trending down" as generated (valid-by-design) tests increase. **About 11% of all new tests reviewed and added to Uber's codebase are generated by AutoCover** (abstract and conclusion only; no numerator, denominator, date or measurement method; no per-mode breakdown).

**Cost.** No dollar figures. Table 2 gives token orders of magnitude and cache hit rates: Preparer O(10^8) tokens 9.5%; Validator CLI/Headless O(10^6) 30.2%; Validator IDE O(10^9) 91.7%; Fixer context crawler O(10^9) 59.5%; Generator O(10^10) 53.5%; Fixer other O(10^8) 22.1%. Authors say caching "substantially" reduces cost versus a naive implementation but give no figure. Unconstrained background IDE execution produced "unpredictable and unsustainable costs", hence the 5-minute debounce and kill switches. Telemetry tracks "compute per accepted test" but it is not reported.

**Survey (N=29; 23 active, 6 inactive; respondents had generated or accepted at least 10 tests in prior two months).** Responses reflect AI test generation broadly, not AutoCover alone. Productivity improved: 83% active vs 40% inactive; positive user experience 61% vs 40%; encourages adding more tests 65% vs 67%. Rated good/excellent: usability 83%, test quality 70%, speed 65% (active); inactive users: none rated quality good or excellent. Improvement themes: style/convention mismatch (6), bloat (4), speed (4), project guidelines (4), coverage integration (3), interactivity (1).

**Failure modes and limitations stated.** Flaky/change-detector tests (hence Validator rules); verbose or redundant tests; convention mismatch; slow CLI; anonymiser corrupting code identifiers (e.g. "User") causing syntax breakage, tuned afterwards with unknown effect. Threats to validity (authors): acceptance may be influenced by coverage targets and team adoption; multiple improvements landed during the study window so effects cannot be separated, hence trends and averages only; coverage is an imperfect proxy (mitigated by scenario coverage and mutation testing); scenario-coverage accounting began later than line coverage so 2024 and 2025 signals are not comparable; expert review subjective; results tied to Uber's environment; target-selection bias (developers may point CLI/Headless at hard legacy code). Authors favour ecological over internal validity. No post-merge defect, flake-rate, mutation-score or review-time numbers are reported. The paper contains no hours-saved figure and no "5,000 tests per month" figure. (A web listing of the ICSE abstract mentions a median of four minutes per covered line; that sentence is not in the PDF text and is unverified here.)

### B. The Pragmatic Engineer (March 2026)

Figures as stated (free sections only; none has a stated measurement method, denominator or period beyond what is quoted):
- **84% of Uber devs are agentic coding users**, defined as "either using CLI-based agents or making more agentic requests than tab-completion in their IDE" (updated numbers as of March 2026, per 11 March update).
- **65-72% of code is AI-generated inside IDE-based tools**; "naturally, 100%" for AI command-line tools such as Claude Code (a tautology of definition).
- **Claude Code usage nearly doubled in 3 months, 32% (Dec) to 63% (Feb)**; IDE-based tools (Cursor, IntelliJ) plateaued. Denominator not stated.
- **92% of Uber devs use agents monthly** (intro "Impact in numbers" summary; sits alongside the 84%: not reconciled in the free text).
- **11% of pull requests opened by agents** (intro summary; detail paywalled).
- **AI-related costs up 6x since 2024**; token-cost optimisation "a growing priority" (no absolute spend).
- **Autocover "for generating 5,000+ unit tests per month"** (intro description; basis unstated).
- Tech function "almost 3,000 people".
- Qualitative: AI adoption "slower than expected, even at a forward-thinking company"; top-down mandates less efficient than engineers sharing wins with peers (challenges section paywalled; stated in intro); Anshu Chada's quote that pushing toil (upgrades, migrations, bug fixes) to AI raises engineer satisfaction (opinion, unmeasured). More AI-generated code "means more code reviews and more noise", motivating Code Inbox and uReview (stated as rationale; no measurement in the free text). Workflow shift to parallel agents creates resource and cost challenges (anecdotal).

## Measured vs self-reported

- **Measured (system telemetry or benchmark):** coverage vs time on 9 Go subjects; per-month generated test counts by mode; viable-test success rates (about 20/40/80% Java/Go/Python); 44% acceptance of viable IDE tests (a behavioural measure, not a quality outcome); cache hit rates; about 11% share of new reviewed tests (measured per authors, method undescribed).
- **Expert judgement:** two reviewers rated test quality on a rubric (subjective, N=9 subjects).
- **Self-reported:** the 29-person survey (83% vs 40% perceived productivity); the 21,000 developer-hours estimate (secondary sources only; method unknown); all PragEng adoption figures (method unstated, effectively speaker-reported).
- **Delta finding:** none can be computed. There is no pairing of perceived and measured outcomes for the same population. Notably the survey measures perceived productivity of active vs inactive users (selection effect), and the only measured counterpart is coverage and acceptance, not time or defects.

## Can / cannot support - verdicts

**Can support (A):** (1) Mechanism and design evidence that a validator-gated, build-integrated generate-validate-repair loop outperforms off-the-shelf agents on time-to-coverage in one company's Go code (directional, Tier C weight). (2) Evidence that test generation (T6) is deployable at scale with caching and routing; the cost-control lessons (debounced background execution, kill switches, uncontrolled background execution is unsustainable) are useful for RQ4 as qualitative cost evidence. (3) Failure-mode taxonomy for generated tests (change-detectors, flakiness, convention mismatch, bloat). (4) A caution that viability rates vary strongly by language (20-80%).

**Cannot support (A):** claims of developer time saved, defect reduction, or improved production quality; any effect size on delivery metrics (RQ5); generalisation beyond Uber's Bazel monorepo; that the 11% share represents value (share of tests is output, not outcome); the 21,000-hours figure; any statement about cost per test or ROI.

**Can support (B):** directional adoption signal at one large organisation: strong shift toward CLI agents (Claude Code) between Dec 2025 and Feb 2026; the claim that agent use is near-universal but adoption was slower than expected; a hype-baseline datapoint for the exec narrative ("65-72% AI-generated code" is a figure of the kind the protocol lists as a bad metric).

**Cannot support (B):** any productivity, quality or cost-effectiveness claim; the cost multiplier has no output denominator; none of the percentages has a stated method or denominator; paywalled sections unread.

## Red flags / things the orchestrator should know

1. **Three different "11%" figures that secondary sources conflate.** (i) *AutoCover:* about 11% of all new tests reviewed and added to Uber's codebase (ICSE paper abstract and conclusion; no denominator or period). (ii) *Agent PRs:* 11% of pull requests opened by agents (PragEng intro, March 2026; opened, not merged). (iii) *Backend code:* an "11% of backend code" claim attributed to press coverage/CTO statements: I did not read or verify this in either primary, and it must be sourced separately before use. Different numerators (tests, PRs, code), no shared denominator; do not merge or cite interchangeably.
2. **The 21,000 developer hours is not in the ICSE paper and has no stated method.** Secondary pages trace it to a May 2025 LangChain Interrupt talk by Uber's Developer Platform team; one secondary page reads it as a collective estimate across Uber's coding agents (Validator, AutoCover, uReview and others), not AutoCover alone; ZenML describes it as "estimated" with no calculation, and links it to a 10% coverage lift (also unexplained). The Uber engineering blog post could not be retrieved (HTTP 406; guessed URLs 404), so the original basis could not be verified. A plausible but unconfirmed construction is per-test or per-line time assumption multiplied by test volume (the ICSE listing's four-minutes-per-covered-line is mentioned in a search snippet only); this is speculation and should not be recorded as the method. Treat as self-reported Tier D-style estimate, relevance 1.
3. **Tests-per-month conflict.** PragEng says "5,000+ unit tests per month"; the paper says IDE alone generates hundreds of thousands per month (Aug-Sep 2025), headless tens of thousands and CLI thousands. Possible reconciliation (5,000+ = accepted/merged, or CLI/headless only) is not stated in either; do not cite the 5,000+ figure as AutoCover's output without this caveat. Record as contradiction candidate.
4. **COI.** Uber authors evaluating Uber's own tool; baselines (Cursor, Claude Code) run without Uber-specific tuning and quality review only against the oldest Cursor version; AutoCover versions improved continuously during the study so no clean before/after.
5. **Newer general agents largely close the gap.** By 60 minutes Claude Code reaches 100% median coverage and Cursor 1.7.54/2.3 reach 98.7%/96.7%; AutoCover's advantage is speed, not final coverage. Era transfer note for the tension on specialised vs general agents.
6. **Coverage as the success measure.** The paper itself cites coverage as an unreliable proxy; no mutation score or flake rate is reported as a number. Viability also requires only raised coverage, not a bug-finding ability.
7. **Acceptance rate (44% of viable IDE tests) is a "suggestion-acceptance" style metric** (PROTOCOL §5.7). Of all generation attempts the viable share is 20-80% depending on language.
8. **PragEng paywall.** The "Impact in numbers" detail and the review-load/uReview/Code Inbox sections are behind the paywall; only intro-level figures are recorded. The Tier C source is partly unread; any escalation decision on whether to obtain the full text is the orchestrator's (Tier C, so not a BLOCKED trigger under CLAUDE.md).
9. **Recency:** both primaries are under 12 months old; no supersession check required, though a March 2026 update note changed figures in (B).
10. **Journalist COI.** Orosz is a former Uber employee (to 2020) and publicly sympathetic to Uber's engineering culture.
