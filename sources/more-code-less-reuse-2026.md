## Dataset provenance (independence flag)

The paper does **not** collect its own PR corpus. It reuses the **AIDev dataset** (Li, Zhang & Hassan, 2025, arXiv:2507.15003, "The Rise of AI Teammates in Software Engineering (SE) 3.0") — a shared, public, third-party dataset of autonomously-submitted agent PRs mined from GitHub. This is a significant **independence flag**: any other source in this project that also draws on AIDev is not an independent triangulation point relative to this one (§3 independence rule — "different organisations... not retellings of the same rollout" extends to not being draws from the same underlying corpus).

Filtering applied by these authors: Python repositories only, >500 GitHub stars (AIDev's own popularity threshold). Two sub-datasets:
- **Dataset A (Full Python Dataset):** 3,858 PRs across all filtered Python repos — used for RQ1 traditional metrics and RQ2 sentiment analysis.
- **Dataset B (Core Case Study):** 617 PRs from a single repository, **crewAI** (the most agent-active repo in AIDev) — used for the flagship redundancy analysis (RQ1) only, because the semantic-embedding pipeline is computationally expensive. Note: crewAI is itself an AI-agent framework project, which may not be representative of typical enterprise/brownfield codebases.

No specific agent tool names (Claude Code, Copilot, Devin, OpenHands, etc.) are disclosed in the extracted text — "Agentic-PRs" is inherited as a category from AIDev without per-agent breakdown. This is a gap: we cannot attribute findings to any specific tool or model.

## Methodology summary

Two RQs, both against the same AIDev-derived corpus:
- **RQ1:** How does AI-generated code differ from human-generated code in terms of code quality?
- **RQ2:** How does reviewer sentiment differ between AI-generated and human-written PRs?

RQ1 uses (a) traditional static metrics — Lines of Code, multi-line strings, blank lines, Cyclomatic Complexity, computed with Radon — and (b) a novel **Max Redundancy Score (MRS)**: for each newly-added function, the maximum cosine similarity (via CodeSage-Large code embeddings) to any pre-existing function in the base snapshot, after using PyRef to strip out genuine Move/Rename refactors (to avoid counting legitimate code movement as "redundancy"). The **Average Max Redundancy (AMR)** aggregates MRS per PR to compare Agent vs Human groups. This targets specifically **Type-4 (semantic) clones** — logically duplicate code with different syntax/naming — which the authors argue LLMs are structurally prone to producing (as opposed to human copy-paste Type-1/2 clones), and which literal/token-matching clone detectors miss.

RQ2 runs review comments (from AIDev's `pr_comments`, `pr_review_comments_v2`, `pr_reviews` tables, bot comments excluded) through **Emotion English DistilRoBERTa-base** (Hartmann 2022), an off-the-shelf sentiment classifier over Ekman's six basic emotions (anger, disgust, fear, joy, sadness, surprise) plus neutral. Per-PR average emotion scores are compared between Agentic-PRs and Human-PRs. Comments over the model's 512-token limit are excluded.

This is important for the CLAUDE.md measured-vs-self-reported distinction: **neither RQ1 nor RQ2 is a self-report survey.** Both are automated measurements — RQ1 measures the code artifact directly; RQ2 measures reviewer *affect as expressed in text*, inferred by an NLP classifier, not asked of reviewers directly. So RQ2 is not the same kind of "perception" as a self-reported productivity survey (e.g. METR's belief-vs-reality gap) — it's a measured proxy for reviewer reaction, with its own validity risk (the classifier is trained on general English, not code-review discourse; authors flag this explicitly as an external-validity threat).

## Findings (one per record)

### Finding 1 — Redundancy: agents produce far more semantic code duplication than humans
Using Dataset B (617 crewAI PRs), Average Max Redundancy (AMR) for Agentic-PRs = **0.2867** vs Human-PRs = **0.1532** — a ~1.87× increase. Mann-Whitney U test: **p < 0.001**. Distributions (violin plot, Fig. 2) show the two groups are similar at low MRS but diverge sharply in the medium band (0.3–0.8), where agents produce disproportionately more near-duplicate functions.
- Measurement basis: **measured** (code artifact analysis, not self-report).
- Task types: T4 (feature dev in mature/popular codebase), T5 (refactoring/tech debt — code reuse failure).
- Can support: a specific, statistically robust, era-appropriate (E3) claim that agentic code generation under-reuses existing code relative to humans, in one real, actively-agent-worked open-source Python repo.
- Cannot support: generalisation beyond this one repository (crewAI) — the authors themselves flag this as a threat to external validity; cannot attribute to any specific agent/tool since AIDev pools multiple agents; cannot speak to non-Python ecosystems.

### Finding 2 — Reviewer sentiment: reviewers react no worse — arguably better — to AI PRs
Across Dataset A (3,858 PRs), Agentic-PRs show a higher proportion of neutral, joy and sadness sentiment in review comments; Human-PRs show a higher proportion of disgust, anger, fear and surprise. Neutral is the dominant sentiment for both groups. **No exact numeric means/medians or p-values are given in the text for RQ2** — the comparison is qualitative, backed only by box-plot figures (Fig. 3) showing distribution shapes per emotion. This is a real gap relative to RQ1's rigor.
- Measurement basis: **measured** (automated sentiment classification of actual review-comment text), but it is itself a *proxy* for developer perception/reaction — not a self-reported survey of how reviewers felt, and not validated against reviewer self-report.
- Task types: T7 (code review).
- Can support: a directional, statistically under-specified claim that human reviewers do not express more negative sentiment toward AI-authored PRs than human-authored ones — arguably the opposite.
- Cannot support: precise effect-size claims (no numbers given); cannot rule out sentiment-classifier misclassification of terse/technical review language, which the authors explicitly flag as an external validity threat ("may misinterpret technical discussions... as neutral or negative").

### Finding 3 — The divergence itself: quality signal and sentiment signal point opposite ways (the paper's headline claim)
The paper's central contribution is the **disconnect** between Finding 1 (measured: agents produce significantly more redundant code) and Finding 2 (measured-proxy: reviewers do not express more negative sentiment towards agent PRs — if anything, less). Authors' interpretation: AI-generated code is "surface-level plausible" (syntactically correct, passes tests), so reviewers lower their vigilance and fail to catch semantic duplication, leading to "silent technical debt" accumulating unflagged. They speculate this connects to RLHF-driven sycophancy/plausibility optimisation in code-generation models (citing Sharma et al. 2023, Fanous et al. 2025 on LLM sycophancy) but present no direct causal test of that mechanism — it is discussion/interpretation, not a further measured result.
- Measurement basis: **both**, compared as a delta — this is exactly the CLAUDE.md-mandated "divergence as its own finding."
- Task types: T7 (code review), T5 (tech debt).
- Can support: a decision-relevant, E3-era, peer-reviewed empirical instance of "review process does not catch a real, measured quality defect in agent output" — directly useful for RQ2 (measurement trustworthiness — human review sentiment is a poor proxy for code quality in the agentic era) and RQ3 (failure map — code reuse/duplication as a specific agent weakness) and cross-references PROTOCOL §5 tension 4 (GitClear duplication/churn findings) with an independent methodology (embedding-based semantic clone detection vs GitClear's churn metrics) — though not an independent *dataset* (see AIDev caveat above) relative to any other AIDev-based source in this project.
- Cannot support: a general "reviewers are fooled by AI code" claim beyond redundancy specifically — the paper does not test whether reviewers miss other defect classes (security, correctness bugs), only redundancy.

### Finding 4 — Null/negligible result: traditional static metrics barely distinguish agent from human code
Cyclomatic Complexity distribution is essentially indistinguishable between groups: of 22,311 file-pair changes, 18,968 (85.02%) score zero complexity for both; only 11 pairs total (0.05%) are "high risk" (CC ≥ 10), split 6 human / 5 agent — no meaningful separation. LOC-addition difference is statistically significant (Human 23.01 vs Agent 23.78 lines, Δ = -0.77, p < 0.001) but the magnitude is trivial — a case of statistical significance without practical significance, likely driven by very large N (3,858 PRs).
- Measurement basis: measured.
- Task types: T4.
- Can support: a null/negligible-effect finding that should be recorded with equal diligence per evidence rule 3 — surface-level static code metrics (LOC, cyclomatic complexity) do not meaningfully distinguish agent from human contributions; the real quality gap only appears via the deeper semantic redundancy analysis (Finding 1). Methodological point for RQ2/RQ6: large-N significance testing on trivial-magnitude differences can look impressive but isn't decision-relevant — a caution for what to instrument internally.
- Cannot support: any claim that agent code quality is equivalent to human code quality overall — the paper explicitly frames this null result as showing traditional/pass-rate-style metrics *miss* the real problem (redundancy).

### Finding 5 — Removal behaviour: humans strip out far more code (especially docstrings/comments) than agents do
Table 1 removal figures: multi-line-string removal Human 26.26 vs Agent 8.47 (Δ = 17.79, p < 0.001, highly significant); LOC removal Human 25.51 vs Agent 16.60 (Δ = 8.91 — **no significance star shown in Table 1**, despite the body text describing it as part of the same "significantly... alongside" sentence as the multi-line-string result). This is a **text/table inconsistency** worth flagging: the prose implies both removal differences are significant, but the table only marks multi-line-string removal as such; LOC removal and blank-line removal/addition deltas are mostly unstarred or only weakly starred (blank-line addition Δ=0.14*, p<0.05).
- Measurement basis: measured.
- Task types: T5 (refactoring/dead-code/cleanup), T4.
- Can support: a directional signal that human developers clean up/remove old code (including stale documentation strings) substantially more than agents do during a PR — consistent with, and a plausible mechanism for, the redundancy build-up in Finding 1 (agents add without pruning).
- Cannot support: a precise, uniformly-significant "agents remove less code" claim — only the multi-line-string component is clearly significant per the table; treat the LOC-removal gap as suggestive, not confirmed, until the discrepancy is resolved.

## Grading

- **Tier: B (structured observational, large-N, no randomisation).** Peer-reviewed (MSR '26, ACM), statistically tested (Mann-Whitney, significance testing throughout), N=3,858 PRs for the broad comparisons and N=617 for the flagship redundancy result — but observational (naturally-occurring PRs, no random assignment/counterfactual design), and the headline redundancy result is a **single-repository case study** (crewAI only) by the authors' own admission, which caps how far Finding 1 can generalise. This combination — rigorous stats, real peer review, but non-randomised and single-repo for the flagship metric — sits squarely in Tier B ("carries claims with caveats"), not Tier A.
- **Era: E3 (agentic).** Studies "Agentic-PRs" — PRs autonomously submitted by AI coding agents via the AIDev SE-3.0 dataset — unambiguously agentic-era tool modality, not autocomplete or chat-assisted. No era-mixing concern.
- **Independence:** Not an independently-collected dataset — built entirely on the public AIDev corpus (Li, Zhang & Hassan 2025). Flag this against any other AIDev-derived source already or later in this project's evidence base for triangulation purposes. No vendor/consultancy funding found; multi-university academic authorship (Japan × Canada); COI risk low but "AI-Driven SE Summit 2025" acknowledgment noted for transparency.
- **Population:** GitHub PRs from popular (>500-star) Python open-source repositories; no developer seniority, demographic, or organisational data — this is a repository/artifact-level study, not a developer-level one. No cost, licence-spend, token-spend, or time-to-complete data anywhere in the paper.

## Threats to validity (as stated by authors, §6)

- **Internal:** Reliance on PyRef to correctly filter out genuine Move/Rename refactors before scoring redundancy; only 10 samples manually verified as a check. Redundancy analysis (the flagship result) restricted to one repository (crewAI) purely for computational-cost reasons — explicit "may not generalise" admission.
- **External:** Python-only; behaviour in other languages (Java, C++) untested. Sentiment model trained on general English text, not code-review-specific discourse — may misclassify technical disagreement as neutral/negative, undermining confidence in the RQ2 comparison specifically.

## Red flags / things to watch

1. RQ2 (sentiment) has materially weaker statistical rigour than RQ1 (redundancy) — no exact numbers, no significance tests reported for the emotion comparisons, only qualitative "higher proportion" language plus box plots. Treat Finding 2/3 as directionally suggestive, not a precisely quantified effect size.
2. Flagship redundancy number (1.87×, p<0.001) rests on a single repository (crewAI, itself an AI-agent-framework project) — generalisation risk is real and authors say so themselves.
3. Shared dataset (AIDev) means this is not an independent triangulation point against any other AIDev-based source elsewhere in the evidence base.
4. Minor prose/table inconsistency in Table 1 (removal-metrics significance) — flagged as Finding 5's caveat.
5. No agent-tool identity, no cost data, no seniority data — cannot speak to RQ4 or the seniority-asymmetry tension (§5.5) at all.
