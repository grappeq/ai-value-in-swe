## What this document is
A between-subjects, randomised online user study. 54 CS students built a small website with either (A) an Aider agent (GPT-4.1) that edits their code via accept/reject diffs, or (B) a GPT-4.1 chatbot with no access to their code that may only give short text or generic snippets of five lines or fewer. Outcomes: initial-task accuracy and time, comprehension of the user's own code, accuracy on a follow-up extension done without the agent, and self-reported ratings. The paper adds exploratory analyses of prompt and review behaviour and design recommendations.

## Full notes
**Design.**
- Random assignment to two arms; 59 recruited, 5 dropped for failing attention checks (in the background quiz or comprehension quizzes), n=54, 27 per arm (the n=27 per arm figure is stated in Section 5).
- Population: CS students at two US colleges, 17 BSc / 31 MSc / 11 PhD (of the 59 recruited). Self-reported 5.4 +/- 0.3 years coding and 16.2 +/- 1.4 months coding with AI. Extra course credit (alternative assignment offered); IRB-approved. No professionals.
- Control: 12-item multiple-choice HTML/CSS/JS background (BG) quiz from public LinkedIn skill assessments, validated by one front-end engineer.
- Initial task: "zic-zac-zoe", a tic-tac-toe variant on a 5x5 board (two symbols per turn; win by full row or column; CSS centring; status element). Three files (HTML/JS/CSS), 50-minute limit, criteria shown as text or video. Participants were not told that comprehension questions or an extension would follow.
- Tools: custom VibeJam IDE; Aider with GPT-4.1 versus a GPT-4.1 chatbot restricted to syntax help (chatbot prompt refuses wider queries). The chatbot arm was designed so users must write or adapt code themselves, mirroring StackOverflow-style adaptation.
- Comprehension: 12 multiple-choice questions per user (6 recall, 6 reasoning; two each on HTML, CSS, JS), generated per user from their own code by GPT-5.2, answered without seeing the code.
- Extension: add a four-corners win condition, red/blue symbol colours, and a reset button; 20 minutes, chatbot only for everyone (agent arm first did a 5-minute chatbot warm-up); 12-rule rubric judged by Gemini-3.1 Pro.
- Total scripted task time about 70 minutes plus quizzes in one session.
- Scoring: initial code accuracy = proportion of 15 hidden rubric rules met (Gemini-3.1 Pro judge); time-to-submission secondary. Validation: authors A and B agreed on 98% of rules on 20 submissions; Gemini vs Author A kappa 0.96. Question validity: two students answering distractor-only questions scored 0.38 (chance 0.5); pass rates 94-100% on study questions; one extraction oddity in about 4% of chatbot questions.
- Prompt counts: initial task 5.8 +/- 0.4 (agent) vs 11.6 +/- 2.5 (chatbot); extension 6.8 +/- 0.9 (agent) vs 4.7 +/- 0.6 (chatbot).

**Outcome 1: speed and accuracy (initial task).** Agent users were more accurate and quicker than chatbot users (Section 4.1, Figure 4). The text gives NO means, SEs, test statistics or p-values for this outcome; they are in Figure 4 only. Do not infer a magnitude. A secondary blog reporting "35 percentage points" appeared in search; it is not in the paper text read and is unverified.

**Outcome 2: comprehension.** Agent users "score much lower" on recall and reasoning questions. The only statistic in the text is the Figure 1 caption: p<0.002, Cohen's d>0.80 (test not named; group means not given). The deficit persists after adding initial accuracy to the regression (agent group still significantly lower; initial accuracy has a small, insignificant coefficient; adjusted R2 0.40 to 0.42). By question type (Appendix A.9.2) the deficit holds for recall (identifiers), snippet identification and purpose questions, but not for "how would the website change" questions (Table 7, not read; text says no stark difference, possibly because they were too easy). BG ability strongly predicts comprehension in both arms.

**Outcome 3: extension without agent.** Agent users "not much higher" than chatbot users (Section 4.1). Figure 1 caption: the agent edge "reverses when controlling for initial task accuracy". Regression: adding initial accuracy and comprehension lifts adjusted R2 for extension accuracy from 0.05 to 0.34 (Section 4.3 text) or 0.22 (Figure 7 caption); the paper is internally inconsistent on this. Both added coefficients are significantly positive. Appendix A.5 path model (lavaan, simplified, omits the BG-by-condition interaction): significant indirect effects via initial accuracy (positive) and comprehension (negative) offset each other; total and direct effects of condition on extension accuracy are non-significant. So: no demonstrated extension penalty or benefit from the agent; the proposed mechanism is offsetting scaffolding vs comprehension, which is observational mediation.

**Outcome 4: BG ability.** BG predicts initial accuracy only with chatbots (agents equalise users); weakly predicts extension accuracy (adjusted R2=0.05), in chatbot but not agent users. Authors' reading: agents can mask skill differences; novices submit code as accurate as experts but with worse comprehension.

**Interaction patterns (agent arm only, n=27, exploratory).** Prompt strategies labelled by Gemini-3 Flash over 152 prompts (Table 1; users can appear in several rows): explain codebase 0.635 comprehension (n=6), copy task criteria 0.654 (n=25), iterative debugging 0.692 (n=5), turn criteria into code syntax 0.743 (n=9). Review behaviour (Table 2): auto-accept 0.615 (n=6; BG 0.603), override changes 0.661 (n=15), Accept All 0.664 (n=20), Accept each file 0.777 (n=7; BG 0.714). Authors note the per-file group tends to have higher BG and still sits below the chatbot mean. Appendix A.4 BG-controlled regressions on proportions of each interaction type: prompts, intercept 0.7141, BG 0.5688, copy -0.4685, exploratory -0.7447, debugging -0.3378; review, intercept 0.4751, BG 0.5088, auto-accept -0.3343, override -0.2136, Accept All -0.1585. No CIs or p-values in text. Readability (Figure 8, coefficients not in text): fewer lines, lower comment proportion and lower Halstead-style volume in the agent's JS file went with higher comprehension.

**Self-reported (Table 3, 1-5, mean +/- SE).** Helpful: agent 4.7 +/- 0.2 vs chatbot 3.3 +/- 0.2. Mental effort: 1.9 +/- 0.2 vs 3.7 +/- 0.2. Reviewed responses: 3.2 +/- 0.3 vs 4.0 +/- 0.2. Code feels my own: 2.5 +/- 0.2 vs 3.7 +/- 0.2. I understand my code: 3.3 +/- 0.3 vs 4.2 +/- 0.2. Could easily extend: 3.1 +/- 0.3 vs 3.2 +/- 0.2. Prefer no AI in new tasks: 1.4 +/- 0.2 vs 1.9 +/- 0.2. Prefer chatbot in new tasks: 3.2 +/- 0.3 vs 2.7 +/- 0.2. Prefer agent in new tasks: 4.2 +/- 0.2 vs 3.9 +/- 0.2. Prefer switching between the two: 4.6 +/- 0.2 vs 4.1 +/- 0.3. (First number in each pair is the agent arm's rating, second the chatbot arm's.) No significance tests in text. Appendix A.6: perceived understanding and extendability correlate significantly and positively with measured comprehension and extension accuracy (Table 8 not read), i.e. users were reasonably calibrated.

**Qualitative themes.** "I didn't have to think at all"; some users felt no need to review because they could preview the site; agents changed unexpected code or added unrequested features; comments and modular structure eased extension but this was onboarding rather than understanding; users split on whether understanding matters ("What's the point of learning all this when the AI can build it out for you?").

**Stated limitations.** CS students only; two website tasks (as worded); few workflow customisation features and no user-chosen agents (Cursor, Codex); LLM-generated questions, rubrics and judges may contain errors; n=27 per arm moderate so all analyses exploratory; short-term productivity may suffice for personal projects; no longitudinal test. No pre-registration or multiple-comparison correction mentioned.

**Transfer to professionals.** The paper does not study professionals and does not claim transfer. It cites Kam et al. (2025) for professionals valuing understanding, and says findings "may not apply to other user groups and tasks".

**Authors' design recommendations.** (1) Discourage low-effort prompting (refusal or nudges to rewrite copy-paste prompts in technical terms; needs classifiers). (2) Promote active review rather than passive acceptance. (3) Optimise agents for readable code without reward hacking. (4) Explore routers that decide when AI or the user implements. (5) Give users more control over execution and ensure trace summaries are faithful. (6) Make the value of understanding explicit. (7) Test longer horizons with periodic comprehension quizzes.

## Tier & era grading
- **Tier: A for design, scope-limited.** Randomised, controlled, with a pre-specified background control and validated measures; this clears the Tier A bar on method. Held back from carrying claims on its own beyond its scope by: n=27 per arm, students only, one small greenfield task, authors' own "exploratory" label, in-progress preprint, LLM-generated questions and LLM judging, and headline statistics available only as a caption (p<0.002, d>0.80) with the speed result unquantified in text. Treat as "A-, narrow". Relevance for our decisions is as a mechanism and design signal on comprehension, not as an effect-size anchor for professional work. If the orchestrator prefers a conservative grade, B is defensible; I have used A for the randomised design and kept the population caveat in every row.
- **Era: agent arm E3 (weak form); chatbot arm E2.** The agent is Aider with GPT-4.1 proposing diffs, reviewed in a custom IDE, over three small files; it is agent-style edit delegation but without a long autonomous plan-execute-verify loop on a real codebase. Tagged E3 as instructed, with this caveat. The chatbot arm is E2 but deliberately restricted (no code access, <=5-line outputs), so it behaves like near-unassisted coding with snippet help; the comparison is agent vs near-manual, not agent vs ordinary chat. The model (GPT-4.1) is a 2025 model.
- **Independence/COI:** academic, NSF-funded; no vendor funding. Authors' prior platform VibeJam is reused. Participants were course-credit students recruited via instructors. No Tier D flag. Authors also hold a design-agenda ("agents should support understanding"), visible in the title framing; the title says "Improve Productivity" though speed magnitude is unquantified in text.
- **Recency check (rule 8):** source is under 3 months old; not applicable. Version/venue check done: v1 only, no published venue.

## Measured vs self-reported
| Item | Basis | Result |
|---|---|---|
| Initial-task accuracy and time | measured | agent better; magnitude not in text |
| Comprehension of own code | measured | agent lower; p<0.002, d>0.80 (caption) |
| Extension without agent | measured | no clear difference; total effect non-significant |
| Helpfulness | self-reported | agent 4.7 vs chatbot 3.3 |
| Mental effort | self-reported | agent 1.9 vs chatbot 3.7 |
| "I understand my code" | self-reported | agent 3.3 vs chatbot 4.2 |
| "Could easily extend" | self-reported | agent 3.1 vs chatbot 3.2 |
| Preference for agent in new tasks | self-reported | 4.2 (agent arm) vs 3.9 (chatbot arm) |

**Delta (own finding).** Perception tracked measurement on understanding: agent users rated their own understanding 0.9 points lower and measured comprehension was also lower. So this is not the METR-type overestimation gap; users were calibrated about understanding (Appendix A.6 supports). The gap that exists is between preference and understanding: users who said they understood less still rated the agent as preferable (4.2) and most wanted to switch between tools (4.6). A second mismatch: users in the agent arm rated "could easily extend" 3.1 vs 3.2, and measured extension accuracy was also not clearly different, so that pairing agrees. No self-reported speed estimate was compared with measured time in the text.

## Can / cannot support — verdicts
- **Can support (medium-low confidence):** in a short greenfield task, delegating code writing to an edit-applying agent raised initial task completion while lowering comprehension of one's own code in students; low-effort prompting and passive acceptance go with lower comprehension (correlational); users knew they understood less and still preferred the agent. Supports the RQ4 and RQ6 skill-formation theme (comprehension as a cost and an instrument), as one randomised student study.
- **Can support as a null:** no demonstrated downstream extension benefit or penalty from the agent in 20 minutes.
- **Cannot support:** any effect size for professional developers; speed magnitude (unquantified in text); durable skill loss (no delay, no longitudinal follow-up); brownfield or mature-codebase claims (T4); generalisation to Claude Code or Cursor-class agents; causal claims about prompting or review habits (observational subgroups, n=5-25 cells); transferability of the agent-vs-restricted-chatbot contrast to agent-vs-ordinary-workflow.

## Red flags / things the orchestrator should know
1. The headline speed result has no numbers in the text; do not quote a percentage. The comprehension effect is quantified only in a figure caption (p<0.002, d>0.80), test unnamed.
2. Internal inconsistency: extension-model adjusted R2 goes 0.05 to 0.34 in Section 4.3 text but 0.05 to 0.22 in the Figure 7 caption.
3. Comparator is artificial: a chatbot that cannot see code and returns <=5-line snippets. The comprehension gap is therefore agent vs near-manual coding, closer to "writing code yourself aids understanding" than to an E2 chat workflow.
4. Agent condition is an early/weak E3 (Aider diffs, small three-file greenfield). Do not use as evidence about agentic work in mature codebases.
5. Extension task: the paper's own mediation shows offsetting effects and a non-significant total; the title's "improve productivity" and "harm understanding" are both true in the initial task and comprehension only. The extension null should be kept visible.
6. Measurement relies on LLM-generated questions and LLM judges (GPT-5.2, Gemini-3.1 Pro, Gemini-3 Flash); validated by the authors but not independently. No pre-registration or multiple-comparison correction.
7. Inconsistent wording: perception-vs-measured here confirms calibration, so do not cite the paper as another perception-reality-gap instance (contrast with PROTOCOL tension 1).
8. Relevant to the skill-formation theme: it is the in-domain counterpart to Shen and Tamkin (2026), which the paper cites and matches on sample size; the orchestrator may wish to check how the two relate (not opened, per blindness rule).
9. Not read: Tables 7 and 8, Figures 1, 4-8 (images). Exact group means for accuracy, time, comprehension and extension are in the released data/GitHub repository, which was not accessed.
