# Source: demirer-2026-writing-vs-shipping

## Identity

- **Citation:** Demirer, M., Musolff, L. and Yang, L. (2026). *Writing Code vs. Shipping Code: Productivity Effects Across Generations of AI Coding Tools.* NBER Working Paper 35275. Issued May 2026; revised September 2026.
- **URL:** https://www.nber.org/papers/w35275 (full PDF read: https://www.nber.org/system/files/working_papers/w35275/w35275.pdf; earlier version read for the version comparison: .../w35275/revisions/w35275.rev0.pdf, listed on the NBER page as a 28 May 2026 revision)

- **Status:** NBER working paper. Not peer-reviewed (NBER disclaimer). Funding stated: Mack Institute for Innovation Management (Wharton) and Chicago AI Incubator, "in part".
- **Authors:** Mert Demirer (MIT, NBER), Leon Musolff (Wharton, NBER), Liyuan Yang (MIT).
- **Full read:** yes (main text, Appendices A-F, tables OA-3 to OA-6; figures read via captions and in-text numbers only, as figure graphics do not extract).

## What this document is

An observational economics paper using public GitHub activity for roughly 500,000 developers, with AI adoption dates taken from confidential Microsoft telemetry (autocomplete, GitHub Copilot agent mode) or inferred from traces left in public repositories (Claude Code, GitHub Copilot coding agent, OpenAI Codex). It estimates the effect of adopting each of three tool generations on weekly activity at six levels of a production hierarchy (lines of code, files, commits, pull requests, repositories, releases), fits a stylised nested-CES model to explain why gains shrink up the hierarchy, and adds descriptive aggregate series from GitHub and four app marketplaces. It does not measure quality, review effort, incidents or cost.

**Abstract headline numbers (30% / 180% / 240%; 80% projects; 30% releases).** These are cumulative, summing the marginal effects across generations (Figure 1: "cumulative effects of adopting all tools up to and including a given generation"). By arithmetic the commits figures are 30.2, 30.2 + 153.2 = 183, and 183 + 60.7 = 244; repos 11.9 + 47.3 + 19.2 = 78; PRs 173; files 398; lines 2,446 (Figure 1 labels 25.5x, 5.0x, 3.4x, 2.7x, 1.8x, 1.3x match). **Releases +30% is 9.0 + 19.8 = 29%, i.e. autocomplete plus sync only; no async release effect was estimated** (releases are repository-level and cannot be split between agent and human). The "240% to 80% to 30%" chain in the abstract therefore compares a three-generation commits number with a two-generation releases number. The additive construction is my reconstruction; the paper text does not spell it out. No CI is given for the cumulative figures.

### 3. Definition of "release"

A GitHub Releases object: the repository's owner tags a commit and posts a release with notes (REST `/repos/{owner}/{repo}/releases`; only repository and creation date used). Developer-week outcome = number of distinct repositories the developer committed to in the trailing 12 weeks that had at least one release created that week. It is a repository-level event attributed to every committing developer, not a measure of user-facing delivery, and most developers never create releases (autocomplete p95 of weekly releases is 0.09). Release regressions use far fewer pairs (autocomplete 1,609; sync 8,912). "Projects" in the abstract = distinct repositories touched, which includes new throwaway repositories.

### 4. Elasticity of substitution (0.23)

Not estimated from developer-level variation with a standard error. It is a **calibration**: a nested CES hierarchy (six layers; AI either augments human effort or partially automates it with review still required) is fitted to the six-layer autocomplete effect profile by minimising squared log differences, with share parameter q = 0.76 and elasticity s = 0.23 constant across layers. Autocomplete is used because it enters only at the code-writing layer; sync and async effects lie above the autocomplete-calibrated counterfactual at every layer, which the authors read as those tools intervening at higher layers too. Cobb-Douglas fits more than 100 times worse; decreasing returns with CES fits only with implausible parameters; allowing developers to reallocate effort across layers does not improve fit. The authors call the model highly stylised and not an identification of the production function. No interval is reported for 0.23. Rev0 gave 0.25 (q = 0.75).

### 5. Mechanism evidence (experimentation versus scope)

Sync, weeks 21-30 (Table 7A): lines added +599.5 (12.3), lines deleted +1115.7 (20.5), so deletions grow faster than additions (12.2x vs 7.0x), meaning more rework; branches created +78.6 (2.4), deleted +109.0 (3.6); lines per commit +67.3 (7.9), files per commit +22.2 (1.3). Autocomplete: lines per commit +32.7 (12.1), files per commit +6.5 (2.1). Aggregate (Table 7B, adopters' repositories): share of repositories abandoned within a month of creation 60.0% (2021), 62.4, 62.7, 63.7, 67.6, 69.0% (2026 Q1 cohort), +3.9pp in 2025 alone; median lines per release 5.21k (2021) to 13.42k (2026 Q1); median files per release 48 to 76; comment-line share of releases 18.6% to 17.4%. Conclusion: scope (bigger units) explains little; most attenuation is experimentation filtered out downstream. The authors note abandoned work is not necessarily low quality. This is inferred from activity patterns; no review or selection data is observed.

### 6. Marketplaces

Four marketplaces (Apple App Store, Google Play, Chrome Web Store via licensed SimilarWeb / chrome-stats data; SourceForge scraped), monthly cohorts of non-incumbent apps, usage = ratings (iOS) or installs (others) in the first three months. Descriptive time series; no regression, no attribution test.

- New apps: iOS about 33,000-45,000 per month (2023-early 2025) rising to about 108,000 by April 2026; Google Play fell from about 145,000 (2020 peak) to about 42,000 (Jan 2025) then recovered to about 99,000 by mid-2026; Chrome extensions roughly 7-fold since 2023 with a further pick-up in 2025 (growth began before agents); SourceForge slight rise.
- Usage: cohort usage did not keep pace on any platform (iOS roughly flat 2024-25; Android up modestly; Chrome down, already falling). Share of new apps with under 10 ratings (iOS), under 10 downloads (Chrome) or at most 100 downloads (Android) rose Jan 2025 to Apr 2026: iOS 78% to 87%, Chrome 19% to 33%, Android 22% to 26%.
- Interpretation offered: either marginal apps are low quality or higher production layers (testing, polish, market fit) still bind, or a consumer-side discovery bottleneck exists. The data cannot separate these. Authors also concede new apps may partly serve AI-related demand.

### 7. Heterogeneity

Only one dimension is reported: pre-adoption weekly commit activity quartile. Percentage effects are larger for less active developers (autocomplete Q1 +61% to Q4 +20%; sync Q1 +345%, Q2 +163%, Q3 +90%, Q4 +53%; async agent commits Q1 +179% to Q4 +13%). The authors caution that this resembles the prior experimental literature but that the direction may flip as tools improve. **Not reported:** developer experience or tenure, seniority, language, repository age or size, OSS versus private, task type. The paper's "cumulative" and per-tool contrasts (Claude Code +295.5% vs Codex +118.8%) may reflect who adopts rather than the tool; Claude Code adopters are early, CLI-using and plausibly more sophisticated, and GitHub Agent adopters are later than Codex adopters (Figure 3).

### 8. Dynamics

The sync effect grows with event time (+81 / +98.5 / +153 in the three bins), which the authors attribute to **model improvements, not within-developer learning**: in a fixed cohort of Claude Code adopters (first three weeks after general availability, 22 May 2025), the effect declines and stabilises through Opus 4 and 4.1, then rises sharply when Opus 4.5 becomes the frontier model. The autocomplete cohort shows no growth over time. Consequence: the sync estimates are cohort- and model-vintage-specific.

### 9. Robustness and placebos

- Docker adopters (identified by first Dockerfile commit, analogous to CLAUDE.md): short spike then settles at about +6.6% commits (+7% in the Figure 6 caption); GitHub Pro (non-AI subscription): spike dissipates in about 10 weeks to about zero. Neither shows the attenuation gradient. Authors' bounding argument: even if all of Docker's +6.6% were activity bias, 153% less 6.6% still gives about +146.6% for agents.
- Contemporaneous controls give estimates smaller by 21% on average (consistent with private AI use in the control group, but also a reminder the headline depends on the year-earlier design).
- Alternative matching gates (commit only, PR only, both), account-creation-year matching, longer matching windows (22-52 weeks), level regressions by decile, 0.1% winsorisation, active-span removal, balanced sample across outcomes: attenuation pattern preserved; magnitudes shift. The pooled sync level regression shows a pre-trend in the top two deciles (hard to match at the top of the distribution).
- Validation against a field experiment: autocomplete +30.2% (SE 2.7) versus +26% (SE 10%) in Cui et al. (2026) for the same tool and period (the paper's authors overlap with that study).
- External validity: the authors state (i) public open source only, little enterprise coverage; (ii) software is the most advanced AI domain, so quantities may not extrapolate; (iii) estimates reflect tools available to mid-2026. They cite firm-level studies as finding smaller effects with the same attenuation (Chen and Stratton 2026: commits +20%; Sarkar 2026: merges +39%, lines +49%; second-hand, not verified here) and argue bottlenecks should bind harder inside firms.

### 12. Authors' stated limitations (condensed)

Open-source only with little enterprise coverage; software may be unrepresentative of other domains; estimates reflect tools to mid-2026; under 18 months of post-launch agent data and a slow usage response is possible; productivity-driven entry cannot be fully separated from demand-driven entry in marketplaces; ratings and downloads are imperfect proxies for consumer surplus; sync/async attribution is blurred because the same tools run in both modes; cross-tool differences may reflect adopter selection; the production model is stylised.

### 13. Quality, review and incident outcomes

Absent. The only quality-adjacent evidence is: bug-fix share of commit messages unchanged after adoption (autocomplete and sync); no fall in commit size; comment-line share of releases not rising; abandonment of repositories rising. There is no defect, incident, security, revert, review-time or review-quality measure. The review bottleneck is a modelling inference (low elasticity), not an observed review queue; the paper cites Chen and Stratton (2026) for direct review-time evidence from firms.

## Tier & era grading

**Tier: B (structured observational, large-N telemetry).** Justification: very large N, a defensible quasi-counterfactual (matched, time-shifted control, placebos, flat pre-trends, multiple robustness checks, external validation against a field experiment) and transparent data appendices. Not Tier A because it is not randomised, the control is a different calendar year (identification rests on no aggregate calendar-time shocks), adoption is self-selected and inferred from traces for most tools, async has no counterfactual group, the elasticity is a calibration without uncertainty, and the paper is an un-reviewed working paper that changed materially between two versions within four months. Not Tier D: authors are academics, but see independence.

**Independence / COI.** Not vendor-published, but: adoption dates for the autocomplete and GitHub Sync samples come from confidential Microsoft data supplied to the authors; two of three authors are paid Microsoft research consultants and former Microsoft postdocs (NBER disclosure); Demirer co-authored the Microsoft/GitHub Copilot RCT of 2023. (2026), which this paper uses as its validation point; they are not independent confirmations of each other. Population selection: restricted to developers active on public GitHub (about 95% of autocomplete subscribers dropped), so results speak to active public-OSS developers.

## Measured vs self-reported

Everything is **measured** (platform telemetry: commits, lines, files, PRs, repositories, releases, branches, marketplace listings and ratings/downloads). There are no surveys, no self-reported productivity, and no perception-versus-reality delta in this source. No cost data. Adoption is inferred (subscription dates, first agent use, CLAUDE.md or bot-authored PR traces), not observed use intensity for most tools. Because outcomes are activity counts, "measured" here means measured activity, not measured value or output quality.

## Can / cannot support — verdicts

**Can support**
- Activity outcomes (commits, lines, PRs) rise strongly after adoption of agentic tools among active public-OSS developers, and rise far more at the top of the chain than at releases: attenuation from +153% commits to +20% releases (sync). Supports RQ5 directionally (local speedup does not translate proportionately downstream) and §5.6 bottleneck displacement as a pattern, at E3, measured, medium confidence.
- Measurement lesson for RQ2/RQ6: commits and lines are poor proxies for shipped output (lines +957% vs releases +19.8% for the same people); activity multiples should not be quoted as productivity. Era-independent.
- Marketplace pattern: supply of new apps up since 2025, cohort usage flat, rising share of unused apps (descriptive).
- Autocomplete as a pre-agentic baseline (+30%), consistent with the Cui et al. field experiment.

**Cannot support**
- Any quality, stability, review-load or incident claim (none measured). Cannot be used for §5.3 (throughput vs stability) or §5.4 (quality debt) beyond null proxies.
- Any claim about enterprise, closed-source or mature-brownfield production codebases (public OSS only; the authors themselves say enterprise effects are smaller). Cannot resolve the greenfield/brownfield split (§5.2); there is no task or codebase-maturity split.
- Seniority asymmetry (§5.5): only an activity-quartile split, not experience.
- A causal "productivity multiple" for any team: headline numbers are percentage changes in activity counts for adopters selected on being active, against year-earlier controls.
- A precise elasticity: 0.23 is a stylised calibration with no interval.
- A single stable E3 effect size: results depend on model vintage and moved by 40-80% between two versions of the same paper.
- Mixing "240% to 80% to 30%" as a like-for-like chain (releases exclude async).

**Confidence:** medium for the direction and the attenuation gradient (consistent across tools, specifications and placebos); low for the exact magnitudes.

## Red flags / things the orchestrator should know

1. **Version drift.** May 2026 (rev0) vs September 2026: 100,000+ to 500,000+ developers; 40/140/180 to 30/180/240; projects 50% to 80%; elasticity 0.25 to 0.23; "moderate" to "sharp" increase in new apps. Sync commits +109% to +153%; async +34% to +61%; autocomplete +36% to +30%. Releases +30% unchanged. The current PDF has no change log. Cite by revision, and treat the magnitude as unstable; the attenuation qualitative message is stable across both versions.
2. **Headline arithmetic.** The abstract's cumulative figures are sums of marginal effects, and the 30% releases excludes async (not estimated), so "240% falls to 30%" is not like for like. The additive construction is my reconstruction.
3. **Activity metrics are gameable (PROTOCOL §5.7).** Commits, lines, PRs and repositories are all outputs the AI can inflate (agent-authored commits count as output; agent PRs count as PRs). What the paper does about it: (a) tests commit size (no decline) and bug-fix share (stable); (b) tests verbosity via comment-line share of releases (flat) and notes verbosity cannot inflate repos or releases; (c) uses the attenuation itself as evidence that raw activity overstates delivered output; (d) Docker and GitHub Pro placebos for activity bias. It does not use any quality-weighted output, merged-PR acceptance, reverts or defects. The authors' framing treats commits as task-level output; we should treat them as an activity metric and releases as a coarse, also-gameable proxy for delivery (a release is a tagged object, not shipped value).
4. **Selection into adoption.** Adopters are self-selected, must be active on public GitHub, and are observed through traces (Claude Code via CLAUDE.md; async only if used on public repos, 24% of async users). Tool comparisons (Claude Code +295% vs Codex +119%) likely reflect adopters; the authors say so. Control is from a different year; no aggregate calendar shock is assumed. Contemporaneous controls give 21% smaller estimates.
5. **Percentage gains from low baselines.** Averages of individual percentage changes weight low-activity developers heavily (the authors illustrate this: 1 to 2 commits and 100 to 110 gives 55%, versus about 11% in levels). Their level regressions agree, but headline percentages should not be read as changes in total team output.
6. **Sync/async blur.** Async adopters also use sync mode (about five-fold increase in sync use), and sync tools can run autonomously; the sync and async split is partly attributional.
7. **Vendor-data dependence and disclosure.** See Tier & era grading. Microsoft data is confidential and not replicable by outsiders for the autocomplete and GitHub Sync samples.
8. **No quality outcomes**, and no review data, despite review being the central mechanism claimed.
9. **Recency check (CLAUDE.md rule 8):** source is under 12 months old; no retraction found. Superseded by its own revision, so use the September version.
10. **Escalation check:** no taxonomy break (activity metrics, T-codes not assignable, recorded as '—'/T3-T4 undifferentiated). Not paywalled. No contradiction was assessed here (blind extraction); candidate tension for the orchestrator to cross-reference, not asserted: METR 2025 (slowdown) versus this paper's large activity gains; activity versus output measures.
