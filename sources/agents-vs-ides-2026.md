# agents-vs-ides-2026 — CMU study of agent adoption vs prior AI-IDE use in OSS repos

## Verification status

**VERIFIED — full text read** (arXiv HTML v2, plus abstract page, plus MSR '26 programme page). Cross-checked abstract wording, Table 1/2 figures, and limitations language against two independent fetches of the full text. No paywall.

**Important correction to the Phase 0 flag: this is NOT a randomised controlled trial.** It is explicitly a **quasi-experimental staggered difference-in-differences (DiD) design with propensity-score-matched controls**, using observational repository-level panel data. The authors themselves call it a "causal study" and use causal language throughout ("causal assessment," "intent-to-treat effects"), but at no point is anything randomly assigned — adoption of agents/AI-IDEs is a self-selected decision by each repository's maintainers, not researcher-assigned. This means it is **not** "only the second RCT after METR" as flagged; METR (task-level random assignment) and Paradis et al./Google (subject-level random assignment) remain the only two coding-agent RCTs identified so far. This paper's evidentiary value is different in kind: large-N, real-world, repo-level, matched-observational — a genuinely useful complement, not a second RCT.

## Design verdict (detailed)

- **What was randomised: nothing.** Treatment (agent adoption; AI-IDE adoption) is observational — determined by which real-world repositories' maintainers happened to start using which tools, and when.
- **Identification strategy:** staggered adoption DiD. Treatment date = earliest month with an agent-attributed PR (agent attribution via a cascading heuristic: branch-prefix → PR-author login → first-commit author name → GitHub "bot" actor type → default human). Repositories split into two treatment cohorts: **Agent-First (AF)** — no detected AI-IDE activity (config artefacts for Copilot/Cursor/WindSurf) at any point before or during agent adoption — vs **IDE-First (IF)** — AI-IDE activity detected before agent adoption. Each treated repo matched via propensity-score matching (logistic regression on dynamic pre-treatment characteristics, reported AUC 0.92–0.99) to control repos that had not (yet) adopted; later adopters and never-adopters both serve as counterfactuals in the staggered design.
- **n:** AF = 401 treated + 606 matched controls; IF = 117 treated + 73 matched controls. (IF sample is markedly smaller — flagged by the authors as an unbalanced panel.)
- **Population:** open-source GitHub repositories, inclusion filtered to ≥10 stars and ≥10 agentic PRs per treated repo (excludes toy/spam projects). Contributor population (professional vs hobbyist engineers) is **not characterised** — a real gap; we do not know if these are paid professionals, students, or hobbyists, only that they are real-world OSS contributors on non-trivial repos.
- **Setting:** real work (actual merged/attempted PRs on live repositories), not constructed tasks — closer to METR's "real issues" setting than Peng et al.'s standardised greenfield tasks. Brownfield by default (existing repos with history), though repo age/maturity varies a lot between cohorts (see below) and there is no explicit greenfield-vs-brownfield design axis.
- **Period:** PRs parsed retrospectively Jan 2024 – Nov 2025 to reduce left-censoring; adoption is concentrated May–Jul 2025.
- **Outcome data:** exclusively **measured/telemetry** — GHArchive for repo activity (commits, LOC added, contributors, PRs, issues, stars, forks) and SonarQube for static-analysis warnings, cognitive complexity, duplicate density, comment density. **No self-report, survey, or interview data anywhere in the paper** — a useful contrast to METR/Peng, and it means this source cannot speak to the perception–reality gap (§5 tension 1) at all, only to measured outcomes.

## Grading

- **Tier: A**, per PROTOCOL §3's explicit inclusion of "large-N telemetry with counterfactuals" — but flagged clearly as **quasi-experimental, not randomised**; weaker causal identification than an RCT (relies on parallel-trends assumption, which the authors themselves report isolated violations of — see Limitations below). Treat as "strong Tier A observational," one notch below RCT-grade confidence, when it is cited.
- **Era:** mixed by design, and this is the paper's whole point.
  - **Agent (treatment) tools: E3, unambiguous.** Classified agents: Claude (Code), GitHub Copilot [agent mode], Cursor [agent mode], Devin, Codex, Jules, OpenHands, Codegen, Cosine, Tembo — all autonomous, PR-generating, multi-file agents. This is squarely the plan–execute–verify modality PROTOCOL §2 defines as E3.
  - **"AI IDE" (prior-exposure) tools: E2/E3 boundary, ambiguous — same caveat as the Cursor entry in metr-2025-rct.** Classified as Copilot, Cursor, WindSurf, detected via editor config artefacts; these products span autocomplete, chat, and (increasingly through 2025) their own light agent modes, and the paper does not disaggregate which sub-modality was in use. Read the IF cohort as "prior chat/IDE-assistant exposure, of unspecified E2–E3 sub-modality," not as a clean E2 baseline.
- **Independence:** Academic authors, all Carnegie Mellon University (Agarwal, He, Vasilescu — Vasilescu is an established, independent mining-software-repositories researcher). No funding or COI statement found in the text; no vendor affiliation identified for any author. **No Tier-D flag.** Secondary dependency worth noting: the underlying AIDev dataset (Zhang et al., arXiv:2602.09185) is a separate, also-independent academic artefact — no vendor sponsorship identified there either at time of check (not deep-verified; flagged as a lead below, not confirmed).

## Key findings

Task-type tag: **repository-level aggregate, cannot be decomposed into T1–T11** — commits and PRs mix all task types (features, fixes, refactors, docs, etc.) indiscriminately. This is a genuine taxonomy mismatch, not a triage failure: the paper's unit of analysis (repo-month) is coarser than PROTOCOL's task-type schema. Record as **"T-mixed / unresolved"** rather than force a T-code; do not use this source's headline effect sizes to support any single task-type claim in the evidence table.

1. **Agent-First (AF) velocity — large, front-loaded, persistent (measured).** Agent adoption in repos with no prior AI-IDE history: commits **+36.25%** (β=0.309, SE=0.051, log scale, p<0.001), lines added **+76.59%** (β=0.569, SE=0.103, p<0.001). Dynamic event-study estimates (Fig. 2, 6-month window): spike at adoption month of roughly **+111% commits, +216% lines added**, settling to a still-elevated **+49% to +109% lines added** through month 6 — i.e. **not transient**, unlike the IF cohort below. [T-mixed; measured; no CIs reported, only SEs — note as a reporting gap]
2. **IDE-First (IF) velocity — small, not significant, and reverses (measured).** Repos with prior AI-IDE exposure show a much smaller and statistically non-significant average effect on adopting agents: commits **+3.06%** (β=0.030, SE=0.092, ns), lines added **−6.34%** (β=−0.066, SE=0.189, ns). The dynamic estimates show a short-lived bump of **+16% to +28% commits** in months 0–2, which **decays and reverses** to roughly **−35% commits and −61% lines added by month 6**. This is the paper's central novel comparison and its most decision-relevant finding: **agent adoption's velocity payoff is front-loaded and only material for repos with no prior AI-tooling experience; for already-AI-adopting repos it is statistically indistinguishable from zero on average and trends negative over time.** [T-mixed; measured]
3. **Quality degradation — persistent in both cohorts regardless of velocity (measured).** Static-analysis warnings rise **≈18%** overall (AF +17.73%, β=0.163, SE=0.048, p<0.001; IF +19.00%, β=0.174, SE=0.114, not significant given SE) and cognitive complexity rises **≈39%** overall (AF +34.85%, β=0.299, SE=0.059, p<0.001; IF +42.87%, β=0.357, SE=0.114, p<0.01). Both effects are described by the authors as persistent through the 6-month dynamic window, i.e. **quality debt does not fade even where velocity gains do** (IF cohort: velocity effect reverses to negative by month 6, but complexity/warnings stay elevated). [T-mixed; measured]
4. **Duplication — null in both cohorts (measured, negative result).** Duplicate density: AF +7.92% (β=0.076, SE=0.044, ns), IF −0.94% (β=−0.009, SE=0.056, ns). Neither reaches significance — recorded here with equal diligence per CLAUDE.md §3 as a genuine null, not folded into the "quality risk" headline. [T-mixed; measured; null]
5. **Comment density — diverges by cohort (measured).** AF +4.34% (β=0.042, SE=0.028, ns); IF **+22.30%** (β=0.201, SE=0.055, p<0.001). Authors' interpretation: teams with prior AI-IDE experience lean on agents for documentation too, a pattern not present in agent-first-only repos. This is the one metric where IF shows a materially larger, significant effect than AF. [T-mixed; measured]
6. **Mechanism claim (authors' interpretation, not directly measured):** "Agentic tools act as high-throughput contributors primarily in new-to-AI workflows, but yield diminishing returns in AI-saturated ones... [agents in already-AI-adopting repos] likely face higher coordination and integration costs that limit throughput." This is authorial interpretation of the pattern, not a separately measured mechanism (no direct measure of coordination/integration cost is presented) — flag as **interpretive, not measured**.
7. **Parallel-trends violation (authors' own limitation, self-reported by the authors about their own design):** "We also observe isolated significant pre-treatment coefficients in static-analysis warnings and code complexity... concerning and highlight a limitation of our quasi-experimental design and the underlying data." Not judged pervasive enough to indicate a sustained pre-trend, but an explicit, honestly-disclosed threat to the DiD identification for the quality outcomes specifically (less so for velocity).
8. **No IDE-vs-agent head-to-head on the same metric scale within a single regression** — the AF/IF split is a moderator of the *agent-adoption* effect (i.e., "does agent adoption help more or less depending on prior AI-IDE history"), not a direct randomised or matched comparison of "developers using an AI IDE" vs "developers using an autonomous agent" doing the same work. Read the "modality comparison" framing in the title as **"does agent adoption's marginal effect depend on prior IDE-AI exposure,"** not as a clean IDE-vs-agent RCT-style contrast.

**Self-reported vs measured:** entirely measured/telemetry; **zero self-report data in this paper.** Cannot inform the perception–reality gap (§5 tension 1) directly, but is a clean measured-only data point to set against METR's measured-vs-self-reported pairing.

**Limitations (authors' own, extracted verbatim/near-verbatim):**
- Isolated pre-treatment coefficient violations in warnings/complexity (parallel-trends caveat, above).
- Attribution noise in agent-vs-human PR classification: "remaining attribution errors primarily introduce noise in treatment timing rather than systematic bias, likely attenuating effects toward zero" — unquantified residual misclassification.
- Left-censoring: tool releases pre-date the Jan 2024 data start; mitigated by retrospective parsing but not eliminated.
- Cannot measure usage intensity or developer-level interaction — effects are **intent-to-treat** (repo "adopted" the tool, not "used it heavily"), which likely understates the true per-use effect in either direction.
- Control-set subsampling capped at 10,000 candidates/month, a scale-driven approximation in the matching procedure.
- No confidence intervals reported anywhere — only coefficients and standard errors on the log scale. (Percentages in this record are back-transformed via exp(β)−1 from the reported β; verified consistent with the authors' own stated percentages where given.)

## What this can and cannot support

Tier-A (observational, matched-DiD, not randomised) evidence that autonomous coding-agent adoption in real OSS repositories produces large, sustained commit/LOC-throughput gains **only** in repositories with no prior AI-tooling history, with those gains fading to null-or-negative within six months where AI-IDEs were already in use — while static-analysis warnings and cognitive complexity rise durably (~18%/~39%) in **both** cohorts regardless of whether the throughput gain persists. It **cannot** support: claims about individual developer time-savings or task success (repo-level aggregate, not task-level); any professional/seniority breakdown (population uncharacterised); any perception-vs-measured claim (no self-report data collected); a task-type-specific claim (T1–T11 not resolvable); or a true random-assignment causal claim (design is matched-observational, with an authors-acknowledged partial parallel-trends violation).

## Cross-reference notes (for orchestrator; not written to contradictions.md)

- **vs metr-2025-rct:** Different metric and different population, so this is a complement, not a contradiction. METR measures *task-level completion time* for 16 highly-repo-familiar developers on their own large mature codebases and finds AI **slows them down 19%** (measured) while they believe they were faster. This paper measures *repo-level commit/LOC throughput* across hundreds of OSS repos and finds throughput **rises** sharply — but only where agents are the *first* AI tool the repo has seen; where prior AI-IDE use exists (arguably closer to METR's "developers already have Cursor/Copilot habits" setting, though METR's devs were mostly agent-inexperienced specifically with Cursor: only 44% had prior Cursor experience), the throughput effect is null-to-negative by month 6 — directionally consonant with METR's slowdown finding, even though the two studies measure different things (time-to-complete vs commits/LOC produced) and LOC/commit-count is exactly the kind of metric PROTOCOL §5.7 flags as gameable. **Recommend NOT treating "LOC added +76%" as a productivity gain claim on its own** — it is at least as consistent with the scope-creep/verbosity mechanism METR itself found (47% more LOC per forecast-hour in the AI-allowed condition) as with genuine output gain. The quality-metric findings here (rising complexity/warnings, persisting even as throughput fades) triangulate well with METR's mechanism analysis (low AI reliability, cleanup burden) and independently corroborate the GitClear churn/quality-debt tension (§5 tension 4) with large-N, non-vendor, telemetry evidence — this is a genuinely useful three-way triangulation point (GitClear + this paper + METR's qualitative note that a majority of developers make major changes to clean up AI output).
- **vs peng-2023-copilot-rct:** Not directly comparable (Peng: RCT, standardised greenfield task, completion-time metric, single-suggestion Copilot E1 modality; this paper: observational, real heterogeneous OSS work, commit/LOC throughput, E3 agents). No contradiction to log — different design tier, different era, different metric — but both point the same direction on the greenfield/brownfield-style split: gains are largest for the "least AI-encumbered / freshest" context (Peng's greenfield tasks; this paper's agent-first, smaller/less-starred repos) and shrink or reverse in the more established/complex context (this paper's IDE-first, higher-star repos). Useful as a second, independent, large-N contributor to PROTOCOL §5 tension 2 (greenfield vs brownfield split), alongside Stanford/Denisov-Blanch telemetry.
- **Perception-vs-reality (§5 tension 1):** no self-report data at all in this source — it cannot confirm or contradict the METR gap, but it is a clean "measured only" data point, useful methodologically as a contrast case (shows a large-N causal-flavoured study can be run on pure telemetry with zero perception data, unlike METR/Peng which paired both).
- **Bottleneck displacement (§5 tension 6):** the authors' "higher coordination and integration costs" explanation for the IF cohort's fading throughput is a plausible bottleneck-displacement story (review/integration friction absorbing the gain) but is **interpretive, not directly measured** in this paper — no PR-review-latency or merge-time metric is reported. Flag as a hypothesis worth testing against a source that does measure review latency, not as evidence in itself.
- **Quality debt (§5 tension 4):** strong, independent (non-vendor, academic, large-N) corroboration that complexity and static-analysis-warning growth is a real, durable, measured phenomenon under agentic adoption specifically (not just autocomplete-era, per GitClear) — strengthens the case that GitClear's pattern replicates into the E3/agent era specifically, with a different methodology and different data source.
