## What this document is
A mixed-methods descriptive study of how developers use ChatGPT for software design. (a) A mining study of 291 design-related shared ChatGPT conversations found on GitHub; (b) an online survey of 65 practitioners. Observational, cross-sectional, no comparison group, no outcome measure. It is a usage-characterisation paper, not an effectiveness paper.

## Full notes

### 1. Data
**Mining dataset.**
- Own mining, extending the authors' prior TOSEM paper (Li et al. 2026, 2,547 shared conversations, May 2023 to June 2024). Not DevGPT by name. They added 670 conversations (June 2024 to January 2025), giving 3,217 conversations in total, all relabelled. Window: May 2023 to January 2025 (20 months).
- Collection: GitHub search for the string `chat.openai.com/share/{id}` across five sources (Code, Commits, Issues, Pull Requests, Discussions); duplicates and non-English removed. GitHub caps at 1,000 results per query; worked around by language qualifier and a crawler for Discussions. Authors state the dataset is not exhaustive.
- Design identification: manual labelling against inclusion criteria I1-I4 (design pattern mentioned; architecture topics; code/module organisation and dependencies; design trade-offs) and exclusion criteria E1-E3 (pure implementation minutiae; business rules only; IDE/config). First author labelled; second and third authors adjudicated unsure cases. 291 of 3,217 (9.0%) retained; 2,926 excluded. By source (total / design): Code 1,377/91; Commits 1,067/67; Issues 377/43; Pull Requests 325/63; Discussions 71/27 (sums verified).
- Unit of analysis: 376 "design task instances" extracted from the 291 conversations (a conversation can hold up to six tasks across four categories).
- ChatGPT versions: **not reported.** The paper says only "the version of ChatGPT available at that time" and that models and interfaces changed over the 20 months. Share links point to chat.openai.com/chatgpt.com web conversations. Era is therefore E2 by modality (web chat, copy-paste), established from the sharing mechanism rather than from a stated model list.
- Coding: open coding and constant comparison. Pilot of 30 conversations double-coded by authors 1 and 4; the full set was coded by author 1 alone and rechecked. **No inter-rater agreement coefficient for the full set** (authors state this as a limitation).

**Survey.**
- Online Google Form, 11 questions (4 closed, 3 semi-open, 4 open). Invitations emailed 6 June 2025; 1,130 sent (200 pilot); 65 valid responses by 21 June 2025; response rate about 5.8%. Pilot sample (19 valid of 200) retained because the instrument was unchanged.
- Recruitment: (i) emails of GitHub developers who had shared ChatGPT conversations (34 valid responses); (ii) members of popular LinkedIn software development groups (31 valid). Both channels self-selecting for LLM users. Valid-response filters excluded respondents who answered "Never" to using LLMs for design.
- Roles (n=65): Developer 27 (41.5%), Tester 12 (18.5%), Architect 9 (13.8%), Requirements Engineer 7 (10.8%), Project manager 4 (6.2%), Team Leader 3 (4.6%), Consultant 3 (4.6%).
- Experience: over 5 years 29 (44.6%); 3-5 years 17 (26.2%); 1-3 years 12 (18.5%); under 1 year 7 (10.8%). About 71% (46/65) over three years.
- Countries: **not reported.** Only that the survey was reachable "in different countries" and that four responses were non-English (two German, one Japanese, one French). Only 41.5% are developers; one-fifth testers, which is a weak population for system design.
- Survey is not independent of the mining study: the answer options for SQ4-SQ7 were the mining-derived categories, shown without definitions. Authors concede it "complements but cannot independently validate" the mining results.

### 2. Design-task taxonomy (RQ1), n=376 task instances
Interface and Protocol Design 73 (19.4%); Use of Design Patterns 62 (16.5%); Architecture Design 52 (13.8%); Data Model Design 43 (11.4%); Code Refactoring 39 (10.4%); Security Design 34 (9.0%); Performance Optimization 31 (8.2%); User Interface Design 23 (6.1%); Component Dependency Optimization 19 (5.1%). Sub-codes inside Architecture Design: system decomposition and modularisation 17; event-driven and messaging integration 10; stream-processing topology 9; workflow orchestration boundaries 7; multi-tenancy 6; CQRS 3.
- Survey (SQ4, multi-select, n=65): 176 category selections, mean 2.7 per participant; all nine categories selected by at least one person; 7 "Other" responses reassigned (3 patterns, 2 architecture, 2 data model). Per-category survey counts appear only in a figure not recoverable from the text.
- The authors note none of the nine categories is requirements-to-design translation (the topic of most LLM design literature) and that patterns and interface tasks need little project context whereas architecture tasks do.

**Design level (Figure 6b, n=376):** Detailed design 203 (53.99%); Architectural 112 (29.79%); Code idiom 61 (16.22%). Survey (SQ7, multi-select, 96 selections): Detailed 46/65 (70.8%); Architectural 31 (47.7%); Code idiom 19 (29.2%). Within-category: Component Dependency Optimization is 63.2% architectural; Design Patterns 75.8% detailed.

### 3. Interaction patterns (RQ2) - purpose of the opening prompt, n=376
Knowledge Query about Design 121 (32.18%); Code Generation for Design 114 (30.32%); Recommendation of Design Solution 89 (23.67%); Verification of Design Solution 52 (13.83%). The "knowledge acquisition vs design-related code generation" pair together is 235/376 (62.5%, derived). Survey (SQ6 multi-select, 120 selections): Knowledge Query 43/65 (66.2%); Recommendation 31 (47.7%); Code Generation 27 (41.5%); Verification 19 (29.2%).
- Dialogue rounds per task: median 5 (IQR 2-11), mean 6.18 (SD 5.33), max 68. Single 58 (15.4%); 2-3 106 (28.2%); 4-10 85 (22.6%); over 10 127 (33.8%). Rounds are a proxy for effort or difficulty; the paper stresses they are not a success measure.
- By category (median rounds): Architecture Design 11 (0 single-round, 57.7% over 10 rounds); Performance 11 (61.3% over 10); Component Dependency 12 (68.4% over 10); Security 10.5 (50.0% over 10); Interface/Protocol 3; Design Patterns 2 (48.4% single-round). Iteration is concentrated where the answer depends on project-specific constraints.
- Survey SQ5 (self-reported typical rounds): single 9 (13.8%); 2-3 13 (20.0%); 4-10 26 (40.0%); over 10 17 (26.2%). Mining vs survey round distributions diverge; authors attribute this to task-level observation vs retrospective perception and to the time gap (survey June 2025).

### 4. Perceived benefits (RQ3, SQ8 free text, n=65; multi-coding; 116 mentions)
More effective search engine 25 (38.5% of participants); Early detection of design flaws 22 (33.8%); Reduced overhead from design tasks 19 (29.2%, derived); Quick project onboarding 17 (26.2%, derived); Innovative ideas 17 (26.2%, derived); Technology selection 9 (13.8%); Concept interpretation 7 (10.8%). The two text-reported participant percentages are 38.46% and 33.85% (top two) and 13.85% and 10.77% (bottom two); the middle three are derived by me as count/65.
- Technology selection (9/65, 13.8%) is among the least-cited benefits, which is worth noting because the abstract lists it first.

### 5. Perceived limitations (RQ4, SQ9 free text, n=65; multi-coding; 118 mentions)
Lengthy outputs 32 (49.2%); Inexecutable code from design 28 (43.1%); Hallucinated results 21 (32.3%, derived); Unclear articulation of requirements 18 (27.7%, derived); Limited source-file uploading 11 (16.9%); Contextual reliance 8 (12.3%).
- Project-context-related limitations are spread across three categories (unclear requirements 18, limited file upload 11, contextual reliance 8); "contextual reliance" alone is the least-cited. Reading the abstract's "dependence on project context" as a headline is stronger than the counts support. The three context-flavoured categories are overlapping but separately coded, so no deduplicated union is available.

### 6. Seniority and codebase maturity
- Seniority (descriptive only, small cells, no tests): 12 of 29 participants with over 5 years' experience reported typically needing over 10 rounds, vs 1/12 (1-3 years) and 0/7 (under 1 year). All 8 "contextual reliance" mentions and 9 of 11 "limited source file uploading" mentions came from participants with over 5 years. Among participants with under 1 year of experience, "innovative ideas" was the most frequent benefit (5 of the 7 mentions coded for that group). Interpretation is confounded: more senior participants may attempt harder tasks, or simply articulate context issues more; no outcome ties seniority to better or worse design results.
- Role: all 9 architects selected Performance Optimization; none of the 12 testers selected Architecture, Security or Component Dependency. Authors caution against generalising.
- Codebase maturity: **not measured.** No data on codebase age or size. The only proxy is the authors' observation that conversations come from code, commits, issues and PRs, so design work attached to an implementation change is likelier than early-stage architecture decisions (selection effect, stated in 5.1.4).

### 7. Outcomes
**No outcome of any kind is measured.** No design-quality rating, correctness assessment, time, effort, rework, defect or cost data. The authors say so repeatedly: rounds "do not measure task success", RQ3/RQ4 data "are not designed to measure time, effort, or rework, and contain no counterfactual", the study "can neither corroborate nor contradict" the METR RCT. They list design-quality and labour-cost measurement as future work. They also note that LLM-generated design content quality was not graded in the 291 conversations.

### 8. Agentic tools
None. The study is of ChatGPT web chat (and "other LLMs" in the survey, unnamed). Agents are mentioned only in related work (ChatDev, SWE-bench). Authors state findings may not transfer to later generations of assistants or other tools. Survey (June 2025) did not ask which tools respondents used, so respondents' "LLM" experience could include early agentic tools, but this is not recoverable.

### 9. Authors' limitations (v2)
Self-selected samples (shared public conversations; 5.8% response rate); convenience recruitment via GitHub and LinkedIn; first-author-only coding of the full set, no kappa; survey options anchored on mining categories; mining/survey time mismatch and model drift over 20 months; ChatGPT-only; non-exhaustive GitHub retrieval; observational design with no causal claims; "no inferential statistics".

## Tier & era grading
- **Tier: C (weak) - descriptive practitioner/usage signal.** It does not meet Tier B (no telemetry with population denominators, no outcomes, hand-coded self-selected corpus) and PROTOCOL Tier A is out of reach. If the orchestrator prefers B-weak-end for "systematic academic mining", the verdict does not change what the source can support. Grade C because it supports only directional claims about what design tasks developers bring to a chat tool and what they say about it.
- **Era: E2 (chat-assisted).** ChatGPT web chat, shared-link conversations, May 2023 to January 2025, survey June 2025. Per PROTOCOL §2 E2 evidence is admissible only as baseline, methodology, or era-independent effects. Model versions unreported, so any "pre-GPT-4o vs later" split is not possible.
- **Independence:** academic; state funding (NSFC); no vendor involvement; no COI declared. Tier D flag: none. Selection flag: survey invitees partly drawn from developers who publicly share ChatGPT chats, an enthusiast subpopulation.
- Peer-review status: preprint v2, "submitted to a journal". Not a published paper; a preprint substitution rule is not needed (not paywalled).

## Measured vs self-reported
- **Measured from logs (but hand-coded by one author, no kappa):** usage distributions from the 291 conversations: task categories (n=376), design level, prompt purpose, rounds per task, sub-codes. These measure *what was asked and how long the exchange ran*, not whether it worked. Sample is the self-selected set of publicly shared chats.
- **Self-reported:** all survey results: benefits (116 mentions), limitations (118 mentions), typical rounds (SQ5), SQ4/SQ6/SQ7 selections, the seniority cross-tabs. Survey options for SQ4-SQ7 were anchored on mining categories.
- **Delta recorded as a finding:** typical rounds: mining over-10-rounds 33.8% vs survey 26.2%; 4-10 rounds 22.6% vs 40.0%. Prompt purpose ordering and design-level ordering agree between sources (Knowledge Query first; Detailed design first). These are not measured-vs-perceived effect gaps; they compare observed usage to recalled usage, so the delta is weak input for RQ2.

## Can / cannot support - verdicts
**Can support:**
- A baseline description of E2-era chat use for design: the work developers bring is mostly detailed design (54.0%), interface/API design (19.4%) and patterns (16.5%); architecture is 13.8% of tasks.
- Directional hypothesis (low confidence): architecture, security, performance and dependency tasks need long iterative exchanges (median 10.5-12 rounds) while pattern questions resolve in about 2; iteration load tracks need for project context.
- The gap statement for RQ1/T2: this is evidence that T2 is thinly measured; it shows usage, not value.
- A methodology note for RQ2/RQ6: rounds-per-task and prompt-purpose taxonomy are cheap log-derived instruments, but the paper itself says rounds do not measure success.

**Cannot support:**
- Any effect size on design quality, speed, cost or rework (none measured).
- Any claim that LLMs help or harm system design in mature codebases (RQ5), or that benefits are real rather than perceived.
- Any E3/agentic claim; any claim about seniority effects on outcomes (cells tiny, uncontrolled).
- Prevalence claims about developers in general (authors disclaim this themselves).

## Red flags / things the orchestrator should know
1. **No outcome measured anywhere.** This is the headline: do not enter any benefit percentage as an effect. "Early detection of design flaws" (33.8%) and "technology selection" (13.8%) are things 65 self-selected respondents said, with no check that flaws were real or selections good.
2. Survey results for RQ1/RQ2 are not independent confirmation of the mining results (answer options came from the mining study; undefined labels).
3. Single-coder labelling of 3,217 conversations and 376 tasks; no kappa. Design-relatedness judgement was by the first author with escalation, so category shares are soft.
4. Only 9.0% of mined conversations were design-related; 291 is a small and self-selected slice (public shares, not private use). Architecture share (13.8% of design tasks, or about 1.6% of all 3,217 conversations, derived) may be depressed because architecture needs context that chat cannot hold.
5. Survey population is weakly matched to the design question: 41.5% developers, 18.5% testers, 13.8% architects; 5.8% response rate; countries not reported. Invalid-response filtering removed respondents reporting no LLM-for-design use, so the sample is pro-adoption by construction.
6. Model versions not reported; 20-month mining window spans major ChatGPT changes (file upload, context length). The "limited source file uploading" limitation is plausibly already outdated, and is exactly the context problem that agentic tools address; the paper itself cannot say.
7. Abstract wording versus counts: "dependence on project context" is the least-cited limitation (8/65, 12.3%); "technology selection" is near the least-cited benefit (13.8%). Quote the counts, not the abstract's ordering.
8. Preprint, submitted to a journal; v2 revised heavily relative to the unseen v1. Cite as arXiv v2 (19 Sep 2026).
9. Recency check (CLAUDE.md rule 8) not triggered: source is under 12 months old; no later version or retraction found (v3 probe 404).
10. Possible tension with PROTOCOL §5: touches nothing directly; closest is seniority asymmetry (item 5) and bottleneck displacement (verification cost mentioned only as authors' interpretation, 5.1.3). No contradiction with other sources identified, because blindness rule forbids cross-referencing here.
