## What this document is
A single-case, practitioner-researcher study of one staff engineer delivering a product initiative (a digital-signature platform for non-account holders) with AI agents under a Spec-Driven Development (SDD) workflow. Outcomes are taken from the bank's internal delivery platform and CI/CD gates and compared with the same squad's historical throughput and the original six-sprint plan. No control group, no inferential statistics.

## Full notes

### 1. Setting
- System: digital signature platform, in production since October 2025; four microservices (Kotlin/Java backend, JaCoCo coverage) plus one Angular frontend (Jest, Cypress); nine repositories in total (4 microservices, 1 frontend, 4 supporting repos for infrastructure, storage and shared components). Integrates with an external signature provider (LACUNA). Described as brownfield: legacy integrations, compliance constraints, implicit organisational knowledge. Age, size (LOC) and pre-existing test coverage of the system are NOT reported. It is not clear how much of the initiative was new code in existing services versus new scaffolding (Sprint 1 was dominated by repo creation and infrastructure setup, which suggests a substantial greenfield component inside a brownfield estate).
- Scope: 5 features x 5 user stories = 25 stories, "scoped for a four-person squad over six sprints". Development August-September 2025, three sprints of three weeks (9 weeks).
- Plan vs actual: units are sprints/weeks. Plan 6 sprints (~18 weeks) for 4 engineers; actual 3 sprints (~9 weeks) for 1 engineer. The paper does not say who estimated the plan or how. The introduction says the 50% reduction is "relative to the team's historical baseline", while the abstract and Table IV frame it against the six-sprint plan; the two comparators are conflated.
- Engineer: staff engineer, over 8 years professional experience, 4 years in the institution's specific technology stack and business domain. Described as a generalist/T-shaped profile with end-to-end command of product reasoning, architecture, implementation and quality.
- The "four AI agents" are four roles on three products (Table I):
  - Discovery and requirements: custom "product manager" agent on StackSpot (Itau's internal AI agent platform; Pinto is a co-author of the StackSpot ICSE-SEIP 2024 paper); human-in-the-loop.
  - Specification: Devin, with multi-repo access across all nine repos; human-in-the-loop.
  - Core development (business rules, domain use cases, user-facing logic): GitHub Copilot in agent mode, human-in-the-loop, engineer reviewing each generation.
  - Non-core development (infrastructure, API integrations, message-queue config, boilerplate): Devin, autonomous.
  - Tests (unit and integration) generated by the same agents from the specifications; reviewed and complemented by the engineer.
  - Models named only as the strongest available then: GPT-5 and Claude Sonnet 4.5 (Aug-Sep 2025); which model sat behind which tool is not stated.
  - Guardrails in CI/CD: WCAG 2.1 AA checks, security scans, 90% coverage target. Homologation (performance testing, UI verification, acceptance) remained human-driven; an accessibility specialist signed off each feature manually.

### 2. Outcomes (numbers as reported)
- Delivery (Table II): features 0/2/3 = 5; stories 7/9/9 = 25; BCP delivered 79/377/434 = 890; avg lead time per story 15/20/18 d (17.6); production deployments 8/13/11 = 32; throughput 0.59/2.79/3.21 BCP per engineer-hour (total 2.20); hours per BCP 1.71/0.36/0.31 (total 0.46). Throughput rose 5.4x S1 to S3; authors attribute it partly to amortised spec effort and partly to a composition effect (more frontend stories, which BCP scores higher).
- BCP: CI&T "Business Complexity Points", assigned by an internal AI scoring component from story text, not manually adjusted; some story types (scaffolding, bootstrap) carry no BCP.
- Historical baseline (Table IV): effort per BCP 8.93 h to "2.2 hours" (-51%); baseline 4 engineers, 6 sprints; features "4-5 per 4 sprints" vs 5 in 3 sprints; time-to-market -50%. Unit inconsistency: Table II gives 2.20 as BCP per engineer-hour and 0.46 as hours per BCP, but Section V-A3 and Table IV present 2.2 as hours per BCP. This is unresolved in v2.
- Quality (Table III): backend coverage 95.7/92.3/90.4 (avg 92.8); frontend 90.2/90.1/90.7 (avg 90.3); integration tests 24+37+52 = 113 defined and passing; E2E 15+21+29 = 65 passing; WCAG automated checks 2, manual sign-offs 10; defects post-validation 1 (accessibility bug found at homologation, Sprint 2); defects post-release 0.
- Coverage and pass rates were mandatory CI/CD gates (90% coverage, 100% suites passing) so values are the gate outputs at release, not independent assessments. Authors say so explicitly.
- First-review acceptance (Table V): 90% "AI-generated code accepted without structural modification in the first review cycle; minor formatting and naming changes were not counted as rejections". Denominator, unit (lines/PRs/generations), and reviewer are not specified; the sole reviewer is the engineer. Not broken down by core vs non-core or by tool.
- Cost (Table V): original project cost R$492,000; actual staffing cost R$60,000 (-88%); AI tooling cost (estimated) R$5,000-R$7,000; "adjusted cost reduction (incl. tooling)" >85%. Derived by the reviewer: 60/492 = 12.2% (-87.8%); with tooling 65-67k, -86.4% to -86.8%. These match the person-weeks ratio 9 vs 72 (-87.5%) if rates are equal, so the figure is essentially planned headcount x planned duration vs actual, not an observed spend. How "original project cost" was derived is not described. Tooling is an estimate, with no token/licence breakdown. No review-time, rework-hours or incident-response data.
- Not collected or not reported: change-failure rate, MTTR, security-scan findings, rework hours, review duration, defect rate of the baseline team, human escalation events (collected only partly from retrospective notes), engineer wellbeing/cognitive load (despite the framing in the Index Terms and related work).

### 3. Design
- Single within-case study following Yin and Runeson and Host; practitioner-researcher: "one of the authors served as both the primary subject and the principal observer". Metrics said to be defined before execution and assessed against pre-established thresholds. Data extracted by the engineer-researcher from the internal delivery platform; reviewed by squad engineering managers as part of the standard sprint reporting cycle ("a layer of validation independent from the engineer-researcher"), but no external audit.
- Comparators: (a) the original six-sprint plan (estimator unknown); (b) the same squad's historical BCP throughput on comparable scope in the same domain. The authors note (b) controls for team familiarity but not for feature-mix differences. No parallel control.
- Related work is largely cited from literature (Peng, Becker/METR, Cui) and used to interpret, not tested.

### 4. Claimed binding constraints
- Specification quality: thorough, unambiguous specs including legacy contracts gave code needing only minor adjustment; vague specs gave "unusable outputs regardless of tool" (held for Copilot and Devin). Undocumented legacy integration contracts were the most frequent rework source, with rework exceeding the cost of fuller upfront specification. Evidence: author observation; no counts of rework events, no specification-quality measure.
- Institutional knowledge of the directing engineer is "the quality gate the removed team members would otherwise have provided". Evidence: one engineer, no variation; supported by citation of Cui et al. and Becker et al. only.
- Core/non-core partition as a repeatable heuristic (empirically calibrated in Sprint 1 via where output needed correction).
- Collapsed outer loop (handoffs, refinement meetings, architecture/security reviews) credited with "in large part" the time compression, rather than faster coding. Not measured; lead time per story stayed at 15-20 days, bound by homologation windows and sign-offs.
- Note that "not model capability" is asserted, not tested: no model or tool was varied.

### 5. Limitations and the "replacing team members" reading
- Authors list: single case; practitioner-researcher confirmation bias; same-team historical baseline not a control; brownfield indicators not instrumented; cost is direct staffing plus approximate tooling, not TCO; engineer experience is both mechanism and confound (a less experienced engineer "would likely produce different outcomes"); out of scope: security of AI code, IP/licensing, skill development, wellbeing of one-person models, labour-market effects, hallucination risk.
- On replacement: abstract says "AI does not replace team members it multiplies the throughput of the experienced engineer who remains". Body: the model is a "boundary test" not a target operating model; single point of failure; recommends hypothetically a two-person pair plus fractional product strategist (untested); additional people remain valuable for product uncertainty, unfamiliar domains, high-blast-radius systems where independent review is regulatory, and long-horizon operation. The staffing-cost headline and the "not replacement" framing sit uneasily together: the quantified cost saving is precisely from not staffing three roles.
- Authors' caveat: tools were GPT-5 / Sonnet 4.5 era; results "a lower bound" on what the configuration could produce now (assertion, no evidence).

Academic co-authorship and arXiv format do not raise it. Independence: low. Authors are employees of the studied bank, the engineer is a subject-author, and one co-author helped build the StackSpot platform used. Not vendor-published in the Tier D sense (no vendor funding stated), but the bank has a strategic interest in the AI-adoption narrative.

Copilot agent mode (multi-file), Devin (autonomous multi-step agent with multi-repo access), and a StackSpot agent for requirements; plan-execute-verify under CI gates; models GPT-5 / Claude Sonnet 4.5 era (Aug-Sep 2025). Note the E3 content is mixed: the product-manager and specification roles are chat/agent-assisted document generation, and the human-in-loop Copilot track is closer to supervised agent mode than to autonomous PR agents; only the Devin non-core track is clearly autonomous.

## Measured vs self-reported
Measured (system-recorded artefacts):
- Features/stories completed, sprint durations, deployments (32), lead time per story (17.6 d), BCP totals, integration/E2E counts and pass results (113/113, 65/65), coverage (JaCoCo/Jest), WCAG sign-off counts, defect counts (1 post-validation, 0 post-release). Caveats: coverage and pass rates are enforced gates (they cannot readily fail); BCP is assigned by an AI scorer from story text; the data were extracted by the engineer-researcher and not externally audited; defect counts depend on the observation window, which is unstated.
Self-reported or author-derived:
- 90% first-review acceptance (engineer's own judgement; denominator undefined).
- Plan of six sprints (estimator unknown) and "original project cost" R$492,000.
- The -88% / >85% staffing-cost reduction (computed, not observed; tooling cost estimated).
- Mechanisms: specification quality, institutional knowledge, outer-loop collapse, core/non-core heuristic (retrospective author observation).
- Historical baseline 8.93 h/BCP and "4-5 features per 4 sprints" (from institutional records but not independently verified; unit inconsistency with Table II).
No perceived-vs-measured delta is available: the paper reports no developer perception data, so no RQ2/RQ6 gap row can be drawn.

## Can / cannot support - verdicts
Can support (directional, Tier C, single source):
- Existence proof: a staff-level engineer with deep domain knowledge, agents across the SDLC, and strong CI gates delivered a 25-story brownfield initiative in a regulated bank in about 9 weeks with no reported post-release defects. This is a feasibility claim, not an effect size.
- Mechanism hypotheses: specification completeness (especially undocumented legacy contracts) and the directing engineer's domain knowledge as limiting factors; split of supervision by task judgement-intensity; end-to-end lead time bound by homologation/sign-off windows rather than coding speed (a bottleneck-displacement observation, tension 6; lead time per story did not fall).
- Cost data point: authors' estimate of tooling R$5-7k for the project (low-reliability, RQ4 scarcity).
Cannot support:
- Any general effect size on productivity, cost or quality in brownfield production codebases (single case, plan-vs-actual and historical-baseline comparators with acknowledged feature-mix confounds).
- The headline -51% effort per BCP or "50% faster" as measured causal effects; the former has an unresolved unit mismatch.
- Quality or stability claims (RQ5b): no incident, change-failure or long-horizon data; 100% pass rates and 90% coverage are CI gates.
- Review burden or verification-cost conclusions: no review-time or rework data; the 90% acceptance rate is a self-assessed, undefined-denominator figure of the type PROTOCOL 5.7 warns about.
- Replacement of team members: the paper does not test it and itself recommends against the one-person model as a target.
- Triangulation role: counts as one independent Tier C source toward the 3-source rule only for claims it actually evidences (feasibility, spec-quality/knowledge mechanism); the bank-affiliated StackSpot lineage should not be treated as independent of other Itau/StackSpot outputs.

## Red flags / things the orchestrator should know
1. Participant-authored: the engineer-subject is an author and the staffing/acceptance outcomes rest on his or her own judgement; confirmation bias conceded by the authors.
2. Unit mismatch in the headline productivity comparison: "2.2 hours per BCP" (Table IV, V-A3) vs Table II "2.20 BCP per engineer-hour" (0.46 h/BCP). The -51% figure cannot be reconciled without the authors.
3. Comparator ambiguity: plan (6 sprints, estimator unknown) vs historical baseline are used interchangeably; baseline productivity of "4-5 features per 4 sprints" implies per-sprint feature throughput only about 1.3-1.7x the baseline, far below the "half the time" framing (derived by the reviewer, not stated by the authors). The comparison is also 1 person vs 4, so the effort ratio (9 vs 72 person-weeks) is about 8:1 while the calendar ratio is 2:1.
4. Cost reduction is arithmetic on planned headcount, not observed spend; tooling estimated; homologation team, accessibility specialist, managers and platform teams are not costed; no TCO.
5. 100% pass rate and 90% coverage are mandatory gates; no information about test quality or escaped defects beyond one short window (production since Oct 2025; window not stated).
6. Brownfield claim is partly weakened: Sprint 1 was mostly scaffolding of new repos; brownfield indicators not instrumented; system age/size/baseline coverage not reported.
7. BCP scored by an AI component; it is a proprietary metric from a consultancy (CI&T); frontend stories score higher; composition effect admitted.
8. Single senior engineer with 4 years in domain: authors themselves say a less experienced engineer would likely differ. Fits seniority-asymmetry tension (5) only by citation, not measurement.
9. Era: only one of four roles is genuinely autonomous (Devin non-core); model versions per tool not stated.
10. Venue and peer-review status not stated; the paper claims to be "the first peer-reviewed account" in the related work, which does not match an arXiv-only record at the time of reading (v2). Treat as preprint.
11. Possible cross-reference conflicts for the orchestrator (not checked, blindness rule): any other brownfield agentic source reporting no or negative gains, or sources on senior-developer speed-ups, should be set against this single positive case; do not average.
